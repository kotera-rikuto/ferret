# Ferret 🦦

**他人のコードが読める、AI時代のエンジニアに。**

AI がコードを書く時代に、価値が残るのは「書く力」ではなく「読んで判断する力」だと考えました。
Ferret は、他人が書いたコードを読み解く力を鍛えるための Web アプリケーションです。

個人開発・実装進行中。

---

## 何をするアプリか

1. コードが提示される
2. 「この関数は何をしているか」を**日本語の自由記述**で答える
3. AI が採点し、次にどこを読むとよいかをフィードバックする

選択式にしなかったのは、コードリーディングの本質が「選ぶ」ことではなく「言語化する」ことだと考えたためです。
そのぶん採点の難易度が上がるので、設計の中心は採点エンジンになりました。

## アーキテクチャ

### 採点エンジン（2層構成）

`lib/ai/scorer.ts` が中核です。自由記述の採点を、性質の異なる2層に分けています。

| 層 | 配点 | コスト | 役割 |
|---|---|---|---|
| 層1: キーワード照合 | 20点 | ¥0 | 必須語の出現を正規表現で判定。API 呼び出しなし |
| 層2: AI 採点 | 80点 | 約 ¥0.03/回 | GPT-4o mini が文意を評価し、フィードバック文を生成 |

層1 は「用語を押さえているか」、層2 は「理解を説明できているか」を見ます。
層1 だけで足切りする高速パスは**あえて設けていません**。キーワードが揃っていても理解していないケース、
逆に自分の言葉で正確に説明できているのに用語だけ違うケースの両方を、AI に判断させたかったためです。

### 採点フロー

```
POST /api/score
  ↓ 認証チェック（未ログインは 401）
  ↓ problems から問題データ・採点基準を取得
  ↓ 層1: キーワード部分点（0〜20点）
  ↓ 層2: GPT-4o mini（0〜80点 + フィードバック文）
  ↓ user_attempts へ保存
  ↓ 保存に失敗したらスコアを返さず 500
```

採点基準（キーワード・模範回答・ルーブリック）は**すべて DB 側**に置いています。
問題ごとに基準を調整するのにコード変更もデプロイも要らない構成にしたかったためです。

## 設計上の判断と、その理由

このプロジェクトで意識的に選んだ点を、判断の根拠とあわせて残しています。

### Embedding 層を実装後に廃止した

当初は「正規表現 → Embedding のコサイン類似度 → AI」の3層構成で、
類似度が高ければ AI を呼ばずに満点を返す設計にしていました。コスト削減が狙いです。

これを実装後に廃止しました。**「偶数」と「奇数」のように、意味が正反対でも文としては極めて似ている回答を、
高類似度と判定して満点を与えてしまう**ためです。しかもこの誤りは、システムが最も自信を持っている帯域で起きます。

削減できる原価を試算すると、Pro プラン上限のヘビーユーザーでも月 ¥7 程度でした。
**その額のために誤採点のリスクを負う設計ではない**と判断し、層ごと削除しています。

判断の記録は [`ideas/採点システム仕様書.md`](ideas/採点システム仕様書.md) §7 に残しました。

### `temperature: 0` を明示する

OpenAI API は未指定だと `temperature` が 1.0 になります。
同じ回答を提出しても点数が揺れることになり、採点者としては成立しません。明示的に 0 を指定しています。

### スコアを 0/20/40/60/80 の5段階に離散化する

1点刻みで返させると、モデルは「63点」のような値を返しますが、その1点差に根拠はありません。
5段階に制限したうえで、指示に反した値が返ってきた場合は最も近い段階へ丸めています（`normalizeDeepScore`）。

### DB 保存に失敗したらスコアを返さない

採点自体が成功していても、`user_attempts` への insert が失敗したら 500 を返します。
スコアだけ返してしまうと、ユーザーには成功に見えるのに履歴が残らず、
症状がリザルト画面やステージ画面という**遠い場所に出て**原因の切り分けが難しくなるためです。

### OpenAI クライアントを遅延初期化する

トップレベルで `new OpenAI()` すると、`OPENAI_API_KEY` 未設定の環境で `next build` の
ページデータ収集ごと落ちます。初回採点時まで生成を遅らせることで、
キーがなくてもビルドが通り、障害範囲が `/api/score` の中に閉じるようにしました。

### UX 方針を AI のプロンプトまで貫通させる

「弱点」「間違い」「初心者」「失敗」といった否定的な語を UI で使わない方針にしたので、
同じ制約を採点プロンプトにも書いています。UI 側だけ整えても、
AI が生成した本文に「弱点」と書かれていれば方針は崩れるためです。

## セットアップ

```bash
npm install
cp .env.local.example .env.local   # 各値を設定
npm run dev
```

必要な環境変数は [`.env.local.example`](.env.local.example) を参照してください。
`SUPABASE_SERVICE_ROLE_KEY` / `STRIPE_SECRET_KEY` / `OPENAI_API_KEY` はサーバーサイド専用で、
`NEXT_PUBLIC_` を付けずに宣言しクライアントバンドルには含めません。
