## 任意の2欄（2026-08-17 追加）

どちらも**入れた問題だけ画面に枠が増える。** 入れない問題は今までどおりの見た目。

### `context` ── 実行結果

コードとは**別のパネル**に出る（コードの下）。`影響` 型が主な使いどころで、
スタックトレース・落ちたテストの出力・型エラーのメッセージなど、
**「実行したら何が出たか」**を入れる。

```jsonc
{
  "order": 59,
  "reading_type": "影響",
  "code": "function buildMessage(user) {\n  return `${user.name} さんの申請が承認されました`;\n}\n\nfunction notifyApproval(userId) {\n  const user = findUser(userId); // 見つからないと undefined を返す\n  return buildMessage(user);\n}",

  "context": "TypeError: Cannot read properties of undefined (reading 'name')\n    at buildMessage (notify.js:2:14)\n    at notifyApproval (notify.js:7:10)\n    at approve (approval.js:12:5)",

  "question": "エラーが「発生した箇所」と「根本の原因がある箇所」はそれぞれどこですか。ログのどの行を根拠にしたかも書いてください。"
}
```

- **コードの中にコメントで押し込まない。** 別パネルにするために足した欄なので、
  コメントに混ぜると本物の画面（ログは別の場所に出る）と読み方が変わってしまう
- ログの行番号・ファイル名は**コード側と食い違わせない。** 影響型は行を根拠に答えさせる問題なので、
  ここがズレていると正解が存在しなくなる
- 命名型の「中身を伏せる」表現はこの欄ではなく `code` に `/* …… */` を書く

### `prerequisite` ── 前提知識

問題画面の「わからない言葉があるとき」を押すと開く。**既定は閉じている。**

```jsonc
{
  "order": 1,
  "prerequisite": "const は、一度入れた値を後から入れ替えられない変数の宣言です。let は入れ替えられます。"
}
```

- **数行に留める**（400字以内。超えると DB が拒否する）。読むのに5秒で足りる分量
- **答えを書かない。** 「const は入れ替えられない」は前提知識、
  「だからこのコードはエラーになる」は答え。後者を書くと問題が成立しなくなる
- **模範解答から文をコピーして貼らない。** `npm run test:db` の I-816 が
  模範解答と長く一致する部分を探して落とす
- **採点キーワードのうち「コードに出てこない語」を書かない**（I-817 が落とす）。
  設問にキーワードを入れない理由（写すだけで層1が取れる）とまったく同じ。
  `const` や `push` のようにコード上に見えている語は書いてよい ── 隠しても画面から読めるので意味がない。
  危ないのは `undefined` `キー` `参照` のように**コードに現れない結論の語彙**で、
  これを渡すと層1が「読めたか」ではなく「写したか」の検査になる
- 採点には渡らない（表示専用）。ここに何を書いても層2の点数は変わらない
- その問題の設問に固有の語だけにする。共通の言語仕様の説明を毎問書く場所ではない

## 書き方のルール

### `core` ── 結論を1つだけ書く（最重要）

**2要素以上を詰めると、正しいが短い回答が落ちる。**

| `core` の書き方 | 「偶数だけ取り出しています」の判定 | 合計 |
|---|---|---|
| 「偶数を集めた**新しい配列を返す**」（2要素） | partial 24点 | 33点 → **不合格** |
| 「偶数だけを取り出している」（1要素） | **full 48点** | **62点 → クリア** |
> **【2026-08-17 追記】層1の配点が変わりました。**
> 均等配分（1スロット5点）から**前寄せのテーブル引き `[0, 12, 15, 18, 20]`** になっています
> （`lib/ai/compose.ts` の `KEYWORD_POINTS`）。「中核は読めているが語彙が少ない短い回答」が
> 48 + 5 = 53点でクリア閾値55に2点届かない取りこぼしへの対処です。
> **このため以下の合計点は現在の値と一致しません。** 満点20点であることと、
> 「1要素の core のほうがクリアしやすい」という結論は変わりません。
> 現在の正確な配点は `tests/unit/compose.test.ts` の §1-1（配点の検算）を参照してください。


2つ目以降の要素は `depth` に回す。**`core` はクリアのゲート、`ground` と `depth` はパーフェクト（80点）への上積み。**

### `core_reject` ── 「惜しいが違う答え」を2件以上

この問題で言いがちな誤読を書く。対義・反転（偶数↔奇数、昇順↔降順、破壊↔非破壊）を最優先で。**誤合格を防ぐ効果が最も大きいフィールド。**

### `keywords` ── ちょうど4スロット、4観点に対応

- **① 対象**と**② 結論**は「理解していればまず書く語」にする。ここが取れないと、正しい回答でもクリア帯に届かない
- ③ 根拠、④ 踏み込み で差をつける
- 各スロットに表記ゆれを2件以上。各要素は2文字以上（`"0"` `"in"` のような誤ヒットを避ける）
- **部分文字列一致**なので「偶数」は「奇数」にヒットしない一方、「再代入」は「再代入しない」にもヒットする点に注意

### `depth` ── 読解型ごとの条件

| 読解型 | full の条件 |
|---|---|
| トレース | 具体的な値・回数・順序・戻り値に踏み込んでいる |
| 意図 | 何を実現したくてその書き方を選んだのか、目的に踏み込んでいる |
| ズレ | 食い違っている箇所を特定し、どう食い違っているかを述べている |
| 影響 | どこに波及するかを具体的に挙げている |
| 命名 | 名前から読める責務と、実装が担っている責務の対応を述べている |
| 仕様 | テスト・型定義から読める契約の境界を述べている |

**`depth` は `core` から独立させる。** `core` を満たせば自動的に満たされる内容を `depth` に書くと、4観点が共線的になり「一文で4観点すべて full」が成立する。そうなるとスコア分布が「ほぼ満点」か「ほぼ0点」の二値になり、**`depth` の判定が機能しているかを測れない**（6問検証の目的そのものが果たせなくなる）。

上のステージ1の例では、初版の `depth` が「TypeError という具体的なエラー名」だった。これは `core`（const の再代入でエラー）を満たせばまず書かれる語なので、`depth` の判定条件を検証できない。`console.log` に到達しない点・`900` まで進んでいる点に限定すると、`core` を満たしても `depth` が none になる回答が現れ、初めて判定を測れるようになる。

**チェック方法:** `core` だけを満たす一文を書いてみて、それが `depth` も満たしてしまわないか確認する。満たすなら `depth` の条件が弱い。

### コードの題材

**実務由来にする。** ユーザー登録処理、APIレスポンス整形、集計バッチなど。`foo` / `bar`、動物クラスの継承といった教材向けの人工的な例は避ける（既存教材との偶然一致リスクが高く、実務の読解訓練にもならない）。

既存教材の本文・サンプルコードは流用しない。閉じてから自分の言葉で書く。

## 投入前セルフチェック

```
□ id を書いていない
□ reading_type が6種のいずれかと厳密に一致（表記ゆれ不可）
□ keywords がちょうど4スロット / 各スロット表記ゆれ2件以上 / 各要素2文字以上
□ rubric_items に core / ground / depth / core_reject の4キー
□ core_reject が2件以上
□ core に読点や「かつ」が2つ以上入っていない（＝結論1つのルール違反）
□ model_answer が4スロットすべてにヒットする   ← 最重要
□ キーワードが question 本文に含まれていない（設問を写すだけで取れる無料点になる）
□ context / prerequisite を使わないなら空文字列ではなく省略か null
□ prerequisite に答えを書いていない / 模範解答を写していない
□ prerequisite に「コードに出てこない採点キーワード」が入っていない
```

**「model_answer が4スロットすべてにヒットする」を必ず確認すること。** 模範解答自身が層1で満点を取れないルーブリックは壊れている。これ1つでキーワード設定ミスの大半が見つかる。

上4つはDBが拒否するので入れた瞬間に分かる。下は**通ってしまう**が、`npm run test:db` が機械で見る（I-801〜I-817）。**問題を追加したら必ず流すこと。**
