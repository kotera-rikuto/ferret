## 設計方針

### 到達目標

未経験〜入社3年目相当。「実務で最低限知っている必要があるもの」に絞る。

### 2軸で設計する

v1 は**言語機能（縦軸）だけ**で並べていた。v2 以降は**読解スキル（横軸）**を明示し、各問題がどちらの座標にあるかを決める。

縦軸だけで作ると「このコードは何をしていますか」→「配列を2倍にしています」という問題になり、満点しか出ず、解いても伸びない。読解訓練で伸びるのは**「意図と実装のズレを見つける」形式**である。

### 読解型（横軸）の凡例

| 型 | 問われること |
|---|---|
| `トレース` | 実行するとどうなるか（出力・戻り値・実行順） |
| `意図` | 書いた人は何をしようとしたのか |
| `ズレ` | **意図と実装が食い違っている箇所はどこか** |
| `影響` | ここを変えるとどこが壊れるか / エラーの原因はどこか |
| `命名` | 名前とコメントから責務を読む |
| `仕様` | テストや型定義から、その関数の契約を読む |

`ズレ` を全体の 15% 前後に配置する。v1 では 10問（10%）が実質すべてで、残りは機能紹介だった。

### 解の収束性

**採点の配点は全100問で「層1 キーワード部分点 20点 + 層2 自由記述 80点 = 100点」に統一する。** これは回答の自由度を担保する Ferret の差別化要素であり、問題タイプごとに配点を変えることはしない（v2 で検討した「客観問題は層1のみで採点しAIを省く」案は撤回）。

そのうえで、各問題が**解が一意に収束するタイプか**を記録する。採点方式を変えるためではなく、以下の運用に使う。

| 区分 | 内容 | 使いどころ |
|---|---|---|
| `一意` | 出力・順序・行番号・回数など、答えが一点に決まる | **採点精度の検証を最初にここで行う。** 正解が明白なので、AI採点のブレを測る基準になる |
| `記述` | 説明の質が問われ、正解に幅がある | ルーブリック設計の難所。`一意` で校正した後に着手する |

`一意` が 27問（27%）ある。**採点エンジンの精度検証は必ずこの27問から始めること。** 正解が定まらない問題でエンジンを調整すると、何がズレているのか切り分けられない。

### その他の方針

- **形式:** 全問「他人のコードを読んで説明する」形式。書かせる問題は作らない
- **配分:** JS 80問（1〜80） / TS 20問（81〜100）
- **除外:** React・Next.js（別カリキュラムとして後日作成）、DOM 操作系
- **1ステージ = 1問。** 総量を増やす代わりに**螺旋型**で接触回数を稼ぐ（後述）

## 出典と権利の扱い

### 何を参照し、何を参照していないか

本構成案で外部資料から取り入れたのは、**JavaScript / TypeScript という言語が備える機能の名称と、その一般的な学習順序**のみである。これらは言語仕様そのものに由来する事実であり、特定の著作物に固有の表現ではない（`const` / `Promise` / `keyof` といった名称は ECMAScript 仕様および TypeScript 公式仕様上の用語）。

参照資料の**本文・解説文・図表・サンプルコードは一切取り込んでいない**。以下は網羅性の確認（「実務で必要なトピックを取りこぼしていないか」のチェックリスト）としてのみ用いた。

| 資料 | 本案での使い方 |
|---|---|
| JavaScript Primer（jsprimer.net） | JS のトピック網羅性の確認 |
| サバイバルTypeScript（typescriptbook.jp） | TS のトピック網羅性の確認 |
| 各種入門記事 | 入門帯（ステージ1〜14）の粒度感の確認 |

章立ての順序は上記いずれとも一致しない。例えば jsprimer は「関数 → 条件分岐 → ループ」「プロトタイプ → 配列」の順だが、本案は「条件分岐 → ループ → 関数」「配列 → クラス/プロトタイプ」の順である。さらに v2 以降は読解スキル軸を主軸に据えたため、章の構成単位そのものが言語機能の分類から離れている（例:「壊れたときの挙動を読む」「時間差のあるコードを読む」）。

### 参照資料のライセンス実態（2026-08-10 確認）

| 資料 | 文章 | コード |
|---|---|---|
| JavaScript Primer | CC BY 4.0（出典表示で商用利用・改変可） | MIT |
| サバイバルTypeScript | CC BY-SA 4.0（表示 + **継承**） | MIT |

**注意:** サバイバルTypeScript の文章は **ShareAlike（継承）** 条件付き。文章を翻案した場合、その派生物も同一ライセンスでの公開義務が生じ、商用クローズドな問題コンテンツとは両立しない。したがって **TS 編は同資料の文章を参照せず、トピック名のみを扱う**方針とする。

### 問題作成時の遵守ルール（コンテンツ制作フェーズで必須）

1. **コード例は全て自作する。** 既存教材のサンプルコードをそのまま／変数名だけ変えて使うことを禁止する
2. **解説文・模範回答の文言を流用しない。** 参照資料を開いたまま執筆しない（閉じてから自分の言葉で書く）
3. **一次情報は言語仕様と MDN に取る。** 仕様上の挙動を確認する際は、教材ではなく ECMAScript 仕様 / TypeScript 公式ドキュメントを当たる
4. **題材は実務由来にする。** ユーザー登録処理、API レスポンス整形、集計バッチなど、業務で実際に読むコードを自前で構成する。教材向けの人工的な例（`foo` / `bar`、動物クラスの継承など）は既存教材と衝突しやすいので避ける
5. **万一の引用が生じる場合は出典を明記する。** CC BY 4.0 の資料（jsprimer）は出典表示により利用可能だが、原則として上記1〜4により引用自体を発生させない

なお `ズレ` 型の問題は「意図と食い違うコード」を題材とするため、正常系のサンプルコードを載せる既存教材との一致リスクが構造的に低い。v2 の形式転換は権利面でも有利に働く。

## v1 からの変更点と根拠

### 1. 「ズレを読む」形式への転換（最重要）

v1 は 10問（10%）しか「意図と実装のズレ」を問う設計になっておらず、残り 90問は機能紹介だった。機能紹介型の問題は満点しか出ず、識別力がない。v3 では `ズレ` 型を 15問、`意図`/`影響`/`命名`/`仕様` を合わせた非トレース型を約3割に引き上げた。

**総量を増やすより形式を変えるほうが到達レベルに効く**という判断。機能紹介を300問やっても3年目には届かないが、ズレを読む訓練を100問やれば届く。

### 2. 参照をステージ32から第1章（4・5）へ前倒し

v1 は「浅いコピーの落とし穴」が「参照」より**前**にあった。順序が逆で、前者が理解不能になる。加えて参照はオブジェクト章の話題ではなく、**プリミティブとの対比としてデータ型の直後に置くのが定石**。ここが空白のまま v1 の 27〜31 を進むと全体が砂上の楼閣になる。

### 3. TS の `strict` を最終ステージ付近から 83 へ前倒し

`strictNullChecks` を知らずに `?`（省略可能プロパティ）とユニオン型を読ませても、「なぜ `undefined` の考慮を強制されるのか」が分からず暗記になる。strict は設定の話ではなく TS の世界観であり、型の各論より前に置く。

### 4. 非同期エラーの追加（65・66・68・69・70）

v1 の第8章は4問すべて同期のエラーで、**非同期のエラー処理が丸ごと欠落していた**。実務3年目のペインの中心がここ。特に 65（`await` 忘れ）は実務バグ発生率が最も高い。

### 5. メタ読解の追加（53・54・59・79）

「命名から意図を読む」「影響範囲を読む」「スタックトレースを読む」は、他社の文法教材が作れない領域であり **Ferret の差別化の核心**。v1 には1問もなかった。

### 6. テストコード読解の追加（78・79）

「他人が書いたテストを読んで関数の仕様を答える」形式はコンセプトと完全に噛み合い、かつ**仕様が明文化されているので採点がブレない**。ライブラリ枠はまずここに使う。

### 7. 型エラー読解の追加（90・91）

TS 実務の8割は「赤い波線を読む」作業。v1 に1問もなかったのは TS 編最大の欠陥だった。

### 8. 総合演習を採点可能な形に変更（80）

v1 の「100行のユーティリティを読み解く」は**答えの幅が広すぎて採点が安定しない**。「仕様と食い違う1つを見つける」に変更し、答えを収束させた。

## 未決の論点 ── ✅ **どちらも採点システム v3 で解消（2026-08-12）**

> **`ai_rubric` は 2026-08-16 に削除済み。** 採点基準は `problems.rubric_items`（`core` / `ground` / `depth` / `core_reject[]`）で、
> **DB 制約で必須**。読解型ごとの書き方は `ideas/問題作成ガイド.md`、判定条件の切り替えは `reading_type` が担う。
> クリア閾値は 55 で、層2は4観点の重み合成（`48/16/12/4`）になったため、層1のスロット数で合否が変わる問題も消えた
> （キーワードは4個固定）。以下は当時の記録。

1. ~~**`ai_rubric` のテンプレート化を読解型ごとに行う**~~
   採点システム仕様書 §8 で「粒度の指針がないと問題間で採点の厳しさがブレる」と挙げられている論点。**読解型（トレース/意図/ズレ/影響/命名/仕様）ごとに6種のルーブリック雛形を作れば、100問すべてがそのどれかに収まる。** 問題ごとに自由記述するより一貫する。

2. ~~**クリア閾値 65点と層2の刻みの噛み合わせ**~~
   層2が 0/20/40/60/80 の5段階の場合、層2=40 では層1が満点（20）でも合計 60点でクリアに到達できない。実質「層2が 60 以上か」の2値判定になっている。加えて層1のスロット数（`20 / スロット数` 刻み）によって、同じ理解度でも合否が変わる（3スロットなら 67点でクリア、5スロットなら 64点で不合格）。**採点システムの再設計で解消する（別途検討中）**

3. **`一意` 27問を先に作り、採点精度を検証する**
   正解が明白な27問でAI採点のブレを測ってから、`記述` 73問のルーブリックを設計する。逆順にすると、ズレの原因が「ルーブリックが悪い」のか「エンジンが悪い」のか切り分けられない

4. **3年目到達レベルの検証手段**
   100問を解いた人が本当に3年目相当になるかは、実際に3年目のエンジニアに解かせて正答率を見るしかない。**78・79（テストコード読解）と 90・91（型エラー読解）を先に作り、現役3年目5人に解かせる**のが最も安いバリデーションになる

5. **診断テストによる開始位置のスキップ**
   3年目が第1章（7問）から始めるのは離脱要因。「最初に数問解いて開始ステージを決める」導線が必要か

6. **入門帯（DOM 操作）の扱い**
   v3 でも DOM 操作系を全て除外している。React を別カリキュラムとするなら素の DOM は不要という判断も成立するが、確定が必要

7. **公開前の著作権照合工程**
   100問を作り切った後、既存教材のサンプルコードとの偶然一致を機械的に照合するか。（`ズレ` 型主体になったことでリスクは下がったが、`fizzBuzz` など定番題材のみ注意）
