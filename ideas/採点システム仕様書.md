## 0. 設計方針

- **正確性を第一、保守性を第二とする**
- 採点基準（キーワード・模範回答・ルーブリック）はすべて DB で管理し、コードを変えずに問題ごとの基準を調整できるようにする
- **誤って「正解」と判定するほうが悪い。** 曖昧なケースは AI に委ねる
- 採点経路は少ないほどよい。分岐が増えるほど「なぜこの点数になったか」の説明が難しくなる

---

## 1. スコア構成（100点満点）

```
合計 100点
 ├─ 層1 正規表現:  20点（キーワード部分点）
 └─ 層2 AI採点:    80点（概念・説明の正確さ）
```

2つの層は**独立して採点し、合算する。**
層1が 0点でも層2が満点になることはあるし、逆もある。

層1は毎回必ず実行する。層2も毎回必ず実行する（v1 にあった「条件次第で AI を呼ばない」高速パスは廃止した）。

---

## 2. 層1: 正規表現（20点）

### 概要

各問題に**可変個のキーワードスロット**を持たせる。スロット数は問題ごとに自由に設定でき、1スロットあたりの点数は `20 / スロット数` で自動計算する。

ユーザー回答に該当するキーワードが含まれていれば、そのスロットの点数を加算する（部分点）。全スロットヒットで 20点。

### DB 設計（問題ごとに設定）

```ts
// 3スロットの例（1スロット = 20/3 ≈ 6.7点）
keywords: [
  { match: ["初期化", "initialize", "0にセット", "ゼロ代入"] },
  { match: ["ループ", "繰り返し", "for文", "while"] },
  { match: ["戻り値", "return", "返す"] },
]
```

各スロットは複数の表記ゆれをまとめて持てる。1つでも含まれていれば加点。

### スコアリングロジック

```ts
function scoreByKeywords(answer: string, keywords: KeywordSlot[]): number {
  const pointPerSlot = 20 / keywords.length
  return keywords.reduce((total, slot) => {
    const hit = slot.match.some(kw => answer.includes(kw))
    return total + (hit ? pointPerSlot : 0)
  }, 0)
  // 返り値: 0〜20
}
```

### この層を残す理由

AI 採点だけでも成立するが、層1には AI に代替できない性質がある。

- **コスト ¥0・レイテンシ 0** — API 呼び出しを伴わない
- **完全に決定的** — 同じ回答なら必ず同じ点数。AI のブレの影響を受けない下限点になる
- **障害時の保険** — OpenAI が落ちても部分点だけは返せる（将来のフォールバック実装の土台）

## 3. 層2: AI採点（80点）

### 概要

正規表現では測れない「説明の概念的な正しさ・深さ」を GPT-4o mini が 80点満点で評価する。

**全ての回答がこの層を通る。** 事前フィルタや高速パスは設けない。

### 呼び出し設定

| 項目 | 値 | 理由 |
|---|---|---|
| モデル | `gpt-4o-mini` | 採点タスクに対して十分な精度とコスト |
| `temperature` | **`0`** | 採点者にランダム性は不要。同じ回答は同じ点数であるべき |
| `response_format` | `{ type: "json_object" }` | 出力形式を固定しパースを安定させる |

**`temperature` の明示は必須。** 未指定だとデフォルト 1.0 になり、同一回答でも実行のたびに点数が揺れる。

### プロンプト設計

- システムプロンプトに「問題のコード・設問・模範回答・採点ルーブリック」を固定して差し込む
- ユーザーメッセージにはユーザー回答だけを渡す
- ルーブリックは問題ごとに DB（`problems.ai_rubric`）から差し込む

### 出力スキーマ

```ts
type AiScoringResult = {
  score: number      // 0 / 20 / 40 / 60 / 80 の5段階のみ
  feedback: string   // 日本語フィードバック（ポジティブ表現のみ）
}
```

**スコアを5段階に限定する理由:** 中間値（例: 53点）はモデルの気分に左右されやすく一貫性がない。離散値にすることで採点のブレを抑える。

**`feedback` は必ず取得し、`user_attempts.ai_feedback` に保存する。** リザルト画面に表示する本文になる。スコアだけ取ってフィードバックを捨てないこと。

### NGワード制約

システムプロンプトに、以下を使わない旨を明示する（仕様書 §9.5 の UX 要件）。

> 「弱点」「間違い」「初心者」「勉強」「失敗」「正しい読み方」

Ferret のトーン設計上、フィードバックは常に「次にどう読むか」を示す前向きな文面に統一する。

## 4. 合算と最終スコア

```ts
async function scoreAnswer(answer: string, question: Question) {
  // 層1: 正規表現（常に実行・API不要）
  const keywordScore = scoreByKeywords(answer, question.keywords)

  // 層2: AI採点（常に実行）
  const { score: deepScore, feedback } = await scoreByAI(answer, question)

  return {
    total: keywordScore + deepScore,   // 0〜100
    keyword_score: keywordScore,
    deep_score: deepScore,
    ai_feedback: feedback,
    scoring_method: "ai",
  }
}
```

### クリア判定

`total_score >= 65` でクリア。一度クリアしたら再挑戦で低いスコアを出してもクリア状態は維持される（`db仕様.md` 参照）。

## 5. コスト試算

### 前提

- GPT-4o mini: 入力 $0.15 / 1M tokens、出力 $0.60 / 1M tokens
- 1回の採点あたり 入力 約800 tokens（システムプロンプト + 回答）、出力 約150 tokens
- 為替 ¥150/$

**1回あたり 約 $0.0002 ≒ ¥0.03〜0.04**

### プラン別

| 想定利用 | 月間採点回数 | AI原価/月 |
|---|---|---|
| Pro 平均ユーザー | 60回 | 約 ¥2 |
| Pro 上限 | 200回 | 約 ¥7 |
| Pro Plus 上限 | 500回 | 約 ¥17 |

全問 AI を通しても、Pro ¥1,480 に対する AI 原価は上限ケースでも **0.5%未満**。

### プロンプトキャッシュについて

v1 では Anthropic のプロンプトキャッシュ前提でコスト削減を見込んでいたが、OpenAI のプロンプトキャッシュは**自動適用かつ 1024 tokens 以上のプロンプトが対象**。現状のシステムプロンプト（約600 tokens）では発動しない見込み。

上記試算はキャッシュ無しの数字なので、**効かなくても問題ない水準**である。コード側で特別な対応は不要。

## 6. エラー処理

| 事象 | 挙動 |
|---|---|
| `OPENAI_API_KEY` 未設定 | 明示的に例外。採点は実行しない |
| OpenAI API 障害・タイムアウト | エラーを返し、**ユーザーの入力は保持する**（再入力させない） |
| 採点結果の DB 保存失敗 | **スコアを返さず 500 を返す**（成功に見せかけない） |

保存失敗を握りつぶすと「採点は成功したのに履歴が残らない」という、症状と原因が離れた不具合になる。必ずエラーを検査すること。

## 7. 廃止した設計と、その理由

### 廃止: Embedding 層（v1 §3）

v1 では、ユーザー回答と模範回答の Embedding コサイン類似度を計算し、閾値で 80/60/20/0点を確定、中間帯（0.63〜0.74）のみ AI に回す設計だった。**v2 でこれを全面廃止した。**

#### 理由1: 最も危険な誤答を、最も自信を持って通してしまう

Embedding が測るのは「話題の近さ」であって「正しさ」ではない。

```
模範回答: 「配列から偶数だけを取り出している」
誤答　　: 「配列から奇数だけを取り出している」
```

差は1単語であり、類似度は 0.9 を超える。v1 の閾値では `>= 0.85` で **80点確定・AI 検証なし**となる。否定・対義語・オフバイワンといった誤りに対して構造的に無力であり、しかもそれが高速パスの最も自信のある帯域で起きる。

§0 の「誤って『正解』と判定するほうが悪い」という方針と正面から衝突する。

#### 理由2: 節約額が小さすぎる

Embedding 層の存在意義は AI 呼び出しの削減だが、§5 のとおり全問 AI でも Pro 上限で月¥7 程度。削減効果は粗利率にして 0.5ポイント未満であり、理由1のリスクに見合わない。

#### 理由3: 閾値のチューニングが構造的に詰んでいる

v1 は「実データ 50〜100件で閾値を見直す」としていたが、正しく採点できなければリリースできず、リリースしなければ実データが集まらない。加えて適切な閾値は問題ごとに異なる（模範回答の長短で類似度分布が変わる）ため、問題数だけ手調整が発生し、スケールしない。

#### 廃止に伴い不要になったもの

- 模範回答の Embedding 事前計算スクリプト
- 「模範回答を編集したら再計算が必要」という運用上の地雷（忘れるとエラーなく静かに誤採点する）
- `problems.model_answer_embedding` カラムの保守
- pgvector 拡張への依存

### 将来の再利用先（採点ではなく分析へ）

Embedding が本来得意なのは**分類・検索**であって採点ではない。将来、ユーザー回答をベクトル化してクラスタリングすれば「この問題は回答者の3割が『奇数』と誤解している」といった**つまずき傾向の分析**ができる。コンテンツ改善に直結する価値があるため、pgvector と `model_answer_embedding` カラムは削除せず保留する。

## 8. 未解決論点

- **AI採点の精度検証が未実施。** 実際の回答 20〜30件を人手で採点し、GPT-4o mini の点数と突き合わせて乖離を測る作業が必要
- **`ai_rubric` の書き方が未定。** 問題ごとに自由記述だが、粒度の指針がないと問題間で採点の厳しさがブレる。数問作った段階でテンプレート化する
- **択一・キーワード記述（タイプA・B）の採点設計は将来追加時に別途定義する**
- **レート制限超過時の挙動。** 「採点をスキップし層1のみで判定」とする場合、`scoring_method` に `keyword_only` を記録する想定（未実装）
