## 1. この作業で一番効いた考え方

### 1-1. 穴は「書き忘れ」より「使い忘れ」から出る

今回いちばん危なかったのは、**ライブラリが渡してくれている引数を受け取っていなかった**ことだった。

```ts
// 直す前
setAll(cookiesToSet) { ... }

// 直した後
setAll(cookiesToSet, headers) { ...; /* headers を反映する */ }
```

第2引数には「このレスポンスをキャッシュに保存させるな」という指示が入っている。
受け取らなくても**型エラーも警告も出ないし、動作も一見正常**。
それでいて、落とすと通信経路上のキャッシュにログイン用の合鍵ごと保存され、
**次に同じURLを開いた別人にそれが渡る。**

気づけたのは、ライブラリの型定義ファイルのコメントを読んだから。

> **教訓:** コールバックの引数は全部使う。使わないなら「なぜ使わないか」をコメントに書く。
> 認証・暗号・決済まわりのライブラリは、`.d.ts` のコメントまで読む。
> そこには「これをしないと壊れる」が書いてあることがある。

### 1-2. 画面で出し分けているものは、ガードではない

ステージ選択画面の 🔒 は、**ブラウザの中の飾り**でしかなかった。
アドレスバーに `/problems/42` と打てば、未開放の問題が普通に開いて採点まで通った。

> **教訓:** 「出す / 出さない」を画面で判断しているものは、必ずサーバー側でも同じ判断をする。
> ボタンを消す・リンクを張らない・`disabled` にする、はどれもガードではない。

### 1-3. 同じ判定を2箇所に書くと、そこが将来の穴になる

上を直すとき、画面用とAPI用で解放判定を別々に書くこともできた。書かなかった。
片方だけ仕様変更したときに、**気づかないままAPI側だけ緩くなる**からだ。
`lib/progress/unlock.ts` に1本化して、画面もAPIも同じ関数を呼ぶ。

> **教訓:** アクセス制御の判定式は、アプリ内に1つだけ置く。
> 「表示のための判定」と「入場のための判定」を別々に書かない。

### 1-4. 状態を壊さないAPIでも、お金は減る

採点APIは、叩かれてもデータは壊れない。他人の情報も漏れない。
それでも**1回叩かれるごとに OpenAI に実費が出る。**
連打されれば請求書が膨らみ、API の利用枠を使い切られれば**全ユーザーの採点が止まる。**

セキュリティを「情報を守ること」だと思っていると、この経路は見えない。

> **教訓:** 外部の有料APIを呼ぶエンドポイントは、それ自体が攻撃対象。
> 「何を盗まれるか」だけでなく「何を消費させられるか」で見る。
> AI を使うサービスでは、こちらのほうが現実的な被害になりやすい。

### 1-5. 設定ファイルが実態とズレていると、それは時限爆弾になる

`supabase/config.toml` は、ツールが最初に生成した**開発用のひな形のまま**だった。
そこには「メール確認は不要」と書いてあり、一方で本番は「必須」で動いていた。

つまり、いつか設定を同期しようとしてコマンドを1回叩くだけで、**本番のメール確認が消える。**
しかも消えたことに気づく仕組みがない。

> **教訓:** 「まだ使っていない設定ファイル」は、たいてい嘘をついている。
> 初めて使う前に、必ず実態と突き合わせる。
> ズレていた項目は、直したうえで**なぜその値なのかをコメントに残す。**

### 1-6. 守りのコードは「壊れたときどっちに転ぶか」で書く

DBの問い合わせが失敗したとき、回数制限のチェックはどう振る舞うべきか。

- 「数えられなかったから通す」→ DBが不調な間、上限が消える（**危ないほうに転ぶ**）
- 「数えられなかったから止める」→ 一時的に採点できない（**安全なほうに転ぶ**）

後者にした。同じ理由で、解放判定は「履歴が読めなかったら、より多くロックする」方向に倒してある。

> **教訓:** 守りの処理を書いたら「この処理自体が失敗したらどうなるか」を必ず考える。
> 失敗したときに守りが消えるなら、それは守りではない。

### 1-7. すでに守れているものにも、もう1枚重ねる意味がある

別サイトからの勝手な送信（CSRF）は、Cookie の `SameSite=Lax` という設定で既に防がれていた。
それでも送信元チェックを足した。

理由は、**1枚目が「他人の設定」に依存しているから。** Cookie の属性はライブラリ側の既定値で、
バージョンが上がれば変わりうる。1枚目が消えたことに気づく仕組みはない。

> **教訓:** 「もう守られているから不要」と判断する前に、
> **その守りは誰が決めているか / 消えたら気づけるか**を確認する。
> 自分の手が届かない場所にある守りは、1枚では数えない。

### 1-8. 「一般に良いとされること」と「この状況で効くこと」は違う

パスワードの最低文字数を上げるのと、流出済みパスワードを拒否するのを、最初は同列に並べてしまった。
調べ直すと、総当たりは既存の試行回数制限で成立せず、**文字数はほとんど効かない**と分かった。
実際に来るのは他所で漏れた組み合わせの使い回しで、そちらは文字数では止まらない。

> **教訓:** 対策を並べる前に「その攻撃は、いまの構成で本当に成立するか」を数字で確かめる。
> 効かない対策を並べると、効く対策が埋もれる。

### 1-9. 自分のサーバーを通らない経路は、コードでは守れない

新規登録は「ブラウザ → Supabase」で直接やり取りしていて、Ferret のサーバーを経由しない。
だからパスワード強度のチェックは、**アプリ側にどう書いても差し込めない。**

> **教訓:** 機能ごとに「データがどこを通るか」を一度紙に書く。
> 自分のサーバーを通らない経路があれば、そこは設定でしか守れない。
> 「コードで直せない項目リスト」を別に持つ。

## 2. 新しく機能を作るときのチェック

### 画面を1つ足したら

- [ ] ログインが要るなら `proxy.ts` の `matcher` に追加したか
- [ ] URL のパラメータを `Number()` する前に、整数か確かめているか
- [ ] 見せてよいカラムだけを `select` で明示しているか（`select("*")` にしない）
- [ ] 「この人が見てよいページか」をサーバー側で判定しているか

### API を1つ足したら（POST 系）

- [ ] 送信元チェック（`isCrossSiteRequest`）を先頭に置いたか
- [ ] Content-Type を確かめているか（`hasJsonContentType`）
- [ ] 本文のサイズ上限を決めたか
- [ ] ログイン確認を、DBを触る前にやっているか
- [ ] 外部の有料APIを呼ぶなら、回数の上限を付けたか
- [ ] エラー時に、内部の事情（DBのエラー文など）を画面に返していないか

### 外部サービスを繋いだら

- [ ] 相手からの通信に**署名検証**があるか（Webhook は特に。これが無いと誰でも偽の通知を送れる）
- [ ] 秘密鍵は `NEXT_PUBLIC_` を付けずに宣言したか
- [ ] ビルド後、その鍵がブラウザに配られる側に入っていないか実際に検索したか

### ユーザーが書いた文字を画面に出すなら

- [ ] React にそのまま渡しているか（`dangerouslySetInnerHTML` を使っていないか）
- [ ] URL のパラメータの中身を、そのまま文章として表示していないか
      （表示するなら、**決められた合言葉と照合した結果**を出す）

## 3. 確かめ方（コマンド）

### DBの防御が効いているか

ブラウザに配られる公開鍵で、実際に攻撃してみるのが一番早い。

```bash
U=$(grep '^NEXT_PUBLIC_SUPABASE_URL=' .env.local | cut -d= -f2-)
A=$(grep '^NEXT_PUBLIC_SUPABASE_ANON_KEY=' .env.local | cut -d= -f2-)

# 読めてはいけないものが読めないか（[] が返れば正常）
curl -s "$U/rest/v1/problems?select=model_answer" -H "apikey: $A" -H "Authorization: Bearer $A"

# 書けてはいけないものが書けないか（42501 で拒否されれば正常）
curl -s "$U/rest/v1/user_attempts" -X POST -H "apikey: $A" -H "Authorization: Bearer $A" \
  -H "Content-Type: application/json" -H "Prefer: return=representation" \
  -d '{"user_id":"00000000-0000-0000-0000-000000000000","problem_id":1,"total_score":100}'
```

**注意: ステータスコードだけ見ない。** PostgREST は、権限で全部弾かれても `200` と `[]` を返す。
更新が0行でも `204` を返す。**中身を見ないと成功と区別がつかない。**

### 公開されているDBの入口を数える

テーブル以外にビューや関数が生えていると、そこから RLS を迂回できることがある。

```bash
S=$(grep '^SUPABASE_SERVICE_ROLE_KEY=' .env.local | cut -d= -f2-)
curl -s "$U/rest/v1/" -H "apikey: $S" -H "Authorization: Bearer $S" \
  | python3 -c "import json,sys; [print(p) for p in sorted(json.load(sys.stdin)['paths']) if p!='/']"
```

意図した4テーブル以外が出てきたら、それが何かを確認する。

### 秘密鍵がブラウザ側に漏れていないか

```bash
npm run build
S=$(grep '^SUPABASE_SERVICE_ROLE_KEY=' .env.local | cut -d= -f2-)
grep -rl -- "${S: -40}" .next/static && echo "漏洩" || echo "OK"
```

**必ず末尾（署名部分）で照合する。** anon キーと service_role キーは
先頭数十文字が同じ（同じ形式のトークンなので前半が共通）。
先頭で検索すると「漏れている」と誤判定する。実際に一度ひっかかった。

### 送信元チェックが効いているか

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:3001/api/score \
  -H 'Content-Type: application/json' -H 'Origin: https://evil.example' -d '{}'
# 403 なら正常
```

### セキュリティヘッダが出ているか

```bash
npm run build && npx next start -p 3123 &
curl -s -D - -o /dev/null http://127.0.0.1:3123/login | grep -i 'content-security\|x-frame\|strict-transport'
```

### 部品の脆弱性

```bash
npm audit
```

## 4. ハマった罠（次も同じところで転ぶので書き残す）

### 部品を入れ替えたら、開発サーバーを再起動する

`npm install` でライブラリを更新した後、動いたままの開発サーバーが**全ページ 500 エラー**になった。
エラーの内容はフレームワーク内部のもので、自分のコードは一切出てこない。
これを「自分の変更が壊した」と思い込むと、無関係な場所を延々と疑うことになる。

> 症状: 直前まで動いていたのに、突然すべてのページが 500。自分のコードがスタックに出ない。
> 対処: サーバーを止めて `.next/dev` を消してから再起動。

### 検証用のデータは、必ずIDを控えてから作る

動作確認のために問題を2件追加したら、削除しても**IDの採番は戻らない**。
`problems.id` は「変えない永続的な識別子」として設計してあるので、
本番のデータに検証用の欠番が混ざる。少量なら実害はないが、意識しておく。

### ソースコードに目に見えない文字を置かない

入力を掃除する処理に、幅ゼロ文字（画面に何も表示されない文字）が**そのまま書かれていた**。
動作は正しいが、コードを読んでも何を消しているのか分からないし、
そこに別の文字を紛れ込ませられても気づけない。`\u200B` のようなコード表記に置き換えた。

> 一般に、ソースコードに不可視文字を置くのは、レビューをすり抜けさせる手口としても知られている。
> 見えない文字はコード表記で書く。

### ブラウザの自動操作ツールは、手元のブラウザと取り合いになる

検証にブラウザ自動操作を使おうとしたら、既に起動しているブラウザと衝突して使えなかった。
`curl` で同じことを確かめられる場合が多いので、無理に使わない。
ログイン後の画面を確かめたいときは、ライブラリを直接呼んでセッションを作ればよい。

## 5. まだ身につけていない観点（今後の宿題）

- **攻撃に気づく仕組み。** いま誰かに攻撃されても、気づく手段がない。
  最低限、採点APIが 429 / 403 を返した回数を見られるようにしたい
- **決済の検証。** Stripe を繋ぐときが、次の山場になる
- **依存の更新を続ける仕組み。** `npm audit` が今 0 件でも、来月には増える
- **バックアップからの復旧手順。** 壊された・消されたときに戻せるか
