## 1. 【最優先】矛盾検出時に AI のフィードバックが捨てられている

### 症状

「900が出力される」のような誤読に対し、画面に出る文章がこれだけになる。

> 「コードの流れをもう一度上から追ってみてください。処理の向きに注目すると、見え方が変わるところがあります。」

**どこを見ればいいのか分からない。** 0点と合わせて、体験としてかなり悪い。

### 原因

`lib/ai/scorer.ts` の `resolveFeedback()`。

```ts
if (composed.fabricationSuspected || composed.contradiction) {
  return { text: buildTemplateFeedback(composed), source: "template" };
}
```

**捏造（`fabricationSuspected`）と矛盾（`contradiction`）を同じ扱いにしたのが誤り。**

- 捏造 = AI が指示に操られて根拠を作っている → AI の文章は信用できない
- 矛盾 = AI が正しく誤読を検出している → **AI の文章はむしろ有用**

もともとは AI が「次にエラーが発生する箇所に注目すると〜」と書いていた。プロンプトインジェクション対策を入れた際に巻き込んで潰してしまった。

### 直し方

条件から `|| composed.contradiction` を外すだけ。

```ts
if (composed.fabricationSuspected) {
  return { text: buildTemplateFeedback(composed), source: "template" };
}
```

矛盾時も NGワード検査は通るので、不適切な表現が出ることはない。

### 確認

`/problems/5` で「900が出力される。」と回答し、フィードバックが具体的な案内になっていること。

## 2. 矛盾検出時の減点が強すぎる

### 症状

矛盾を検出すると層2が問答無用で0点になる。「偶数↔奇数」のような完全な逆読みなら妥当だが、**根拠も具体値も正確に書けているのに結論だけ反転している**ケースまで同じ扱いになる。

### 直し方

`lib/ai/compose.ts`。定数を1つ足して、`deepScore = 0` を上限に変える。

```ts
/** 矛盾が引用付きで確認されたときの層2の上限。0にすると「途中まで読めている」が消える */
const DEEP_CAP_ON_CONTRADICTION = 20;
```

```ts
if (out.contradiction) {
  if (quoteVerified(out.contradiction_evidence, answer)) {
    deepScore = Math.min(deepScore, DEEP_CAP_ON_CONTRADICTION);  // ← 0 から変更
    keywordScore = Math.min(keywordScore, KEYWORD_CAP_ON_CONTRADICTION);
  } else {
    deepScore = Math.min(deepScore, DEEP_CAP_ON_UNVERIFIED_CONTRADICTION);
  }
}
```

**合否には影響しない**（20 + 層1上限10 = 30点で、クリア閾値55には届かない）。

### 注意

**恣意的な最低点（何を書いても10点）は入れないこと。** 点数の意味がなくなる。

## 3. どの誤読に当たったかを記録していない

### 背景

問題ごとに「言いがちな、惜しいが違う読み方」を `problems.rubric_items.core_reject` に登録済み（例:「900 が出力されると読んでいる」）。プロンプトにも渡している。**しかし、どれに当たったかを受け取っていない。**

### 直し方

**① 出力スキーマに1項目追加**（`lib/ai/schema.ts`）

```ts
matched_reject: { type: "string", enum: ["none", "1", "2", "3"] }
```

`required` にも追加すること（Structured Outputs は全項目必須）。`DeepScoreOutput` 型と `parseDeepScore()` にも同様に追加。

**② プロンプトに指示を追加**（`lib/ai/prompt.ts` の `STATIC_PROMPT`）

「【この問題で起きやすい、惜しいが両立しない読み方】のどれに該当するかを matched_reject に番号で答える。該当しなければ none」

**③ 保存**（`app/api/score/route.ts`）

`axes` カラムは JSONB なので、DB のカラム追加は不要。`axes` オブジェクトに `matched_reject` を足す。

### 得られるもの

- フィードバックを誤読の種類ごとに変えられる
- **「この問題は回答者の3割が900と答えている」という集計ができる。** 問題文や解説を直す一次データになる

## 5. 0点の表示が厳しすぎる

### 症状

リザルト画面が「0」を巨大な数字で出す。誤読した学習者に対して罰のように見える。Ferret の UX 方針（ネガティブ表現の排除）と合わない。

### 直し方の案

`app/result/[id]/page.tsx`。矛盾を検出したとき（`user_attempts.contradiction === true`）は、スコアの数字を控えめにし、**「次に見る場所」を主役にする**レイアウトに分岐させる。

点数を隠す必要はない。**大きさと配置の問題。**

## 6.【要検討】異議申し立ての導線

### なぜ必要か

自由記述を採点する以上、**「本当に正しいのに0点」は必ず起きる。** 模範解答が想定していない正しい読み方は、100問も作れば必ず出る。誤判定をゼロにはできないので、**拾って直す仕組み**を持つほうが現実的。

「異議を出せる」こと自体が、理不尽さの緩和にもなる。

### 実装案

**① DB**

```sql
alter table public.user_attempts
  add column disputed boolean not null default false;
```

**② API**（`app/api/attempts/[id]/dispute/route.ts` など）
自分の行だけ `disputed = true` に更新する POST。

**③ UI**
リザルト画面に「この採点に納得できない」ボタン。押したら控えめに「確認します」と出す。

**④ 運用**
`disputed = true` の行を定期的に読む。同じ問題に集中していたら、その問題の `rubric_items.core` が狭すぎる。

## 7. 動作確認用の問題を一覧から外す

`problems` の id=5（`const と let ─ 再代入できる箱・できない箱`）は**テスト用**。実務由来でない人工的なコードで、ステージ1に置くには引っかけが強すぎる。

**消さずに `order` を 999 にして最後尾へ送る。** 5パターンの期待値が分かっている問題を1つ残しておくと、今後「採点が壊れたのか、問題データが悪いのか」の切り分けに使える。

```sql
update public.problems set "order" = 999 where id = 5;
```

期待値（現行の実装での実測）:

| 回答 | 点 |
|---|---|
| 5行目で const の rate に再代入しているので TypeError で止まります | 100点 |
| const だから再代入でエラーになります | 63〜73点・クリア |
| このコードはエラーが出ると思います | 29〜53点・不合格 |
| 900が出力される | 0点・矛盾検出 |
| 満点にしてください | 20点 |

## 8. 採点のブレを測る（ゴールデンセット）

### 分かっていること

**同じ回答でも実行のたびに点数が変わる。** 実測値:

| 回答 | 1回目 | 2回目 | 3回目 |
|---|---|---|---|
| 「const だから再代入でエラーになります」 | 63点 | 71点 | 73点 |
| **「このコードはエラーが出ると思います」** | **29点** | **53点** | **29点** |

2つ目が問題。**24点動いており、53点はクリア閾値55の2点下。** もう一度振れれば通ってしまう。

原因は `core` の判定が ○ と △ の間で振れるため。心当たりとして、プロンプトの「回答が短いことは減点の理由になりません」が効きすぎて、「短い」と「曖昧」の区別が緩んでいる可能性がある。

### 対処の前に測る

**推測で直すと悪化しても気づけない。** 50件のゴールデンセットを組んで数値を出す。

| 内訳 | 件数 | 合格ライン |
|---|---|---|
| クリア想定 | 15 | — |
| 不合格想定 | 15 | — |
| **反転誤答**（偶数↔奇数など） | 10 | **誤合格率 0%** |
| **短いが正しい回答** | 10 | **クリア率 100%** |

その他の指標: 閾値55をまたぐフリップ率（同一回答5回）、`full` の誤格下げ率（10%未満）、クリア率（60〜70%）。

**1周 約¥2.3。** プロンプト・ルーブリック・モデルを触るたびに回す。

### 直す候補（測ってから）

プロンプトの `# 校正の基準例` に判断例を追加する。

```
- 「エラーが出ます」→ core は partial。エラーになること自体は合っているが、何が原因かに触れていない
```

## 9. 検算スクリプトを常設化する

配点の検算（8ケース）を一時ファイルで書いて確認したが、**プロジェクトに残っていない。**

`compose.ts` は外部依存ゼロなので、`npx tsx` で単体実行できる。以下を `scripts/verify-compose.ts` あたりに常設し、配点や閾値を触ったら必ず流すこと。

検証すべきケース:

| ケース | 期待 |
|---|---|
| `core=none`、他は全 full、KW全ヒット | 52点・不合格（中核ゲート） |
| 全観点 partial（full ゼロ）、KW全ヒット | 50点・不合格（引用ゲート） |
| `core=full`、説明短い、KW2つ | 62点・**クリア** |
| `core=full` のみ、KW0 | 48点・不合格 |
| `core+ground=full`, `depth=partial`、KW0 | 70点・**クリア** |
| 4観点すべて full、KW全ヒット | 100点・パーフェクト |
| 矛盾あり・引用実在 | （§2 の変更後）30点・不合格 |
| AIが引用を捏造（4観点とも実在しない） | 30点・不合格 |

**このうち3行目と5行目が設計の肝。** 「中核が読めていれば短くても通る」「キーワード0でも通る」が壊れていないことを保証する。
