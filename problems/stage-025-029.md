## 各問の設計

### 25 ─ プロパティアクセスと存在チェック(in)

**読ませどころ:** `in` は名前があるかどうかだけを見る。**値が `undefined` でも true。**
`settings[key]` の真偽で分岐する1つ目と対比させるため、
`false`（notify）・`undefined`（label）・存在しない（locale）の3種類を並べてある。

**`core` を label に置いた。** notify（`false`）は「falsy だから2つ目に落ちる」で説明でき、
`in` の性質まで理解していなくても当てられる。**`in` を分かっていないと当たらないのは label だけ。**

### 26 ─ オプショナルチェーン

**読ませどころ:** `?.` が守るのは**書いた位置の1回だけ。** 左側の取り出しには効かない。
city の行（`customer?.address?.city`）と zip の行（`customer.address?.zip`）を並べて、
**同じオブジェクトを掘るのに片方だけ落ちる**形にしてある。

**`core_reject` の3つ目に誤解そのもの**（`?.` を書けば左側も守られる）を入れた。
これが最も多いはずの読み違いで、`matched_reject` の集計に乗る。

**郵便番号を `"6008216"` にしてある。** ハイフン入り（`600-8216`）だと
採点APIの個人情報検査（電話番号のパターン）に当たる可能性があり、
**コードを引用した回答が 400 で弾かれる**（`tasked/A1` の決定②と同じ事故）。

### 27 ─ 分割代入と省略記法

**読ませどころ:** `...rest` には**手前で名指しした名前が残らない。**
あわせて `author: writer = "匿名"` のリネーム + 既定値で、`null` には既定値が効かないことも見せる。

**`core` を rest 側に置き、既定値の話は `depth` に回した。** 既定値は 18 で `core` に置いており、
ここでも `core` にすると同じことを2回測ることになる。

### 28 ─ 浅いコピー（ズレ・回収）

**読ませどころ:** `{ ...preset }` は一番外側だけ。`notify` は同じものを指したまま。
コメントが「壊さないよう複製してから」と書いているのに、**`notify` は壊れている。**

**9・17 と同じ「片方だけがズレている」構造。** `name` は意図どおり動くので、
`depth` は**どちらの行がズレているかの切り分け**に置いた。ズレ型3問で形をそろえている。

### 29 ─ Object.keys / values / entries

**読ませどころ:** プロパティの並び順。**数字として解釈できる名前が先に、小さい順。**
`{ "2026": 4, error: 12, "10": 1, warn: 3 }` と書いても `10` が最初に来る。

**`reduce` を使わなかった。** `reduce` はステージ35（第5章）なので、
ここで使うとカリキュラムの順序を追い越す。`Object.keys(...).length` に置き換えてある。
