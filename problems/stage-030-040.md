## 各問の設計

### 30 ─ 破壊する / しないメソッド（ズレ）

**読ませどころ:** `splice` は取り出すと同時にもとの配列から抜く。
**返り値だけ見ていると気づけない**形にしてある（`batch` は期待どおり）。

**`slice` をキーワードから外した。** 対比として前提知識で `slice` と `splice` を並べたかったが、
`slice` はコードに現れないので、キーワードに入れると I-817（前提知識にコード外のキーワード）に当たる。
**説明に必要な語と、採点に使う語を分ける**判断。

### 31 ─ forEach（意図）

**読ませどころ:** なぜ変換系のメソッドではなく `forEach` なのか。
送ること自体が目的で、集めたいのは失敗分だけ。`try` を各件の中に置いてあるのも同じ理由。

**設問で手段の名前を出していない。** 「map ではなく」と書くと答えを渡すことになる
（第2バッチの申し送り6）。「何のために回しているのか」だけを訊いている。

### 32 ─ map

**読ませどころ:** `map` は**その時点の値**で作り終える。あとから元を書き換えても反映されない。
28（浅いコピー）と逆向きの確認になっている ── **あちらは共有される、こちらは共有されない。**
`lines` に入るのが文字列（プリミティブ）だからで、4・5 の理解が効く。

### 33 ─ map の return 忘れ（ズレ・17の回収）

**読ませどころ:** 分岐の片方だけ `return` があり、もう片方は式を置いただけ。
`labels` に `undefined` が混ざる。**17 とまったく同じ形**をコールバックの中に置いてある。

**17 と同じ「片方だけがズレる」構造。** `depth` は品切れ側が動くことの切り分け。

### 34 ─ filter / find / some / every

**読ませどころ:** **空の配列に対する `every` は `true`。** 反例が存在しないため。
`some` は `false` になるので、同じ空配列で2つの答えが分かれる。

**`core` を「空で `true` になる」に置いた。** 4つのメソッドの説明を並べるだけの問題にすると
機能紹介型になり、識別力が出ない。

### 35 ─ reduce（第2引数を省いた場合）

**読ませどころ:** 第2引数を省くと**配列の先頭要素そのもの**が出発点になる。
ここではオブジェクトなので、`+` が文字列連結に落ちて `[object Object]800500` が出る。
**ステージ6（`+` の二つの顔）が効いてくる。**

**正しい書き方と省いた書き方を並べてある。** 省いたほうだけ見せると
「reduce は難しい」で終わるが、並べると**差が第2引数1つだけ**だと分かる。

### 36 ─ reduce 応用（ズレ・4の回収）

**読ませどころ:** 第2引数に渡したオブジェクトは複製されない。`push` がそれを直接書き換える。
コメントは「雛形として残す」と言っているのに、雛形が壊れる。

**28 と同じことを別の入口から踏ませている**（28 はスプレッド、36 は reduce の第2引数）。
`depth` は「集計そのものは正しい」という切り分け。

### 37 ─ sort

**落とし穴が2つある。** 比較関数を省くと文字として比べる（`100` が `25` より前）ことと、
`sort` がもとの配列を並べ替えて**同じ配列を返す**こと。
`sorted.push(1)` が `scores` にも現れ、`scores === sorted` が `true` になる。

**`core` は文字比較のほう、`depth` は同一性のほう**に分けた。

### 38 ─ 複数キーの並べ替え

**読ませどころ:** `a - b || c - d` は、第1キーが同点（0）のときだけ第2キーを見る。
`||` が「なし」とみなす値に **0 が含まれる**ことが効いている（ステージ9・10 の理解）。

**同点かつ同日の2件を入れてある。** そこが**もとの並び順のまま残る**ことまで読めるかを `depth` に置いた。

### 39 ─ メソッドチェーン

**読ませどころ:** 段ごとに件数と形が変わる。`filter` で2件になり、`map` で数になり、`reduce` で1つに。
クーポンが金額を超えた行が**負の数**になり、合計を押し下げる。

**`core` を「負の数になる」に置いた。** 合計値を `core` にすると計算間違いと読み違いが混ざる。

### 40 ─ flat / flatMap（意図）

**読ませどころ:** 注文ごとに配列が返るので、そのまま集めると配列の配列になる。
`flatMap` が1段だけ開く。`orderId` を足しているのは平らにしたあとの手がかりを残すため。

**`core_reject` の3つ目に「すべての深さまで開く」を入れた。** `flat()` は既定で1段だけなので、
ここは誤解が起きやすい。
