## ステージ 1 ─ const と let ─ 再代入できる箱・できない箱

| 項目 | 値 |
|---|---|
| order | 1 |
| title | const と let ─ 再代入できる箱・できない箱 |
| language | js |
| difficulty | 1 |
| reading_type | トレース |
| 収束性 | 一意 |

> `ideas/問題作成ガイド.md` の記入例をそのまま正とする。ガイドがこれをトレース型の基準として参照しているため、別案を立てると基準が二重になる。
>
> **改訂で `depth` を変更した（ガイド側も同時に修正済み）。** 理由は下記「`depth` を変更した理由」。

### code

```js
function applyCoupon(price) {
  const rate = 0.9;
  let total = price;
  total = total * rate;
  rate = 0.8;
  return total;
}

console.log(applyCoupon(1000));
```

### question

このコードを実行すると何が起きますか。

### model_answer

5行目で const で宣言された rate に再代入しているため、TypeError が発生して実行が止まります。console.log は実行されません。

### keywords

```json
[
  { "match": ["rate", "const", "定数"] },
  { "match": ["エラー", "TypeError", "止ま", "落ち", "例外"] },
  { "match": ["再代入", "代入", "0.8"] },
  { "match": ["console.log", "出力されない", "表示されない"] }
]
```

### rubric_items

```json
{
  "core": "const の rate への再代入でエラーになるという結論を指していれば満たす",
  "ground": "5行目の rate = 0.8 が const 宣言への再代入である点に触れていれば満たす",
  "depth": "console.log(applyCoupon(1000)) に到達せず何も出力されない点、または total の計算（900）までは進んでいる点に触れていれば満たす",
  "core_reject": [
    "900 が出力されると読んでいる",
    "let の total への再代入が問題だと読んでいる"
  ]
}
```

### `depth` を変更した理由

初版の `depth` は「TypeError という具体的なエラー名、または console.log まで到達しない点」だった。前半の TypeError は **`core`（const の再代入でエラー）を満たせばまず書かれる語**なので、`core` と `depth` が共線的になる。「5行目で const の rate に再代入しているので TypeError で止まります」の一文で core・ground・depth・articulation がすべて full になり、`depth` の判定が働いたのか core の巻き添えなのかを切り分けられない。

**6問検証の目的は「読解型ごとに異なる `depth` の判定条件が機能しているか」を測ることなので、トレース型の代表でこれが測れないのは検証設計として成立しない。**

エラー名を外して `console.log` 未到達・`900` まで進んでいる点に限定すると、core を満たしても depth が none になる回答（＝「const の再代入でエラーです」だけの回答）が現れ、判定を測れるようになる。トレース型の depth 条件「具体的な値・回数・順序・戻り値に踏み込んでいる」とも一致する。

なお `ideas/問題作成ガイド.md` の記入例も同時に修正済み。あわせて同ガイドに「`depth` は `core` から独立させる」というルールと、その確認方法（core だけを満たす一文が depth も満たさないか試す）を追記した。**残り94問すべてに効く。**

### 残る性質（許容と判断）

この修正後も、core と ground を満たす回答は 83点前後（パーフェクト帯）に届く。1問目としてはこれで妥当と判断した。潰したかったのは点の高さではなく **`depth` が独立に測れないこと**で、そちらは解消している。

## ステージ 2 ─ var が混ざったコードの読み方

| 項目 | 値 |
|---|---|
| order | 2 |
| title | var が混ざったコードの読み方 |
| language | js |
| difficulty | 3 |
| reading_type | ズレ |
| 収束性 | 記述 |

> **改訂で `continue` を撤去した。** 初版は「`var` は関数スコープ」＋「`continue` は手前の代入を止めない」という**独立した洞察2つ**を要求しており、2問目としては前提の借金が大きすぎた（`continue` は構成案ステージ14）。条件を `if (order.status !== "canceled")` の肯定形にすると、代入が if の外にあることが見た目で分かるため洞察が1つに収まる。**出力・題材・ズレの構造は初版のまま。**

### code

```js
function summarizeOrders(orders) {
  var total = 0;

  for (var i = 0; i < orders.length; i++) {
    var order = orders[i];
    if (order.status !== "canceled") {
      total = total + order.amount;
    }
  }

  // 集計に入れた最後の注文を運用ログに残す
  console.log("最後に集計した注文:", order.id);

  return total;
}

console.log(summarizeOrders([
  { id: "A-1", status: "paid", amount: 1200 },
  { id: "A-2", status: "paid", amount: 800 },
  { id: "A-3", status: "canceled", amount: 5000 },
]));
```

### question

コメントに書かれた意図と、実際にログへ出る内容が食い違っています。ログに何が出るか答え、なぜそうなるのかを説明してください。

### model_answer

ログには「最後に集計した注文: A-3」と出ます。しかし A-3 は status が canceled なので合計に加算されておらず、返ってくる合計も A-1 と A-2 だけの 2000 です。コメントが意図している「集計に入れた最後の注文」は A-2 なので、意図と実際の出力が食い違っています。

原因は order が var で宣言されていることです。var はブロックスコープを持たず関数全体で有効になるため、ループを抜けた後も最後の繰り返しで代入された値、つまり配列の末尾要素が残ります。合計に加算するかどうかを分けているのは if の中だけで、var order への代入はどの注文でも必ず実行されます。

### 想定誤読（`core_reject` の材料）

- 「A-2 が出る」と読んでいる（＝ `var` のスコープに気づかず、コメント通りに動くと考えている）
- 「if で弾かれるので `order` に canceled の注文は入らない」と読んでいる
- 「ループの外なので `order` は参照できずエラーになる」と読んでいる（`let` の挙動と取り違えている）
- 合計値（2000）の計算だけを説明して、ログの食い違いに触れていない

### 補足

- 出力は `最後に集計した注文: A-3` → `2000` の2行（node で実行確認済み）。
- `let order` に変えるとログ行が `ReferenceError: order is not defined` になる。**これは模範解答に書かない。** ブロックスコープ（構成案ステージ20）・TDZ（同21）の内容を2問目の模範解答に置くと、学習者は「知っているべきだった」と受け取る。振り返り画面の解説側で軽く触れる程度に留める。
- `orders` が空配列だと `order` が undefined になり `order.id` で TypeError（確認済み）。設問では問わない。
- **`keywords` を書くときの注意:** 模範解答に「巻き上げ」「hoisting」の語を使っていない。スロット語に入れると模範解答自身が層1で落ちる。

## ステージ 3 ─ 基本型と「無い」の2種類

| 項目 | 値 |
|---|---|
| order | 3 |
| title | 基本型と「無い」の2種類 |
| language | js |
| difficulty | 2 |
| reading_type | トレース |
| 収束性 | 記述 |

> **改訂で「7つの出力を順に答える」を設問から外した。** 理由は下記「設問を1本化した理由」。コードは初版のまま（型の一覧を見せる材料として必要）。

### code

```js
// GET /api/profile のレスポンスをそのまま受け取ったもの
const profile = {
  id: 1024,
  name: "佐藤",
  isActive: true,
  age: null,
};

console.log(typeof profile.id);
console.log(typeof profile.name);
console.log(typeof profile.isActive);
console.log(typeof profile.age);
console.log(typeof profile.company);
console.log(profile.age);
console.log(profile.company);
```

### question

`age` と `company` はどちらも「値が無い」状態ですが、意味が違います。それぞれ何を表しているか、コードの出力を根拠に説明してください。

### model_answer

age はキー自体がレスポンスに存在していて、その値として null が入っている状態です。サーバーが「この項目に値は無い」と明示して返したことを表します。一方 company はキー自体がレスポンスに存在せず、存在しないプロパティへアクセスした結果として undefined が返っています。項目そのものが返ってこなかった状態です。

根拠は6つ目と7つ目の出力で、profile.age は null、profile.company は undefined になります。5つ目の typeof profile.company だけが "undefined" になるのも、キーが存在しないことの現れです。

なお4つ目の typeof profile.age は "null" ではなく "object" になります。null に対する typeof が "object" を返すのは JavaScript 初期からの既知の仕様上の不具合で、null かどうかの判定に typeof は使えません。

### 想定誤読（`core_reject` の材料）

- **age と company を「どちらも値が無いので同じ」とまとめている** ← `core_reject` に入れるのはこれだけにする
- 存在しない `profile.company` へのアクセスはエラーになると読んでいる

### 【重要】`core_reject` に入れてはいけないもの

- 「`typeof profile.age` を "null" と答えている」
- 「`profile.company` の出力を null と答えている」

この2件を `core_reject` に昇格させると、v3 の矛盾 veto（`contradiction`）が発動して `deep_score ≤ 20` かつ `keyword_score ≤ 10` の**一発30点上限**になる。`typeof null` は3問目に置く罰としては過剰で、そのまま離脱要因になる。**`depth` の減点材料に留めること。**

### 設問を1本化した理由

初版の設問は「7つの出力を順に答える」＋「null と undefined の違いを説明する」の2部構成だったが、v3 の単一 `core` に載らない。

- `core` を「7つの出力」に置く → 暗記ゲーになり、構成案が批判する機能紹介型に寄る。かつ**値の誤りの発生面が7個**あり、どれか1つの取り違えで矛盾 veto が発動して全損する
- `core` を「null と undefined の違い」に置く → 出力を全問正解したが説明を書かなかった回答が `core = none` になり、理論上限52点で**絶対にクリアできない**

どちらに置いても壊れるため、設問を後者に絞った。7出力の列挙をやりたい場合は別ステージに分ける。

### 補足

- `typeof` の出力にクォートは表示されない（`console.log(typeof x)` の stdout は `number`）。値は文字列だが画面上はクォートなし。ルーブリックを書くときに表記を問わないこと。
- ステージ26（オプショナルチェーン）・ステージ7（`==` と `===`）への伏線になる。`??` はステージ10で扱うため、ここでは意図的に登場させていない。
- 箇条書き回答（`1. number` `2. string` …）を誘発する設問は、引用照合が外れて `fabricationSuspected`（3観点以上 demote → deep 20点上限）を誤爆させうる。設問を1本化したことでこのリスクも下がっている。

## ステージ 4 ─ コピーされる値・共有される値 ─ プリミティブと参照

| 項目 | 値 |
|---|---|
| order | 4 |
| title | コピーされる値・共有される値 ─ プリミティブと参照 |
| language | js |
| difficulty | 2 |
| reading_type | トレース |
| 収束性 | 記述 |

### code

```js
const defaultSettings = { notifyEmail: true, maxProjects: 3 };
const proSettings = defaultSettings;
proSettings.maxProjects = 20;

let defaultRetryCount = 3;
let proRetryCount = defaultRetryCount;
proRetryCount = 20;

console.log(defaultSettings.maxProjects);
console.log(defaultRetryCount);
console.log(defaultSettings === proSettings);
```

### question

3つの出力を順に答えてください。そのうえで、同じ手順で書いているのに `defaultSettings` と `defaultRetryCount` で結果が変わる理由を説明してください。

### model_answer

出力は順に 20、3、true です。

オブジェクトを代入するとき、渡るのは中身の複製ではなく同じ実体を指す参照です。proSettings と defaultSettings は同じオブジェクトを見ているため、proSettings.maxProjects を書き換えると defaultSettings 側からも 20 に見えますし、=== の比較も true になります。

一方 number はプリミティブなので、代入時に値そのものがコピーされます。proRetryCount と defaultRetryCount は別々の値を持つため、proRetryCount への再代入は defaultRetryCount に影響せず 3 のままです。

defaultSettings は const で宣言されているのに中身が変わっている点も重要です。const が禁止するのは変数への再代入だけで、参照先のオブジェクトのプロパティを書き換えることは禁止しません。

### 想定誤読（`core_reject` の材料）

- `defaultSettings.maxProjects` を 3 と答えている（オブジェクトもコピーされると読んでいる）
- `defaultRetryCount` を 20 と答えている（プリミティブも共有されると読んでいる）
- 「const なのでプロパティも変更できない／エラーになる」と読んでいる
- `defaultSettings === proSettings` を false と答えている

### 【先回り】`core` は1要素に絞ること

この問題の理由は本質的に2要素（オブジェクトは参照が共有される / プリミティブはコピーされる）ある。**そのまま `core` に書くとガイドの「結論1つ」違反**になり、正しく短い回答が partial（24点）に落ちて不合格になる。

- `core` = 「オブジェクトは同じ実体を共有するため、片方の書き換えが両方に見える」の1要素
- `depth` = 「number はコピーされるので影響しない」「`===` が true になる」を回す

### 補足

- **螺旋の回収元。** ステージ28（スプレッドの浅いコピー）とステージ36（reduce の蓄積オブジェクト）で再登場させる。
- ステージ5 と対になる。4 で「参照とは何か」、5 で「参照が関数をまたぐと何が起きるか」を扱う。
- `===` がステージ7（`==` と `===`）より前倒しになるが、ここで問うのは型変換ではなく同一性なので実害はない。

## ステージ 5 ─ 参照が共有されたまま渡される関数を読む

| 項目 | 値 |
|---|---|
| order | 5 |
| title | 参照が共有されたまま渡される関数を読む |
| language | js |
| difficulty | 3 |
| reading_type | ズレ |
| 収束性 | 記述 |

> **6問検証セットの「ズレ」型の代表。** ズレ型の `depth` 判定（食い違っている箇所を特定し、どう食い違っているかを述べているか）の検証はこの問題で行う。
>
> **改訂で `email: "sato@example.com"` を `userId: "u-1024"` に変更した。** メールアドレス形式が `app/api/score/route.ts` の PII 検出（`/[\w.+-]+@[\w-]+\.[\w.]{2,}/`）に引っかかり、**オブジェクトを引用して正答した学習者が 400 `pii_detected` で採点自体を拒否される**ため。実際に検出されることを確認済み。参照共有の主題は `tags` 配列なので `email` は不要。

### code

```js
// 既定のタグを足したユーザーを返す（元のデータは変更しない想定）
function withDefaultTags(user) {
  const copied = user;
  copied.tags.push("newsletter");
  return copied;
}

const registered = { userId: "u-1024", tags: ["signup"] };
const forMail = withDefaultTags(registered);

console.log(forMail.tags);
console.log(registered.tags);
```

### question

この関数はコメントに書かれた意図で作られています。意図と実装が食い違っている箇所を挙げ、どのように食い違っているかを、実行するとどうなるかまで含めて説明してください。

> 「実行するとどうなるかまで含めて」を足したのは、設問に忠実に「3行目がコピーになっていない点です」とだけ答えると、設問要求は満たしているのに `core`（元のオブジェクトも書き換わる）が partial に落ち、合計55点前後の綱渡りになるため。設問と `core` を一致させる。

### model_answer

食い違っているのは3行目の const copied = user; です。これはオブジェクトを複製しておらず、同じオブジェクトを指す参照に copied という別名を付けただけです。

そのため copied.tags.push("newsletter") は、呼び出し元の registered が持っている配列そのものを書き換えます。出力は2行とも ["signup", "newsletter"] になり、「元のデータは変更しない」という意図は満たされていません。

const で宣言していても防げません。const が禁止するのは変数への再代入だけだからです。

### keywords

```json
[
  { "match": ["copied", "3行目", "user", "引数"] },
  { "match": ["書き換わ", "書き換え", "registered", "呼び出し元"] },
  { "match": ["参照", "複製", "コピーではな", "別名", "同じオブジェクト", "共有"] },
  { "match": ["signup", "newsletter", "2行とも", "両方とも"] }
]
```

- スロット①=対象（どこが問題か）、②=結論（何が起きるか）、③=根拠（なぜ起きるか）、④=踏み込み（具体的な出力値）。
- **②に結論語（`書き換わ` / `書き換え`）を入れてある。** 初版は②が `同じオブジェクト` / `共有` という根拠側の語彙で、③と役割が重複していた。ガイドの「1・2番目は対象名と結論語」に合わせて入れ替えた。
- **`code` のコメント行に「元のデータは変更しない」があるため、この語はキーワードに入れていない。** 設問文よりもコードのコメントのほうが写しやすく、無料点になりやすい。
- 模範解答は4スロットすべてにヒットする（`copied` / `書き換え` / `参照` / `newsletter`）。`lib/ai/compose.ts` の `normalizeForMatch` + `scoreKeywords` で照合確認済み（20/20）。

### rubric_items

```json
{
  "core": "元のオブジェクト（registered）も書き換わってしまうという結論を指していれば満たす",
  "ground": "const copied = user; がコピーではなく同じオブジェクトへの参照であることに触れていれば満たす",
  "depth": "出力が2行とも [\"signup\", \"newsletter\"] になる点に触れていれば満たす",
  "core_reject": [
    "registered.tags は [\"signup\"] のままだと読んでいる",
    "const で宣言しているので変更できない、またはエラーになると読んでいる",
    "関数の引数はコピーして渡されるので呼び出し元は影響を受けないと読んでいる"
  ]
}
```

- `depth` は単一条件に短縮した。初版は「特定したうえで、Aまたは B」という入れ子条件113字で、「特定したうえで」が両方の枝にかかるのか読めず gpt-4o-mini の判定が振れる。ズレ型の共通条件は `lib/ai/prompt.ts` の STATIC_PROMPT 側に既にあるので、rubric 側は上積み分だけを書く。
- 配列の表記ゆれ（`[ 'signup', 'newsletter' ]` / `["signup","newsletter"]`）は問わない。学習者には出力が表示されないため、脳内表記で書く。

### 補足

- **螺旋の回収元。** ステージ28（スプレッドの浅いコピー）で「`{ ...user }` にしても `tags` は共有されたまま」として再登場させると、4→5→28 が一本の線になる。

- 模範解答の第3段落（const は再代入だけを禁じる）はステージ4の第4段落と内容が重なるため、1文に圧縮した。4を通った直後の学習者に焼き直しと見せないため。
