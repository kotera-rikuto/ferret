## ステージ 15 ─ 関数宣言 ─ 入口（引数）と出口（戻り値）を掴む

| 項目 | 値 |
|---|---|
| order | 15 |
| reading_type | 意図 |
| 収束性 | 記述 |
| difficulty | 2 |
| context | なし |

### code

```js
// カートの小計から送料を決める
function calcShipping(subtotal, region) {
  if (subtotal >= 5000) return 0;

  if (region === "okinawa" || region === "hokkaido") {
    return 1200;
  }

  return 700;
}
```

### question

この関数には、書いた人が実現しようとしたルールが表れています。どういうルールなのかを、コードのどこからそう読み取れるのかを添えて説明してください。

### model_answer

この関数は、カートの小計 subtotal と届け先の region を受け取り、送料の金額を数値で返します。

実現しようとしているのは、購入額が 5000 円以上なら送料を無料にするというルールです。その判定を関数の先頭の if に置いているため、沖縄や北海道でも 5000 円以上なら送料はかかりません。

5000 円未満のときだけ region を見て、okinawa と hokkaido なら 1200 円、それ以外は 700 円を返します。

### prerequisite

`||` は「または」を表す演算子で、左右のどちらかが成り立てば全体が成り立ちます。`===` は左右が同じかどうかを判定します。`return` はその場で関数を終わらせ、書かれた値を呼び出し側に返す文です。

### keywords

```json
[
  { "match": ["送料", "subtotal", "小計"] },
  { "match": ["無料", "0円", "取らな", "かからな"] },
  { "match": ["5000", "先頭", "最初", "return 0"] },
  { "match": ["沖縄", "北海道", "okinawa", "hokkaido", "地域"] }
]
```

### rubric_items

```json
{
  "core": "購入額が 5000 円以上なら送料を無料にするというルールを実現しようとしているという結論を指していれば満たす",
  "ground": "無料にする判定が関数の先頭の if にある点、または 5000 円という基準に触れていれば満たす",
  "depth": "無料の判定を先に置いているため沖縄や北海道でも 5000 円以上なら無料になる、という書き方の狙いに触れていれば満たす",
  "core_reject": [
    "5000 円以上でも沖縄や北海道は 1200 円かかると読んでいる",
    "送料は届け先だけで決まり購入額は関係しないと読んでいる",
    "5000 円未満はすべて 700 円になると読んでいる"
  ]
}
```

### 設計の意図

**`core` を「5000 円以上なら無料」の1要素に絞り、「地域によって金額が変わる」を `depth` に回した。**
ルール自体は2要素（免除条件 + 地域差）あるので、両方を `core` に詰めると
「5000円以上なら送料無料です」という正しく短い回答が partial に落ちる（ガイドの「結論を1つだけ」）。

**`depth` に置いたのは地域差そのものではなく「無料の判定を先に置いた狙い」。**
早期 return の位置が「沖縄でも 5000 円以上なら無料」という挙動を作っているので、
これが意図型の `depth` 条件（何を実現したくてその書き方を選んだのか）に一致する。
`core` を満たす一文はここに触れないため、**`depth` が独立に測れる**（実測でそうなった）。

`送料` を設問文に入れないため（I-802）、設問は「どういうルールなのか」と抽象的に書いた。
何についてのルールかはコード1行目のコメントから分かる。

## ステージ 53 ─ 命名とコメントから意図を読む ─ 中身を見ずに責務を答える

| 項目 | 値 |
|---|---|
| order | 53 |
| reading_type | 命名 |
| 収束性 | 記述 |
| difficulty | 3 |
| context | なし |

### code

```js
// articles.js ── 記事の公開まわり

/** 下書き記事を公開状態に切り替える。すでに公開済みなら何もしない */
async function publishArticle(articleId) { /* …… */ }

function isPublishable(article) { /* …… */ }

function formatPublishedAt(date) { /* …… */ }
```

### question

このファイルは中身を伏せてあります。isPublishable がどういう役目を担う関数だと読めますか。何を受け取って何を返すのかと、そう判断した手がかりがどこにあるのかを説明してください。

### model_answer

isPublishable は、記事1件を表す article を受け取り、その記事を公開してよい状態かどうかを true か false で返す判定の関数だと読めます。

手がかりは2つあります。ひとつは is で始まる命名で、真偽値を返す判定の関数にはこの付け方をする習わしがあります。もうひとつは publishArticle に付いている「すでに公開済みなら何もしない」という説明で、公開状態に切り替える前に切り替えてよいかを確かめる場所が必要になるため、その判定を担うのが isPublishable だと読めます。

記事の状態を実際に書き換えるのは publishArticle 側で、isPublishable は判定だけを担い、状態は変えないと読むのが自然です。formatPublishedAt は日付を表示用の文字列に整える関数なので役目が別です。

### prerequisite

`/** … */` は JSDoc と呼ばれる形式の注釈で、直後の関数の説明を書きます。`async` が付いた関数は、中で保存や通信の完了を待てます。`/* …… */` の部分は、この問題のために中身を隠してあります。

### keywords

```json
[
  { "match": ["article", "記事"] },
  { "match": ["true", "false", "真偽", "boolean"] },
  { "match": ["命名", "コメント", "名前の付け方"] },
  { "match": ["何もしない", "すでに公開", "publishArticle", "切り替え"] }
]
```

### rubric_items

```json
{
  "core": "isPublishable が公開してよい状態かどうかを真偽値で返す判定の関数だと読み取れていれば満たす",
  "ground": "is で始まる命名、または publishArticle に付いている説明を手がかりとして挙げていれば満たす",
  "depth": "判定だけを担い記事の状態を変えるのは publishArticle 側だという役目の切り分けに触れていれば満たす",
  "core_reject": [
    "isPublishable が記事を公開状態に切り替える関数だと読んでいる",
    "isPublishable が公開日時を文字列に整える関数だと読んでいる",
    "isPublishable が公開済みの記事の一覧を返す関数だと読んでいる"
  ]
}
```

### 設計の意図

**中身を伏せているので `depth` を「実装が担っている責務」に置けない。**
ガイドの命名型の `depth` は「名前から読める責務と、実装が実際に担っている責務の対応」だが、
この問題では実装が見えない。そこで**同じファイルの他の関数との責務の切り分け**に置き換えた
── `is` で始まる述語は判定だけを担い、状態を変えるのは `publishArticle` 側、という対応。
名前から読める規約と、周囲のコードから読める役割の対応なので、命名型の趣旨からは外れていない。

`core_reject` の1件目（切り替える関数だと読む）が命名型で一番起きやすい誤読。
`is` の規約を知らないと `publishArticle` と混ざる。

`prerequisite` で「コメント」ではなく「注釈」と書いてあるのは、
`コメント` がスロット#3 のキーワードで、かつ**コードに出てこない語**だから（I-817）。

## ステージ 59 ─ スタックトレースを読む ─ ログから原因の行を特定する

| 項目 | 値 |
|---|---|
| order | 59 |
| reading_type | 影響 |
| 収束性 | 一意 |
| difficulty | 3 |
| context | **あり**（実行結果パネル） |

### code

```js
function buildMessage(user) {
  return `${user.name} さんの申請が承認されました`;
}

function notifyApproval(userId) {
  const user = findUser(userId); // 見つからないと undefined を返す
  return buildMessage(user);
}
```

### context（実行結果）

```
TypeError: Cannot read properties of undefined (reading 'name')
    at buildMessage (notify.js:2:14)
    at notifyApproval (notify.js:7:10)
    at approve (approval.js:12:5)
```

**行番号はコード側と一致させてある。** `notify.js:2` は `user.name` を読む行、
`notify.js:7` は `buildMessage(user)` を呼ぶ行。影響型は行を根拠に答えさせる問題なので、
ここがズレると正解が存在しなくなる（ガイドの注意）。

### question

エラーが発生した箇所と、根本の原因がある箇所はそれぞれどこだと読めますか。実行結果のどの行を手がかりにしたかも添えて説明してください。

### model_answer

エラーが発生したのは buildMessage の中、notify.js の2行目で user.name を読もうとした箇所です。実行結果の1行目に Cannot read properties of undefined (reading 'name') と出ていて、2行目が at buildMessage (notify.js:2:14) になっているのが手がかりです。

ただし根本の原因は notifyApproval 側、notify.js の6〜7行目にあります。findUser は見つからないと undefined を返すのに、その戻り値を確かめないまま buildMessage に渡しているためです。buildMessage は user が必ずある前提で書かれているので、直すべきなのは呼び出す側です。

実行結果の4行目に at approve (approval.js:12:5) とあるので、この失敗は approve まで伝わり、承認の処理全体が止まります。

### prerequisite

スタックトレースは、エラーが起きたときにどの関数からどの関数へ呼ばれてきたかを並べたものです。上の行が新しく、下へ行くほど呼び出した側になります。各行の `ファイル名:行:桁` は、その関数のどの位置で止まったかを表します。`${...}` はテンプレートリテラルで、文字列の中に値を差し込む書き方です。

### keywords

```json
[
  { "match": ["buildMessage", "2行目", "user.name"] },
  { "match": ["notifyApproval", "findUser", "6行目", "7行目"] },
  { "match": ["undefined", "確かめ", "チェック", "見つからな"] },
  { "match": ["approve", "approval.js", "波及", "伝わ"] }
]
```

### rubric_items

```json
{
  "core": "根本の原因は notifyApproval で findUser の戻り値を確かめていない点にあるという結論を指していれば満たす",
  "ground": "実行結果の at buildMessage (notify.js:2:14) や at notifyApproval (notify.js:7:10) の行を手がかりとして挙げていれば満たす",
  "depth": "この失敗が approval.js の approve まで伝わっている点、または buildMessage を直しても他の呼び出し箇所で同じことが起きる点に触れていれば満たす",
  "core_reject": [
    "buildMessage の書き方そのものが原因だと読んでいる",
    "findUser の中に原因があると読んでいる",
    "approval.js の approve に原因があると読んでいる"
  ]
}
```

### 設計の意図

**`core` を「発生箇所」ではなく「原因箇所」に置いた。** 発生箇所はログの2行目を写せば分かるので、
そこを `core` にすると転記で満点になる。原因箇所は「`findUser` が `undefined` を返しうる」と
「その戻り値を確かめていない」を結び付けないと出てこないので、読解の中核になる。

**`depth` は波及範囲（`approve` まで伝わる）。** 影響型の `depth` 条件そのもの。
発生箇所と原因箇所の切り分けができても波及に触れないまま終わる回答が普通にあるので、
`core` から独立している。

`core_reject` の1件目が**この問題の主題そのもの**（発生箇所と原因箇所の混同）。
ただし正しい回答も「発生したのは buildMessage」と書くため、
`原因だと読んでいる` まで含めた書き方にして誤爆を避けている。実測では誤爆しなかった。

`prerequisite` に `approve` / `伝わ` / `確かめ` を書いていないのは、
どれもキーワードでコードには出てこないため（I-817）。
`context` はこの検査の対象外だが、`prerequisite` は対象。

## ステージ 78 ─ テストコードを読む① ─ テストから関数の仕様を答える

| 項目 | 値 |
|---|---|
| order | 78 |
| reading_type | 仕様 |
| 収束性 | 記述 |
| difficulty | 3 |
| context | なし |

### code

```js
// zipCode.test.js
import { describe, it, expect } from "vitest";
import { normalizeZip } from "./zipCode";

describe("normalizeZip", () => {
  it("ハイフンなしで渡したとき", () => {
    expect(normalizeZip("1500001")).toBe("150-0001");
  });

  it("ハイフンありで渡したとき", () => {
    expect(normalizeZip("150-0001")).toBe("150-0001");
  });

  it("桁が足りないとき", () => {
    expect(normalizeZip("15000")).toBe(null);
    expect(normalizeZip("")).toBe(null);
  });
});
```

### question

このテストだけを根拠に、normalizeZip がどういう約束（入力と出力のきまり）を持つ関数なのか説明してください。

### model_answer

normalizeZip は郵便番号を表す文字列を受け取り、150-0001 のようにハイフン入りの形にそろえて返す関数です。

1つ目のテストでは 1500001 のようにハイフンなしの7桁を渡すと 150-0001 が返り、2つ目のテストでは最初からハイフンが入っている 150-0001 を渡しても同じ 150-0001 が返ります。つまりどちらの渡し方でも出力は1つの形にそろいます。3つ目のテストからは、桁が足りないものと空のものには null が返ると読めます。根拠は expect と toBe が期待している値です。

一方で、このテストが保証しているのはここまでです。8桁以上のものや全角の数字、ハイフンの位置が違うものをどう扱うかはテストに無いため、決まっていないと考えるべきです。

### prerequisite

Vitest はテストを書くための道具です。`describe` はまとめの見出し、`it` は1つの場合を表し、`expect(値).toBe(期待値)` で「この値はこうなるはず」と書きます。実際の値が期待値と違えば、そのテストは失敗します。

### keywords

```json
[
  { "match": ["郵便番号", "文字列", "7桁", "zipCode"] },
  { "match": ["ハイフン", "150-0001", "そろえ", "同じ形"] },
  { "match": ["toBe", "expect", "null", "2つ目"] },
  { "match": ["保証", "8桁", "全角", "テストに無い", "決まっていな"] }
]
```

### rubric_items

```json
{
  "core": "渡し方が違ってもハイフン入りの同じ形にそろえて返す関数だという結論を指していれば満たす",
  "ground": "expect と toBe が期待している戻り値（150-0001 や null）を根拠として挙げていれば満たす",
  "depth": "テストに現れない入力（8桁以上・全角の数字・ハイフンの位置が違うものなど）の扱いは保証されていない点に触れていれば満たす",
  "core_reject": [
    "ハイフンを取り除いた形にして返すと読んでいる",
    "桁が足りないときは空の文字列を返すと読んでいる",
    "渡したものをそのまま返す関数だと読んでいる"
  ]
}
```

### 設計の意図

**モックの `maskEmail` を採用しなかった。** `design/problem-samples-desktop-light.html` の
仕様型サンプルは `maskEmail("taro@example.com")` を題材にしていたが、
メールアドレス形式は `app/api/score/route.ts` の PII 検出
（`/[\w.+-]+@[\w-]+\.[\w.]{2,}/`）に当たる。
**テストの入力値を引用して正答した学習者が 400 `pii_detected` で採点そのものを拒否される。**
ステージ5で `email` を `userId` に差し替えたのとまったく同じ理由。
郵便番号なら電話番号の検出（`\b0\d{1,4}-?…`）にもカード番号の Luhn 検算にも当たらない
（`150-0001` / `1500001` で確認済み）。

**`it` の名前は「入力の場合」だけを書き、出力のきまりは書いていない。**
`it("ハイフンを補う")` のように結論を日本語で書くと、**テストの見出しを写すだけで
仕様の説明ができてしまう**（層1が「読めたか」ではなく「写したか」の検査になる）。
出力のきまりは `expect` / `toBe` の中身を読まないと出てこない形にした。
日本のコードで「正常系 / 異常系」のような見出しが普通にあることを踏まえた形でもある。

**`depth` は契約の境界（保証されていない範囲）。** 仕様型の `depth` 条件そのもの。
`core` は「そろえて返す」で、テストが**カバーしていない**入力に触れるかは別の一歩なので独立する。

### `depth` が読解型ごとに独立して動いていること

### 矛盾 veto の実測

④（結論が逆）は4問すべてで `contradiction = true` になった。
**ステージ59 だけ 30点**で、他の3問は10点。差は層2の中身:

- 15 / 53 / 78 … 4観点すべて `none` になったので層2が 0点。層1は矛盾により 10点で頭打ち
- 59 … 層2が 44点（`core=partial` 24 + `ground=full` 16 + `articulation=full` 4）付いたところを
  `DEEP_CAP_ON_CONTRADICTION = 20` が切って 20点。層1も 10点に頭打ちされて合計30点

**`ideas/採点システム_残課題.md` §2 で入れた「矛盾時の層2は0ではなく上限20」が実際に働いた初の実測。**
④は「発生箇所とログの読み方は合っているが原因の結論だけ反転している」回答で、
まさにこの上限が想定していたケース。0点にしていたら「途中まで読めている」が消えていた。

**§11（数値だけの引用で veto が素通りする経路）は今回は踏まれていない。**
ステージ59 の矛盾の根拠は「buildMessage を直せば解決し」という句で、
数値だけの引用にはなっていなかった。**遵守率の実測は B1 のゴールデンセットで行うこと。**

## 気づいた点（採点の仕組みは触っていない）

**A1 の方針どおり、ズレは記録に留めて `lib/ai/` は触っていない。** 判断は B1・B3 でまとめて行う。

### 1. ステージ78 の「短いが正しい回答」が 92点（パーフェクト帯）に入った

`ground=full` 16点 と `depth=partial` 6点 が付いている。回答は
「ハイフンありでもなしでも 150-0001 の形にそろえた文字列を返し、桁が足りなければ null を返します」で、
`expect` / `toBe` を根拠として挙げてはいないし、テストに無い入力の扱いにも触れていない。
`core` と `ground` の引用はどちらも回答の同じ部分だった。

**合否は正しい**（クリアすべき回答がクリアしている）が、**パーフェクト帯の希少性が薄れる。**
v3草案 §11 はパーフェクト率 15〜25% を目安にしている。

- 問題側の可能性: `ground` の条件が「戻り値を根拠として挙げていれば」なので、
  戻り値を書いただけで満たされると読める。「どのテストのどの `expect` か」まで求める書き方に絞れる
- 仕組み側の可能性: 同じ引用で複数の観点を full にできる（下記3と同根）

### 2. ステージ59 の ① が `depth=partial`

「この失敗は approve まで伝わります」は `depth` 条件（`approve` まで伝わっている点）に
そのまま当たるが partial 判定だった。合計94点でパーフェクト帯には入っているので実害はない。
影響型は「具体的に挙げている」が条件なので、波及先を1つ挙げただけでは足りないと
判定された可能性がある。**`articulation` が厳しい疑い（`残課題` §10）と同じ系統の観察。**

### 3. `verdict` が `none` / `partial` なのに `evidence` が入っている

プロンプト（`lib/ai/prompt.ts`）は「partial と none の evidence は空文字列にする」と指示しているが、
ステージ15 ② の `ground=none` に「5000円以上なら送料が無料になるルール」が入っていた。
**点数への影響はない**（`none` は 0点で、`evidence` は `full` の照合にしか使わない）が、
指示が守られていない箇所として記録しておく。

同じ引用を複数の観点に使い回す挙動も見られた（ステージ15 ②、78 ②）。
1つの引用で `core` と `articulation` の両方を full にできるので、
**引用照合は「観点ごとに別の根拠を持っているか」までは見ていない。** 上記1の遠因でもある。

### 4. 問題を作るうえで効いた制約（A2 への申し送り）

- **I-802（キーワードを設問文に入れない）が設問の書き方を強く縛る。**
  設問で対象を名指しすると、その語をキーワードに使えなくなる。
  4問とも「この関数」「このファイル」のように**設問側を抽象的にして、
  対象名はキーワードに回す**書き方に落ち着いた。既存5問も同じ形になっている
- **`prerequisite` は I-817 の制約でほぼ「コードに見えている記法の説明」しか書けない。**
  結論の語彙（`保証` `確かめ` `真偽` など）はキーワードなので書けない。
  結果として「演算子・構文・道具の説明」に収束する。**これは正しい落ち着き方**だと思う
  （前提知識は答えの下敷きではなく、記法の壁を外すためのもの）
- **モックの下書きはそのまま使えない場合がある。** ステージ78 は PII 検出に当たるため
  題材を差し替えた。`design/problem-samples-desktop-light.html` を叩き台にするときは、
  入力値が PII 検出の正規表現に当たらないかを必ず確かめること
- **投入前に機械検査を回すと手戻りが無い。** I-801〜I-817 は `npm run test:db` で
  投入後にしか回せないが、同じ判定を投入前に通すと1件も差し戻しが出なかった。
  A2 では投入前チェックを常設化する価値がある（`lib/ai/compose.ts` は依存ゼロなので
  `scoreKeywords` / `normalizeForMatch` をそのまま呼べる）
