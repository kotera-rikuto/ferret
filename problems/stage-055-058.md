## 各問の設計

### 55 ─ throw と Error

**読ませどころ:** `throw` に `Error` 以外の値も書けること。
文字列を投げると `catch` では受け取れるが、`name` も `message` も無い。
**しかもそれを読んでも実行時エラーにならない**（`undefined` が出るだけ）ので、静かに壊れる。

**`Error` を継承した自作の種類と並べてある。** 片方は `name` も `message` も揃っていて、
もう片方は何も無い。**同じ `catch` が両方を受けている**のが要点。

### 56 ─ try / catch / finally の順

**読ずどころ:** `return` を決めたあとにも `finally` が走ること。
`finally` に `return` を書くと、**先に決まっていた戻り値が捨てられる。**

**壊れていない関数と壊れている関数を並べてある。** 前者（`loadRecord`）で
「`return` の後でも `finally` は走る」を見せ、後者（`loadRecordBroken`）で
「だから `finally` の `return` が勝つ」に繋げる。**片方だけだと順序の理解が確かめられない。**

**`core` を「捨てられる」に置き、出力の順は `depth`。**
順序だけ答えた回答と、その帰結まで読めた回答を分けたい。

### 57 ─ 握りつぶされた catch（ズレ・72 の回収元）

**読ませどころ:** `try` の範囲に `applyTheme` の呼び出しまで入っているため、
**設定は正しく読めているのに既定値が返る。** しかも2つ目（本当に設定が壊れている回）と
**戻り値がまったく同じ**なので、呼び出し元から原因を区別できない。

**「握りつぶし」を `catch` の中身ではなく `try` の範囲の問題として組んだ。**
`catch (e) { return 既定値 }` だけを見せると「例外を無視するな」という一般論で終わるが、
**範囲が広すぎることが原因**だと分かると、直し方（`try` を割る）まで見える。

`catch` が `e` を一度も使っていない点は `depth` に回した。

### 58 ─ バリデーション（意図）

**読ませどころ:** 問題を見つけても途中で切り上げず、全部集めてから返す設計。
さらに **`ok` が `true` のときだけ変換済みの `order` を返す**ので、
呼ぶ側は「`ok` なら中身は揃っている」と信じられる。

**`core` は「一度に返す」1点。** 戻り値の形の話と、例外にしなかった選択は `depth`。
3つとも `core` に詰めると、正しいが1つしか書いていない回答が落ちる。

**この問題だけ `console.log` を置いていない**（意図型なので実行結果は答えにならない）。
