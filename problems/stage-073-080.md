## 各問の設計（要点のみ）

### 73 ─ ES Modules

**default に付ける名前は読み込む側が自由に決められる**ので、
`import toYen` と書いても入ってくるのは `summarize`。**名前に騙される形**にしてある。
中括弧の中（`TAX_RATE`）は同じ名前でなければ受け取れない、という対比も同じコードに入れた。

### 74 ─ CommonJS と ESM（ズレ）

`module.exports = helpers` は**オブジェクトを1つ渡しているだけ**で、名前ごとに出してはいない。
組み立ててから代入する書き方にしてあるので、Node の名前推測も効かない。

**「実行時のエラーではなく読み込み時のエラー」**というのが要点で、
`try` で囲んでも捕まらない。`depth` にここを置いた。

### 75 ─ package.json

`^` / `~` / 記号なし の3つを並べ、**上がってよい幅の違い**を読ませる。
`ci` の `&&` と `devDependencies` の扱いを `depth` に回した。

**読み物としての `code`。** 実行するものではないと `runnable: false` で明示している。

### 76 ─ fs / path（意図）

**なぜ文字列の足し算ではないのか。** `outDir` の末尾に区切りがあるかどうかを
気にしなくてよくなること、入力の形（相対・絶対・深さ・拡張子）に依存しなくなること、
区切り記号が OS で違うこと。3つを `core` / `depth` に振り分けた。

### 77 ─ process.env（実行できる形にした）

**環境変数はすべて文字として届く。** `RETRIES: "0"` は `??` を通り抜けて 0 のまま残る
（`||` だったら 3 に戻ってしまう）。**ステージ10（`??` と `||`）の理解がそのまま効く。**
`DEBUG: "false"` を `=== "true"` で比べているのは、`Boolean()` を使うと必ず true になる罠の回避。

### 79 ─ 落ちたテストから絞る（影響型・`context` を使う）

**4件のうち1件だけが落ちる**ようにしてある。
落ちた入力「Hello, World!」はカンマの後ろに空白があり、
**カンマ → ハイフン、空白 → ハイフン が続けざまに効いて2つ並ぶ。**

**通っている3件が「原因ではない場所」を教えてくれる**というのが影響型の読み方で、
そこを `depth` に置いた。59（スタックトレース）と同じく、`core` は原因箇所。

### 80 ─ 総合演習（ズレ・30 の回収）

**4つのうち1つだけが決まりを破っている。** `slice` / `filter` / スプレッドは新しい配列を返すが、
`sort` だけが同じ配列をその場で並べ替える。

**先頭のコメントが「仕様」の役をしている。** 機械が守らせてくれるわけではないので、
実際の動きと突き合わせるしかない ── これが総合演習として問いたいこと。
出力の2行が同じ中身になるのが、そのまま証拠になっている。
