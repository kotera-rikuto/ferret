## 各問の設計

### 16 ─ アロー関数

**読ませどころ:** `=> ({ … })` と `=> { … }` の書き分け。後者はブロックなので `return` が要る。
同じコードに両方を並べて、**1文字の差で結果が変わる**形にしてある。

**`core` は「値が返らない」1点。** 丸括弧の役割は `depth` に回した。

### 17 ─ return を書き忘れた関数を読む（ズレ）

**読ませどころ:** 3つの分岐のうち silver だけ `return` が無い。
`0.1;` は式として評価されて捨てられるだけで、**実行時エラーにならない。**

**9（truthy と falsy）と同じ「片方だけがズレている」構造にした。** ズレ型の `depth` 条件は
「食い違っている箇所を特定し、どう食い違っているかを述べている」なので、
gold が意図どおり動くことまで切り分けられて初めて `depth` が付く。

**33（`map` の return 忘れ）の回収元。**

### 18 ─ デフォルト値と残余引数

**読ませどころ:** 既定値が効くのは `undefined` のときだけで、**`null` では効かない。**
`undefined` を明示的に渡した2回目と、`null` を渡した3回目を並べて差を見せている。

**`core` を3回目に置いた。** 1回目（省略）は既定値の説明そのもので、
理解していなくても書ける。差が出るのは `null` を渡した場合だけ。

### 19 ─ 早期リターン（意図）

**ステージ15（A1・意図型）と題材を離した。** 15 は送料計算で「早期 return の位置に意図が出る」問題。
こちらは**ガード節を並べる形そのもの**を問うので、投稿の受付という別の題材にしてある。

**`core` は「末尾を通す場合だけにする」。** 「読みやすいから」で止まる回答と、
末尾に何が残るかまで言える回答を分けたい。

### 20 ─ スコープ

**読ませどころ:** `for` の中の `const total` が外側の `total` を隠す。
**実行時エラーにならず、`total: 0` という「それらしい値」が返る**ので気づきにくい。

**`depth` を `labels` 側に置いた。** `total` の話だけで終わる回答と、
戻り値の全体を追った回答を分けるため。

### 21 ─ 巻き上げと TDZ

**読ませどころ:** 3行の `console.log` が3つとも違う振る舞いをする。
`function` 宣言は中身ごと使える／`var` は名前だけで `undefined`／`const` は宣言前に触ると停止。

**`core` を「止まる」に置き、`depth` を「そこまでに何が出るか」にした。**
エラーだけ見て「全部動かない」と読む回答と、2行は出ていると読める回答が分かれる。

**この章で唯一、実行が途中で止まる問題。**

### 22 ─ クロージャ

**読ませどころ:** `createCounter` を2回呼ぶと、**別々の `issued`** ができる。
1つしか作らないコードだと「関数が変数を覚えている」ことは見えても、
**「呼ぶたびに新しく作られる」ことが見えない**ので、2つ作って比べる形にした。

**`core` は「別々に持つ」。** 3行の出力は `depth`。

### 23 ─ 高階関数（意図）

**読ませどころ:** 再試行を個々のAPI呼び出しに書かず、包む関数に切り出した理由。

**`core` は「切り離して1か所にまとめる」。** 「使い回せる」「呼ぶ側が楽」は `depth` に回した。
`core` に3つとも詰めると、正しいが1つしか書いていない回答が落ちる。

**呼び出しを2つ（回数 3 と 2）置いてある。** 1つだと「なぜ関数にしたのか」が
「たまたまそう書いた」と区別できない。

### 24 ─ 再帰関数

**読ませどころ:** 止まり方。`replies` を持たない葉で `return 0` に入る一方、
**`id: 3` の空の配列は最初の `if` に入らない**（`[]` は「あり」とみなされる）が、
数える相手が無いので結局 0 になる。**止まる理由が2通りある。**

**`core` は合計値ではなく「孫まで数えられる」に置いた。**
一意な問題で数字を `core` にすると、当てずっぽうでも通ってしまう（候補が少ないため）。
