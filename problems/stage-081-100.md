> ### TS編は語彙が三重に重なる。**これが原因のすべて**
>
> JS編では「前提知識が模範解答の言い換えになりやすい」だった（第5バッチの申し送り）が、
> TS編では**設問文まで含めて三重に重なる。**
>
> 型の説明に使う語（推論・検査・確かめる・共通・書かれていない・引き受ける…）は、
> **前提知識でも模範解答でも設問文でも同じ言い方になる。** JS のように
> 「`push` は末尾に足す」と具体物で言い換える余地が少ない。
>
> **対策は1つ。スロットには「模範解答にだけ出る語」を選ぶ。**
> 具体的には、**識別子（`config.mode`・`SettingKey`・`OrderSchema`）と、
> そのコード固有の値（`84`・`a,b`・`3件`）**を優先する。
> 一般的な説明語（`検査`・`確かめ`・`宣言`）をスロットに置くと、ほぼ確実に落ちる。

## 各問の設計（要点のみ）

### 81 ─ JS と TS を並べて読む（意図）

**同じ関数を型なし・型ありで並べてある。** 型なし側には2つの呼び出しを置き、
片方は静かに壊れ（`1200 - "300"`）、片方は実行時に落ちる。
**「動かさないと気づけない」対「書いた時点で分かる」**が1画面で見える。

### 82 ─ 型注釈と型推論

**`let` と `const` で決まり方が変わる**のが要点。86（`as const`）の下地になる。

### 83 ─ strictNullChecks（意図）

**同じ処理を2通り書いて、片方だけが止められる。** 早期リターン（第3章）と同じ形が
型の世界でも効くことを見せている。

### 84 ─ オブジェクト型と省略可能プロパティ

**4つの宣言のうち2つが通らない。** 「項目が足りない」と「余分な項目がある」の
**両方を1問に入れてある**（後者は見落とされやすい）。

### 85 ─ ユニオン型

**同じ変数に対する4つの呼び出しのうち2つだけが書けない。**
`if` の中と外で同じ `toFixed` を書いて、**位置によって可否が変わる**ことを見せている。87 への橋渡し。

### 86 ─ リテラル型と as const

**`const` に入れても中は守られない**というのが要点。`as const` を付けた側と並べてある。

### 87 ─ 絞り込み（**実行できる**）

型の話でありながら**実行して確かめられる**数少ない問題。
出力（`12.3` / `OK`）が、絞り込みが効いている証拠になっている。

### 88 ─ 関数の型（仕様型）

**実装を載せていない。** 型だけから何が言えて何が言えないかを分けさせる。
「呼ばれる回数」「並び順」は型に書かれていない、という**限界のほうを `depth` に置いた。**

### 89 ─ any / unknown / never（意図）

**同じことをする2つの関数を並べる。** `any` は照合をやめる側、`unknown` は先送りにする側。
`never` は3つ目として置き、数え漏らしの受け皿だと示している。

### 90 ─ 型エラーメッセージ①（影響型・`context`）

**`context` を使う3問目**（59・79 に続く）。コンパイラの出力を別パネルに置いた。
出力の**後半が「期待している側がどこで決まったか」を指している**ことに気づかせる。
`depth` は「直し方で波及範囲が変わる」で、54（影響範囲を読む）と同じ形。

### 91 ─ 型エラーメッセージ②（影響型・`context`）

**出力に出ている候補が原因とは限らない**という、長いユニオン型に特有の読み方。
`'keydown' is not assignable to type '"click"'` という一見矛盾した出力を題材にした。

### 92 ─ type と interface（意図）

**2つの別々の意図を1問に入れてある。** 共通項目の切り出し（`&`）と、
同じ名前の `interface` がまとまる性質。後者は**外部ライブラリの型を足すときにしか要らない**
ことまで書かせる。

### 93 ─ ジェネリクス（**実行できる**）

**3回の呼び出しで `T` が別のものに決まる。** 3つ目は配列が空なので、
**もう1つの引数のほうから決まる**のが読みどころ。

### 94 ─ keyof / typeof と Utility Types

**5つの型が1つの値から作られている。** `OnlyView` と `NoDebug` が結果として同じ形になる、
という気づきを `depth` に置いた。

### 95 ─ 型ガード（**実行できる**）

**`r is ApiOk` を書かないと `if` の中で絞られない。** ただの `boolean` との違いが要点。

### 96 ─ 判別可能なユニオン（**実行できる**・11 の回収）

**同じ `switch` が型を絞る。** 11 では「どの枝を通るか」だったものが、
ここでは「通ることで型が変わる」に変わる。

### 97 ─ Promise<T>（**実行できる**・65 の回収）

**違いは `await` の1語だけ。** 65 では実行するまで分からなかったものが、
**型を書いておくと書いた時点で止まる。** TS 編で JS 編の理解が報われる形。

### 98 ─ as と !（意図）

**どちらも「確かめていない」**というのが要点。
`parseAny` を3つ目に置いて、**何も書かなければその場で指摘される**ことも見せている。

### 99 ─ .d.ts を読む（仕様型）

**実装が存在しない前提。** `readonly`・`?`・戻り値が関数、といった手がかりから使い方を組み立てる。
`onFailed` が関数を返すのは「解除用」という慣習で、**型から慣習を読む**練習になっている。

### 100 ─ zod（仕様型・最終問題）

**1つの定義が検査と型の両方を決めている。** `z.infer` で型を手書きしていないので、
**検査を直せば型も付いてくる。** `parse` と `safeParse` の使い分けまで読ませる。

**100問目にふさわしい題材**として、型とバリデーションの同居を選んだ
（構成案の指定どおり）。
