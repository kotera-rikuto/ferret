## 何をするか

**最初の数問を、ログインなしで読めるようにする。**

**オーナーの方針（2026-09-11）:** いきなり登録が要るのは、触ってもらううえで障害になる。

**採点は登録後のまま。** 回答欄には「採点するには登録が必要です」を出す。

---

## なぜ「読むだけ」で止めるのか（採点を開けない理由）

**採点は1回 ¥0.04 の実費が出て、上限はすべて `user_id` に紐づいている。**

| | いま |
|---|---|
| 1人1日 20問 | `ai_usage_daily` の `(jst_date, user_id)` |
| 全体1日 500回 | 同じテーブルの「全ゼロUUID」の行 |
| 連打の安全網 | `user_attempts` を `user_id` で数える |

登録なしで採点できるようにすると、**その回の費用を誰にも紐づけられない。**
全体の上限があるので青天井にはならないが、**アカウントを持たない誰かが
全ユーザーぶんの枠を使い切って、その日の採点を止められる**（1日約¥20ぶんで全員が使えなくなる）。

**Ferret の価値はコードを読ませることなので、問題を見せた時点で大半は伝わる。**
費用の紐づけという別問題を抱え込むのは、人が集まってからでよい。

## なぜ必要か（もう1つの効き方）

**C8 が保留した論点がここで解ける。**

> **検索に出るページが5枚しかない**（問題100問はログインの向こう）── 事業判断

いま検索に出るのは `/` `/changelog` `/terms` `/privacy` などの**5枚だけ**です。
`CRAWL_DISALLOW` に `/problems` が入っているので、**100問は検索エンジンから見えません。**

数問を開けると、**その数問は検索の対象になります。** 「JavaScript const 再代入 エラー」のような
具体的な検索で当たる可能性が出てくる。**M1（技術記事）より手数が少なく、同じ方向に効きます。**

## ✅ 決まっていること（2026-09-11・オーナー判断）

**LP に「1問目をみてみる」ボタンを置き、そこからお試しで問題を見せる。**

**開放の実装と同じ回で出すこと。**

これにより下の判断②（区切り方）と④（回答欄の見せ方）が一部確定している。

## ⚠️ オーナーに確認すること

> **① 何問を開けますか**
>
> **LP のボタンは「1問目をみてみる」なので、最低でも1問目は開けます。**

>
> **② どこで区切りますか**
> - **案A: `order` が N 以下**（おすすめ）— 単純で、問題データを触らない
> - 案B: `problems` に「公開」の欄を足す — 問題ごとに選べるが、**欄が1つ増える**

> - **案A: 開ける**（おすすめ）— 全体像（101問ある）が見えるほうが「ちゃんとある」と伝わります。
>   開放済み以外は鍵のまま
> - 案B: 開けない — 問題ページに直接来た人だけが見る形になります
>
> **④ 回答欄をどう見せますか**
> - **案A: 入力欄は出すが、押すと登録へ誘導**（おすすめ）— 書いてみたくなった時点で誘導できます
> - 案B: 入力欄を出さず「登録すると採点できます」だけ置く

> **⑤ 開けた問題を検索の対象にしますか**

> - 案B: しない — 登録の障害だけ下げます
>
> **⚠️ 案Aを選ぶと、開けた問題の模範解答が検索に出る可能性があります。**

## 手順

1. 上の5点を決める
2. **開放の判定を1か所にまとめる**（例: `lib/progress/preview.ts` に `isPreviewProblem(order)`）
   - **画面と `proxy.ts` の両方から同じ判定を使うこと。** ズレると抜け道になる
3. `proxy.ts` の `matcher` を調整する
   - ⚠️ **matcher はリテラルしか書けない**（Next.js の制約）。
     `/problems/:path*` を外して**ページ側で判定する**形になる見込み
4. **`lib/seo/site.ts` の `CRAWL_DISALLOW` を対で更新する**
   - ⚠️ **忘れると `tests/unit/seo.test.ts` の U-836 が落ちる**
   - ⑤で案Aなら、開けた問題を `sitemap` にも載せる
5. `app/problems/[id]/page.tsx`
   - `!user` のときに `redirect("/login")` しない分岐を足す
   - **`loadProgress` は `userId` 必須**なので、未ログインでは呼ばずに「開放済みか」だけで判定する
   - ⚠️ **`select` の欄を増やさないこと。** `model_answer` と `rubric_items` は渡さないまま
6. 回答欄（`ProblemForm.tsx`）を④のとおりに
7. ③で案Aなら `/stages` も同様に
8. **確認する**
   - **ログアウトした状態で**開放した問題が読める
   - **開放していない問題は読めない**（URL 直打ちでも）
   - **採点APIは未ログインで 401 のまま**（ここが崩れると費用の穴になる）
9. `npm test` `npm run test:e2e` `npm run build`

### 判断したこと（票に書いていなかった分）

- **`id` で区切らなかった。** 実データはステージ1の `id` が **8**（`order` と一致していない）。
  `id` で書くと、問題を入れ直した日に**別の問題が黙って公開される**。
  そのぶん URL（`/problems/8`）が定数にできないので、`sitemap` と `/llms.txt` は
  ビルド時に DB を1回引く形にした。
- **`matcher` は「外す」しかなかった。** リテラルのパスしか書けず、
  開けてよいかは `order` で決まるのに URL に出るのは `id` なので、proxy 側では判断できない。
  代わりに **I-395 を「matcher にあるか、`lib/progress/preview.ts` を通しているか」** に書き換え、
  **I-404**（画面に `order <= 3` のような式を書いていない）を足した。
- **`CRAWL_DISALLOW` は `/problems` だけ外し、`/stages` は残した。**
  `/problems` をまとめて塞ぐと robots.txt で中身を読ませないことになり、
  **開けた1問も検索に出ない**（`index: false` すら届かない）。
  一方 `/stages` は人には見せるが、**あの画面には鍵付き100問へのリンクが並んでいる**ので、
  開けるとクローラーが100本のログイン画面へのリダイレクトを辿ることになる。
  残り100問を索引から守っているのは、問題画面の `generateMetadata` が返す `index: false`。
- **ブラウザで見て2つ直した。どちらもテストでは出なかった。**
  1. 送信ボタンは画面下に貼り付いている（`lg:fixed`）ので、
     案内をそのまま出すと **1280×900 で y=990、375×780 で y=778** ── どちらも画面の外か下端ぎりぎりで、
     **「押しても何も起きない」ように見えた。** 案内が出た時点でその位置まで送るようにした
     （`prefers-reduced-motion` を見て動きを切り替える）。
  2. **狭い画面の `/stages` に、登録の入口が1つも見えなかった。**
     マップは開いた瞬間に現在地までスクロールするので（375px の実測で**ページの約 24,000px**）、
     上端の簡易ヘッダーは一度も目に入らない。ログイン済みの人向けの数字の帯は
     もともと `sticky` にしてあったが、ログイン前はその帯を出さないので**貼るものが無くなっていた。**
     同じ位置・同じ高さ（`h-15`）に簡易ヘッダーを貼り付けた
     （高さを揃えないと `StageMap` の章バナーが重なる ── E-466）。
