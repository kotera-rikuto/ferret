## 何をするか

**リザルト画面で0点のとき、巨大な「0」が画面の真ん中に出る。**
コードを読み違えた人に対して、罰のように見える。

数字を隠す必要はない。**大きさと配置を変える。**

---

## なぜ必要か

Ferret は「ネガティブな表現を使わない」という方針で全体を作っている。
文章では徹底しているのに、**一番目立つ数字がその方針を裏切っている。**

特に、結論が逆になっている回答（読み違い）を検出したときは0点になりやすい。
このとき本人は**真面目に読んで、間違えている。** 罰する場面ではない。

---

## ⚠️ オーナーに確認すること

> 0点のときの見せ方を変えたいのですが、方向性を決めてください。
>
> **案A: 読み違いのときだけ見せ方を変える**（おすすめ）
> 結論が逆だと判定されたときだけ、数字を小さくして
> 「次に見る場所」を画面の主役にします。
> - よい点: 一番きつく見える場面を狙って直せる
> - 悪い点: 画面の作りが2通りに分かれる
>
> **案B: 低い点のときは常に控えめにする**
> 何点以下なら控えめにするかを決めます（例: 30点未満）。
> - よい点: 作りが1通りで済む
> - 悪い点: 「あと一歩」の人にも同じ見せ方になる
>
> **案C: 点数の見せ方自体を全体的に変える**
> 数字を主役にするのをやめて、常に「読めたところ / 次に見る場所」を主役にします。
> - よい点: 方針として一貫する
> - 悪い点: 作業が大きくなる。**点数が見えにくいと物足りないと感じる人もいる**
>
> **おすすめは案A**です。問題が起きている場面が特定できているので、
> そこだけ直すのが確実で、作業も小さいためです。

## 手順

1. 上の方針を決める
2. リザルト画面（`app/result/[id]/ResultView.tsx`）で分岐を作る
   - 読み違いの判定は `user_attempts` の `contradiction` という記録で分かる
   - **すでに画面まで渡っているか確認すること**（渡っていなければ `page.tsx` で取得を足す）
3. 見せ方を変える
   - 数字を小さく、または位置を下げる
   - 「つぎの一歩」の文章を大きく、上に置く
   - **点数は隠さない**（信頼に関わる）
4. 文言を確認する
   - 禁止されている言葉を使っていないか
5. 画面で確認する
   - 動作確認用の問題（`order` が 999）に「900が出力される」と回答すると0点・読み違いになる
6. `npm run build`

### 着手前に分かったこと

**票が書かれた時点より状況が進んでいた。** 「巨大な0が画面の真ん中に出る」はデザイン移植の時点で
すでに解消されていて、いまは統計チップ3枚（スコア / キーワード / AI 採点・各 28px）に分かれている。

残っていた問題は2つ。

1. **読み違いのときは3枠すべてが 0 で並ぶ。** しかも数字が画面の上、文章（フェレットのメモ）が下という順番
2. `user_attempts.contradiction` は保存されているのに、**リザルト画面まで渡っていなかった**ので分岐が作れない

### 決めたこと

| | 決定 | 理由 |
|---|---|---|
| 適用範囲 | **案A: 読み違い（`contradiction`）のときだけ** | オーナー判断。点数で線を引く案Bは「あと一歩」の回まで巻き込む |
| 文章の扱い | **1枠のまま位置と大きさを変える** | オーナー判断。2枠に分けるのは E2 の担当で、保存形式の変更が要る |
| 見出し | **`もう一度挑戦しよう` のまま変えない** | 矛盾検出時の上限は30点（引用付き）・50点（申告のみ）で、クリア閾値55に届かない。「もう少しで届きそう」と書くと**事実と違う**。文言を足さなければ禁止語の risk もゼロで、票の「大きさと配置の問題」という指示にも忠実 |
| カウントアップ | **控えめにする回では止める** | 数字が動くと視線がそこに集まり、主役を入れ替えた意味が消える |
| XPバーの位置 | **控えめにする回は点数の下**（メモ → 点数 → XPバー） | E3 との衝突の解消時に決めた。数字系を1か所にまとめ、文章より下に置くため。通常時は E3 のままの並び（点数カード → XPバー → メモ） |

### 実装

**分岐の条件**（`ResultView.tsx`）:

```ts
const softened = contradiction && !cleared && Boolean(feedback);
```

- `!cleared` は保険。いま矛盾はクリアし得ないが、将来クリア閾値を下げたときに
  「クリアなのに控えめ」が生まれないようにしてある
- `Boolean(feedback)` が無いと、文章が無い回で**主役の枠が消えて画面が空になる**。
  そのときは通常の並びに戻す

**見せ方**（`softened` のとき）:

| | 通常 | 読み違いのとき |
|---|---|---|
| 並び | チップ3枚 → XPバー → 文章 | **文章 → 点数 → XPバー** |
| 点数 | チップ3枚（28px） | **1行に畳む（12px・ラベル付き）** |
| 文章 | 14px / `p-6` | **15px / `p-7`・下辺を厚くして主役に** |
| カウントアップ | あり | なし（真値をそのまま） |

チップと1行で**同じ数字**を出すため、3項目を `stats` 配列に寄せて両方から使っている
（片方だけ直して数字がずれるのを防ぐ）。`accent` はクラス名を文字列そのままで持つこと。
`bg-${...}` で組み立てると Tailwind がクラスを生成せず色が消える。

### 詰まった点

- `useEffect` の中で直接 `setState` すると `react-hooks/set-state-in-effect` で lint が落ちる。
  カウントアップの状態を `countUp` に改名し、**表示値は `softened ? totalScore : countUp` として
