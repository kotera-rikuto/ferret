# A4. 問題の頭に「実務の場面」を足す

**種別:** コンテンツ作成 + 実装（**判断が主**）
**規模:** 判断次第で**中〜特大**（下記）
**前提として終わっていること:** **A2（101問）** ✅済み・**A3（チュートリアル）** ✅済み

> ### ⚠️ 同時進行の注意
> `app/problems/[id]/page.tsx` を触る（E4・E5 と同じファイル）。
> **問題データを全件触るので、他の問題コンテンツ作業と同時に進めないこと。**

**先に読むもの**
- `ideas/問題作成ガイド.md`
- `app/problems/[id]/page.tsx`（**`context` と `prerequisite` の出し方が手本になる**）
- `tasked/E4-問題データに欄を足す.md`（**欄を足したときの手順がそのまま使える**）

---

## 何をするか

**問題の頭に「どういう場面でこのコードを読むことになったか」を置く。**

**オーナーの案（2026-09-02）:**
> 「上司から〜を頼まれました」のような**4コマ漫画**をそれぞれに入れたい。
> そのほうが文脈があって実務に近い。

### いまの状態（2026-09-02 実測）

設問は**場面の説明が一切なく、いきなりコードの話**から始まる。

```
[1] このコードを実行すると何が出力されますか。その数になるまでの過程も説明してください。
[2] このコードを実行すると何が出力されますか。そうなる理由も説明してください。
[3] 2つ目の console.log は何を出力しますか。1つ目の出力との違いも説明してください。
```

**「なぜこのコードを読んでいるのか」が無い。**

| 欄 | 使用状況 |
|---|---|
| `context` | **4問**（影響型の実行結果に使用済み。**空いていない**） |
| `prerequisite` | 100問（前提知識） |
| **場面を入れる欄** | **無い** |

---

## なぜ必要か

**Ferret の売りは「他人のコードが読める」こと。**

実務でコードを読むときは、必ず**理由**があります。「引き継いだ」「バグの報告が来た」
「レビューを頼まれた」。**その状況が読み方を決めます。**

いまの形は「問題集」に近く、**実務の読解とは別の作業**になっています。
場面があれば、**なぜこの観点で読むのかが自然に伝わります。**

---

## ⚠️ オーナーに確認すること（**ここが本体**）

### ① 「4コマ漫画」は絵ですか、文章ですか ← **一番大きい判断**

> **絵にする場合、101問 × 4コマ = 404枚**が必要です。
> マスコットの素材は `public/` に4種ありますが、**場面ごとの絵は1枚もありません。**
> 個人開発で404枚を用意するのは、**A2（101問）より大きい作業**になります。
>
> - **案A: 文章だけ**（おすすめ）
>   「先輩から、注文の集計処理を引き継ぐことになった。まずは中身を読んでほしいと言われた。」
>   のような**2〜3行**。**AIで下書きでき、101問ぶんでも現実的**です
> - 案B: マスコット + 吹き出し
>   既存のマスコット画像を1枚置いて、その横に文章を出します。
>   **絵は使い回すので新規に描く必要がありません**。「漫画っぽさ」は出ます
> - 案C: 本物の4コマ漫画
>   **404枚。** 外注か、絵を描ける人が要ります。**現実的ではないと思います**
>
> **案Bを勧めます。** 「漫画」の要望に一番近くて、作業量が案Aとほとんど変わりません。

### ② 全101問に入れますか

> - **案A: まず最初の10問程度で試す**（おすすめ）
>   **効果があるか分からないうちに101問書くのは危ない**です。
>   数問で試して、良ければ広げる
> - 案B: 全101問に入れる
>   統一感は出ますが、**やり直しになったとき101問ぶん書き直し**です

### ③ 場面をどう見せますか（画面の縦が伸びます）

> いま問題画面は上から「タイトル → コード → 実行結果 → 設問 → 前提知識 → 回答欄」です。
> 場面を足すと**さらに縦に伸びます**。E11 でスマホ対応をしたばかりなので、
> **スマホだとコードに辿り着くまでスクロールが増えます。**
>
> - **案A: 最初から表示（短く2〜3行）**（おすすめ）— 読ませたいものなので隠さない
> - 案B: たたんでおいて、押すと開く — 場面を読まない人が出ます

### ④ 上司をどう描きますか ← **方針と関わります**

> `CLAUDE.md` に**ネガティブな言い方をしない**という決まりがあります。
> 「上司に怒られた」「ミスを指摘された」のような書き方は方針と衝突します。
>
> **「頼まれた」「引き継いだ」「相談された」**のような、
> **前向きな依頼の形**に統一することを勧めます。

## 設計上の要点（実装する人へ）

### 場面を採点に使わないこと

**AI には渡さない。表示専用。**

`prerequisite`（前提知識）が既にこの扱いになっています。同じにしてください。
渡すと**採点基準がぶれます**（場面の文章に引っ張られて点が動く）。

### `context` を使い回さないこと

`context` は**影響型の実行結果**で既に使われています（4問）。
**新しい欄を足すこと**（例: `scenario`）。

### 既存の設問との重複

いまの設問は「このコードを実行すると何が出力されますか」で完結しています。
場面を足すと**設問と内容が重なる**ことがあります。
**場面は「なぜ読むか」、設問は「何を答えるか」**と役割を分けてください。

---

## 手順

1. 上の4点を決める
2. **マイグレーションで欄を足す**（例: `scenario text`。**NULL 可にすること**。既存101問が入っている）
3. 問題画面に表示する
   - `app/problems/[id]/page.tsx` の `select` に足す（**`prerequisite` の出し方が手本**）
   - **`model_answer` と `rubric_items` は渡さないままにすること**
4. **まず数問だけ書いて画面で見る**（②で案Aの場合）
5. `ideas/問題作成ガイド.md` に書き方と例を追記
6. `ideas/db仕様.md` に欄を追記
7. `npm run test:db` `npm test` `npm run build`
8. **スマホ幅（375px）で、コードに辿り着くまでの長さを確認する**

## 注意

- **場面を長く書かないこと。** 本題はコードを読むこと。**2〜3行**が上限
- **答えを場面に書かないこと。**「この関数はバグっているらしい」と書くと、
  読む前に結論を渡すことになります
- **絵を新規に描く判断は慎重に。** 101問ぶんは A2（101問作成）より大きい作業です
- **採点に渡さないこと。** `prerequisite` と同じ扱い
- **まず数問で試すこと。** 効果を見ずに101問書くと、やり直しが101問ぶんになります
