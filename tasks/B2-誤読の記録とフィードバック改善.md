## 何をするか

2つある。どちらも小さく、まとめてやるのが効率的。

### ① 「よくある勘違い」のどれに当たったかを記録する

問題ごとに「**言いがちだけれど違う読み方**」を登録してある。
例: 「900 が出力されると読んでいる」

AIには渡していて、判定にも使っている。**でも、どれに当たったかを受け取っていない。**
受け取って保存するようにする。

### ② 「どこを見ればいいか」を案内に必ず書かせる

いま読み違いを指摘するとき、
「もう一度上から追ってみてください」のような**場所を示さない案内**が出ることがある。
これでは何をすればいいか分からない。**行や式を必ず示させる。**

---

## なぜ必要か

**①は、問題の改善に使える唯一のデータになる。**

「この問題は、答えた人の3割が同じ勘違いをしている」と分かれば、
問題文が紛らわしいのか、そもそもよくある誤解なのかを判断できる。
いまはその材料が一切ない。

**②は体験の問題。** 間違いを指摘されたうえに、どこを見ればいいか分からないのは、
学習アプリとして最も避けたい状態にあたる。

---

## 手順

### ① 誤読の記録

1. AIの回答の形（`lib/ai/schema.ts`）に項目を1つ足す
   - `matched_reject`。値は「該当なし」か番号（`none` / `1` / `2` / `3`）
   - **必須項目として登録すること。** この仕組みは全項目が必須という決まりになっている
   - 型と検証（`parseDeepScore`）にも同じ項目を足す
2. AIへの指示（`lib/ai/prompt.ts`）に、番号で答えるよう追記する
3. 保存する（`app/api/score/route.ts`）
   - **データベースの変更は不要。** `axes` という欄が自由な形を入れられるので、そこに足す

### ② 案内の具体化

4. `lib/ai/prompt.ts` の指示文（`STATIC_PROMPT`）の feedback の節に追記
   ```
   読み違いを見つけた場合は、それに気づける具体的な箇所（行や式）を必ず示します。
   「もう一度追ってみてください」のような、場所を特定しない案内は書きません。
   ```

### 共通

5. `npm test` を通す
   - **指示文には内容を固定する検査がある**（`tests/unit/__snapshots__/prompt.test.ts.snap`）。
     意図した変更なので、確認したうえで更新する
6. ブラウザで実際に採点し、案内に場所が入っていることを確認する

---

## ⚠️ オーナーに確認すること

**基本的に判断は不要。** ただし1点だけ、作業中に気づいたら報告すること。

指示文を長くすると、**他の点数帯の文章が悪くなることがある。**
1つ直すと別が崩れる、という関係があるため。

> 案内に場所を示させる指示を足したところ、
> （合格圏 / 不合格圏）の文章が以前より（内容）になりました。
> このまま進めますか、それとも指示の書き方を変えますか。

判断がつかない場合は **B1（ゴールデンセット）の後に回してよい。** その旨を報告すること。

## 終わったと言える条件

- [ ] わざと「よくある勘違い」の回答をして、`user_attempts` の `axes` に番号が記録される
- [ ] 該当しない回答では「該当なし」が記録される
- [ ] 読み違いを指摘する案内に、**具体的な場所（行や式）が入っている**
- [ ] `npm test` と `npm run build` が通る

---

## 注意

- **指示文の先頭部分を書き換えないこと。**
  この部分は全ての採点で同じ文章を送ることで、外部AIの費用を大幅に下げている（実測で97%削減）。
  **追記は末尾に寄せる。** 途中に差し込むと、それ以降が節約の対象から外れる
- **採点の点数の計算式は変えない。** 記録を増やすだけのタスク
