**種別:** 判断 + 外部サービス設定

## 何をするか

**Ferret 専用のドメイン（`〇〇.com` のような住所）を1つ用意して、2か所に登録する。**

1. **Resend**（メール送信）に登録 → 確認メールが**誰のアドレスにも届くようになる**
2. **Vercel**（公開先）に設定 → 本番URLがそのドメインになる

---

## なぜ必要か

**いまの状態では、iCloud を使っている人が登録できない。** 2026-08-17 に実測して分かった。

C1 では、送信元として Resend が用意しているお試し用アドレス（`onboarding@resend.dev`）を使った。
仕組みは全部動いた（送信・日本語の文面・リンクからのログイン）。**ただし実際のアドレス宛に送ったら拒否された。**

```
宛先 rikuto042700@icloud.com  →  Bounced
理由 Blocked due to content: The message was rejected because it contained
     content that the recipient's server doesn't allow.
```

原因は2つあり、**デプロイで消えるのは片方だけ。**

| 原因 | どうなるか |
|---|---|
| リンクが `http://localhost:3000` を指している（暗号化なし・外から到達できない宛先） | **デプロイで解決する見込み。** `https://` の本番URLになれば、この引っかかりは消える |
| 差出人が共用のお試しドメイン | **デプロイでは解決しない。** Resend でのドメイン認証が必要 |

2つ目が残る理由。メールが本物かどうかは**差出人ドメインの持ち主が送信を許可しているかをDNSで照合して**判定される。
`resend.dev` は Resend の共用ドメインで、Ferret として認証されたものではない。
Resend 公式も「送信にはドメインの追加と認証が必要」と明記している。
**今回 iCloud まで到達したのは、宛先が Resend アカウントの持ち主本人だったからで、他人のアドレス宛は Resend 側で止まる可能性が高い**（未検証）。

> **`*.vercel.app` では代用できない。** Resend の認証にはDNSを触る必要があり、`vercel.app` は Vercel のものなので触れない。

---

## ⚠️ 着手前にオーナーに確認すること

> **ドメインを1つ取得する必要があります。費用は年 1,000〜2,000円程度**（`.com` や `.dev` の相場）。
> これは Ferret を公開するなら避けられない出費です（プロダクトのURLも同じものを使います）。
>
> 決めていただきたいのは2点です。
>
> **1. どの名前にするか。** `ferret.io` のような短い名前は既に取られているか高額なことが多いので、
>    実際に空いているものから選ぶ形になります。候補の空き状況は調べられます
>
> **2. どこで取得するか。** Cloudflare / Google Domains（Squarespace）/ お名前.com など。
>    **Cloudflare が最安に近く、DNSの設定画面も分かりやすい**のでおすすめですが、
>    すでに使っている業者があればそちらで構いません
>
> 名前は**あとから変えると、メールの差出人・本番URL・Supabase の設定を全部やり直す**ことになります。
> 決めるときは慎重に。逆に、決まれば作業自体は30分ほどです。

## 手順

1. ドメインを取得する（上の確認で決めたもの）
2. **Resend にドメインを登録する**
   - Resend → Domains → Add Domain
   - 表示される3行（DKIM / SPF 相当）をドメインのDNS設定に貼る
   - `Verified` になるまで待つ（数分〜数時間）
3. **Supabase の送信元を変える**
   - Project Settings → Authentication → SMTP Settings
   - Sender email を `noreply@<取得したドメイン>` に変更（Sender name は `Ferret` のまま）
4. **Supabase の URL 設定を本番向けにする**（C5 と重なる部分。順番はどちらでもよい）
   - Authentication → URL Configuration → Site URL を `https://<ドメイン>` に
   - `additional_redirect_urls` に開発用（`http://localhost:3000`）を残す
5. **確認メールの文面を再反映する**
   - `node supabase/templates/apply.mjs`（`supabase/templates/README.md` 参照）
   - **これで C1 で残した件名の日本語化も同時に片付く**（スクリプトに入っている）
   - 実行には Auth の**書き込み権限**を含む Personal Access Token が必要
6. **`supabase/config.toml` の `site_url` / `additional_redirect_urls` を本番URLに直す**
   - ここまでやれば `supabase config push` が安全に使えるようになる（いまは実行禁止）
7. **実配信を確認する**
   - **iCloud のアドレスで登録して届くこと**（今回弾かれた経路。ここが本題）
   - Gmail でも届くこと
   - **迷惑メールフォルダに入らないこと**

## 触る場所

| 場所 | 何をするか |
|---|---|
| ドメイン取得業者の管理画面 | 取得・DNS設定（3行） |
| Resend（Domains） | ドメイン登録・認証 |
| Supabase（SMTP Settings） | Sender email の変更 |
| Supabase（URL Configuration） | Site URL の変更 |
| `supabase/config.toml` | `site_url` / `additional_redirect_urls` |
| `supabase/templates/apply.mjs` | 実行するだけ（変更不要） |

**アプリのコードは変更しない。** 文面のリンクは `{{ .SiteURL }}` を見ているので、Site URL を変えれば追随する。

## 注意

- **DNSの反映は待ち時間がある。** `Verified` にならないうちに送っても改善しない。焦って設定を変え直さないこと
- **`onboarding@resend.dev` に戻さないこと。** 動作確認用の暫定手段であって、公開状態では使えない
- 送信元を `noreply@` にする場合、返信は届かない。問い合わせ導線は C2（法務文書）で決める
