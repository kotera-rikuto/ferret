## 上限に達したときの扱い（設計上の要点）

**「不合格」にしてはいけない。** ここが一番間違えやすい。

上限に達したら、AIによる採点（80点分）をやめて、
キーワードによる採点（20点分）だけで返す。

ところが**キーワードだけでは最大20点で、合格ライン55点に届かない。**
そのまま扱うと、上限に達した人の画面に**理由の分からない不合格が並ぶ。**

なので **「判定保留」** として扱う。

- `is_provisional` を `true` にして保存する
- `scoring_method` に `keyword_only` と記録する
- **クリア状況の計算からは除外する**（すでにそう作ってある）
- 画面には「きょうの採点回数を使い切りました」と出す

## 作業記録

### 2026-08-22 — 完了（ただし**プラン別にはしていない**）

**オーナー判断:** 課金を入れると別の問題が出ると分かったので、**いまは全員一律の使用制限**にする。
つまりこの票の「Free 1日3問 / Pro 月200問」は**採らなかった。** プラン別にするのは D2 の作業。

やったことは「商品の線引き」ではなく「**いっぱい採点させる攻撃を止める栓**」。
そのため票の手順とは何か所か違う判断をしている。理由は下に全部書いた。

#### 入れたもの（4層）

```
④ OpenAI 管理画面の使用量上限     ← **未設定。金額の天井はここだけ**（残タスク.md §C-4）
   └─ ① 全体で1日 500回          ← 新規。**アカウント量産に効くのはこれだけ**
        └─ ② 1人1日 20問（JST）   ← 新規。商品としての上限ではない
             └─ ③ 既存の安全網（1分10 / 1時間60 / 24時間300）← 触っていない
```

- **①が要る理由。** 登録はブラウザから Supabase Auth へ直行するので、アプリ側から
  「1人が何アカウント作ったか」は分からない。②をいくら下げてもアカウント数を掛ければ原価は伸びる。
  ①があれば何アカウント作られても1日の支出は動かない。**この票には無かった観点。**
- **20問の根拠。** 原価は1回 約¥0.04 なので1人1日 ¥0.8。全100問を5日で走り切れる量。
  **3問にはしない** ── 課金前のいまは商品の線引きではないので、訓練が成立しない高さまで下げる理由がない。
- **500回の根拠。** 最悪 1日 ¥20〜40。環境変数で上げられる（`AI_SCORING_DAILY_LIMIT_GLOBAL`）。
  上げ忘れると全員が「混み合っています」になるので、**発動時は `console.error` に出す。**

#### 票の手順と変えたところ（4つ）

**① `ideas/db仕様.md` の「レート制限のクエリ」は使わなかった。**
票は「すぐ使える完成品がある」と書いていたが、あの方式では上限を守れない。

- `count → 判定 → 採点` が不可分でない。**並列で来たリクエストは全部が同じ古い件数を読んで通る。**
  Vercel は同時に複数インスタンスが動くので、`route.ts` の `inFlight`（プロセス内の `Set`）では止まらない
- **行の数は採点の回数ではない。** 解放用に入れた行（`problems/unlock-seed.mjs`）は
  `scoring_method = 'ai'` なので数えてしまい、逆に**採点が失敗すると行が作られない**ので数えない
  ── つまり失敗を誘発するループはタダで OpenAI を叩ける

代わりに専用の表 `ai_usage_daily` と関数 `consume_ai_quota` を作った
（`supabase/migrations/20260822174900_ai_usage_daily.sql`）。
**要点は `for update`（行ロック）だけ。** 全体行 → 本人行の順にロックを取り、
両方が上限未満のときだけ両方を +1 する。順序を固定しているのはデッドロック回避。
**同時に20本投げて上限3ならちょうど3本しか通らないことを実DBで確認した**（`I-682`）。

**② 上限に達した回はリザルト画面へ遷移させない。**
票の手順どおりに「判定保留で保存 → リザルトへ」を作ると**無限に跳ね返される。**
`app/result/[id]/page.tsx` は `is_provisional = false` で絞ったうえで
「行が無ければ問題画面へ戻す」ので、保留の行しかない問題のリザルトは必ず問題画面へ戻る。

なので **429 + `code: "quota_exceeded"`** で返し、`ProblemForm` がその場に案内を出す。
既存の `!res.ok` の経路がそのまま使えるので、回答も下書きも残る。
赤いエラー表示とは別の枠にしてある（上限は失敗ではないため）。

**③ 失敗したときに枠を戻すかは、失敗の種類で分けた。**
票は「採点できなかったら消費させない」としていたが、**全部戻すと穴になる。**
失敗を誘発できる入力を持った相手が、枠を消費せずに何度でも OpenAI を叩ける
（`scoreAnswer` は内部で1回リトライするので1回の失敗で最大2回課金）。

| 失敗 | 枠 | なぜ |
|---|---|---|
| OpenAI が 429 / 5xx | **戻す** | トークンが1つも課金されていない |
| 応答は返ったが使えない（JSON 壊れ・スキーマ違い・refusal） | 戻さない | 課金済み |
| タイムアウト | 戻さない | 課金されたか判定できない（安全側） |

判定は `lib/ai/scorer.ts` の `isUnbilledFailure`（新設）に置いた。
429 / 5xx を `api_unavailable` という別のコードにして、呼び出し側がコード名を直接比べないようにしてある
── 失敗の種類を増やしたときに片方だけ直って静かに枠を返すのを防ぐため。

**④ 残数の表示は肉球3つにしなかった。**
モック（`design/stages-desktop-light.html`）の肉球は **Free 1日3問の前提**。
一律20問だと粒が並ばないので、レベル・すすみぐあいと同じバーにした。
`peek_ai_quota` を通して**強制と同じ値・同じ日付の決め方**を読んでいる。
右レールの「AI 採点 月200問」は、プラン別の上限が無いいまは嘘になるので文言から外した。

#### 権限まわり（レビューで見てほしい点）

**Postgres は関数の EXECUTE を既定で PUBLIC に配る**（Supabase の既定権限では `anon` / `authenticated` にも付く）。
取り上げないと、ブラウザの anon キーから `consume_ai_quota(<他人の id>, 1, 1)` を叩いて
**他人の枠を焼ける**（全体行を膨らませれば全員を止められる）。マイグレーションの末尾で `revoke` している。

関数は `security definer` に**していない**。表は RLS 有効・ポリシー0件なので、
万一 EXECUTE が漏れても INSERT が RLS で拒否されて例外になり、**通す方向には倒れない**。
definer にすると、その場合に「他人の枠を焼ける関数」になる。

#### 「数えない」の申し送りへの回答（残タスク.md §D-1 の問い）

**安全網（`RATE_LIMITS`）の数え方は揃えない。** あちらは行の数を数える連打のブレーキで、
判定保留や手で入れた行まで含めて多めに当たる。多めに当たるのは安全側。
**判定保留の行を作る連打を止めているのはあちらだけ**なので、緩めると別の穴が開く。

#### 実測で見つかって直したこと（返却の非対称）

**`refund_ai_quota` が、本人の行が無い（または既に0）ときでも全体の行だけを減らしていた。**
実DBのテスト（`I-685`）で踏んだ。

全体の行はサービス全体の使用量なので、これが減ると
**その日に流せる採点の総数が実際の消費より増える** ── 天井が静かに上へずれる。
二重返却でも同じ向きに崩れる。**上限の実装で一番避けたい向きの壊れ方。**

`supabase/migrations/20260822184000_refund_ai_quota_symmetric.sql` で
「本人の行が実際に減ったときだけ全体も減らす」に直した（ロック順は consume と同じ「全体 → 本人」を維持）。
`I-685` は「1回取って2回返しても、減るのは1回ぶんだけ」まで見るようにした。

**モックのテストでは絶対に出なかった。** 実DBに繋ぐ §13-6 を書いた価値はここに出た。

#### E2E との関係（入れておいた対処）

E2E は L2 スタブなので費用は出ないが、**`/api/score` を通るので枠は本物を消費する。**
そのまま回すと2つ困る。

1. 1回の実行で採点が20回を超えると、以降が「判定保留」になって
   **落ちるのは上限のテストではなく採点・リザルト・ふりかえりの全部**になる
   → `playwright.config.ts` の dev サーバーに大きな上限を渡した
2. **E2E を回すほど本番の1日500回が削られる**（天井は本物）
   → `clearAttempts` が使った回数ぶん `refund_ai_quota` を呼んでから行を消す（`clearAiUsage`）

#### ⚠️ 取り込む順番（**この順で実施済み**・2026-08-22）

**`supabase db push` を先に。`main` へのマージは後。**

`main` に push すると Vercel が自動で公開する（C5）。DB に関数が無い状態でこのコードが本番に出ると、
`consume_ai_quota` の rpc がエラーになり **`/api/score` が全リクエストを 503 で止める**
（数えられないときは通さない設計なので、**通る方向には倒れないが採点は全部止まる**）。

マイグレーションは**追加だけ**なので、いまの本番コードに影響しない（誰も呼んでいない関数と表が増えるだけ）。
だから **先に適用しておくのが安全側。** 順番はこの一択。

1. `supabase db push`（この worktree から）
2. `npm run test:db` で §13-6 が緑になることを確認 ── **`I-682`（同時20本で3本だけ通る）が本番のDBで効いている証明**
3. `main` にマージ → 自動公開
