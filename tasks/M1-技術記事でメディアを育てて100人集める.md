# M1. 技術記事でメディアを育てて、まず100人集める

**種別:** マーケティング（判断と継続作業が主。コードはほぼ触らない）
**規模:** 特大（複数セッションに分ける前提。**続けることが本体**）
**前提として終わっていること:** **C5（本番デプロイ）必須。** 登録できないサイトに人を呼んでも意味がない
**関連:** **M2（LPページ）**とセットで効く。集めた人の着地点が必要

**先に読むもの**
- `ideas/仕様書.md` の「ターゲット」「コアコピー」（**誰に向けて何と言うかが決まっている**）
- `ideas/需要分析.md`（どの訴求が刺さると分析したか）
- `ideas/問題構成案.md`（記事の題材はここから取れる）

---

## 何をするか

**Qiita / Zenn のような技術プラットフォームで記事を書き、Ferret を知ってもらう。**
最初の目標は **登録ユーザー100人**。

---

## なぜ必要か

**100問できても、誰も知らなければ使われない。**

いまの状態は「作ったが、存在を誰も知らない」。
そして**Ferret は使ってもらわないと改善できない。** 採点の精度も、問題の難易度も、
実際の回答が集まらないと判断できない。

異議申し立ての仕組み（`problem_feedback`）も、人がいないと材料が集まらない。

**100人という数字の意味:** 統計的に意味のあるフィードバックが返ってくる最小ラインとして。
「有料ユーザー100人」ではなく**「登録100人」**なので、無料のままでよい。

---

## ⚠️ オーナーに確認すること（このタスクは判断が主）

> 集客の方針を決めてください。**書き始める前に決めないと、記事の内容がぶれます。**
>
> **① 誰に向けて書きますか**
> 仕様書では **新人エンジニア（新卒〜2年目）** が主軸、需要分析では
> **「3年目のほうがペインが強い」**と指摘されていて、**ここが未解決の論点として残っています。**
> 記事の書き方が変わるので、どちらに寄せるか決めてください。
>
> **② 記事の路線をどうしますか**
> - **案A: 技術記事として書き、Ferret はさりげなく出す**（おすすめ）
>   例「他人のコードを読む練習を100問作って分かったこと」「AI採点の点数がブレる問題をどう測ったか」
>   - よい点: **技術プラットフォームは宣伝を嫌う。** 中身のある記事なら読まれる
>   - このプロジェクトは**書ける題材が異常に多い**（採点設計・プロンプトの穴・引用照合など）
> - 案B: サービス紹介記事を書く
>   - **反応が悪いことが多い。** 「宣伝」と見なされる
>
> **③ AI にどこまで書かせますか**
> 下書きはAIで作れます。ただし**そのまま出すと読まれません。**
> 技術記事は「実際にやった人の話」が価値なので、**実測値と詰まった点を必ず自分の言葉で入れる**必要があります。
> このプロジェクトには `tasked/` に実測値と判断の理由が大量に残っているので、**題材には困りません。**
>
> **④ 効果をどう測りますか**
> いま**アクセス解析が入っていません。** 記事から何人来たか分からない状態です。
> - 案A: 先に簡単な解析を入れる（Vercel の機能で足りる可能性あり）
> - 案B: 登録ユーザー数だけを見る（雑だが費用0）
>
> **⑤ どのくらいの頻度で書きますか**
> **続けることが本体**です。月1本を半年より、週1本を1ヶ月で止めるほうが効果が薄い。
> 無理のない頻度を決めてください。

## 手順

**1記事＝1セッションを目安にする。**

1. 上の5点を決める
2. **書ける題材の一覧を作る**（`tasked/` の作業記録から拾う。すでに素材がある）
   - このファイルの末尾に一覧として残し、書いたものに印を付けていく
3. 1本書く
   - 実測値・詰まった点・判断の理由を入れる
   - **Ferret へのリンクは記事の価値を損なわない位置に置く**
4. 出す
5. **反応を記録する**（閲覧数・登録に繋がったか）— このファイルの末尾に
6. 次の1本へ

## 注意

- **公開前に書き始めないこと。** 登録できないサイトに人を呼ぶと、その人は二度と来ない
- **宣伝色を出しすぎないこと。** 技術プラットフォームでは逆効果になる
- **平日日中の投稿は、勤務先から見える可能性がある**（リポジトリのコミット時刻と同じ論点）。
  副業の届出の状況を確認したうえで判断すること
- 記事に**問題の答えを書きすぎないこと**。ただしリポジトリは公開なので、隠す前提では書けない
- **AI が書いた文章そのままは読まれない。** 実体験の部分は自分で書くこと

**冒頭「オーナーに確認すること」の5点は、以下で決着した。ここが正。**

### メディア ── Zenn 単独

**Zenn だけで始める。** GitHub 連携（`articles/*.md` を push）で投稿する。

| 記事の型 | Zenn の `type` | 狙い |
|---|---|---|
| **「作った側」の技術記事** | `tech` | 読まれること・信用。素材が `tasked/` に大量にある |
| **「読者の痛み」に当てる記事** | `idea` | 登録に直結。手元に作業記録がない題材 |

**両方 Zenn に出す。** 媒体を分けないので、記事は1か所に集約される。

#### はてなブログを2媒体目に足す案は見送った

**検証した事実（2026-08-23。実際の HTML を見て確認）**

| | 本文中の外部リンク |
|---|---|
| **Zenn** | `rel="nofollow noopener noreferrer"` が**自動で付く**（本文中の記事リンクにも付く） |
| **はてなブログ** | **rel を付けない＝follow のまま**（nofollow が付いていたのは筆者が自分で付けたアフィリエイトリンクだけ） |

**つまり「Zenn からのリンクは票にならない」は事実で、はてなブログなら票が渡る。** それでも見送った理由:

1. **被リンクはインデックスの必須条件ではない。** C8 の記録どおり Googlebot は既に来ていて
   「クロール済み - インデックス未登録」＝**発見はされている。** 載らない理由は
   **公開ページが実質1枚しかないこと**で、C8 自身が「索引に載るのは実質トップページ1枚」と書いている
2. **新規のはてなブログ自体が評価ゼロ**なので、渡せる票がほぼ無い
3. **1本目を出す前に運用を2倍にすると、このタスクが一番失敗しやすい形になる**
   （タスクファイルの「週1本を1ヶ月で止める」）

**効き方の順序:** 自ドメインにページを増やす ≫ follow の被リンク（はてな） > nofollow の被リンク（Zenn）。
nofollow でも発見には効く（2020年3月以降 Google は nofollow を「ヒント」扱い）。

**Google に載せたいときの本当の手は `ferretcode.com` に記事を置くこと。** 被リンクを他人に依存せず、
インデックス対象そのものが増え、記事も1か所に集まる。ただしこれは C8 末尾の
**「公開側にコンテンツを置く判断＝料金プランと直結する事業判断」**なので M1 の範囲外。

**見直す条件:** Zenn で3〜5本出した時点で `site:ferretcode.com` を確認する。
**載らないままなら「自ドメインに記事を置く」を検討し、はてなブログはその代替案として比べる。**

#### 確認済みの Zenn 仕様（Skill を組む前提。2026-08-23）

| | |
|---|---|
| frontmatter | 必須 = `title` / `emoji`（1文字）/ `type`（`tech` \| `idea`）/ `topics`（最大5）/ `published`。任意 = `published_at`（`YYYY-MM-DD hh:mm`・JST） |
| slug | **ファイル名が slug。12〜50字・`a-z0-9` と `-` `_` のみ。** そのまま URL になる |
| 連携 | リポジトリは**最大2つ**まで。登録ブランチへの push / PR マージでデプロイ。**削除はダッシュボードからのみ**（Git から消すだけでは復活する） |
| canonical | **frontmatter に項目が無く、公開 HTML にも反映されない**（要望は 2020 年から出ているが未実装）。他媒体との重複を打ち消す手段が無い |

**M1 は「記事を書く運用」ではなく、まず「記事を出すパイプライン」を作る。**

1. **M1-0 メディア選定** ── ✅ 完了（Zenn 単独）
2. **M1-2 題材の棚卸し** ── ✅ 完了（2026-08-23）。`tasked/` 30本・7,728行から **73本**。下の一覧
3. **M1-1 Skill を作る** ── ✅ 完了（2026-08-23）。`.claude/skills/article/`。下の「作った道具」
4. **M1-3 1本出して Skill を直す** ── ✅ **完了（2026-08-23）。1本目を公開した。**
   **初回で実際に Skill を3回直した**（Ferret の紹介を必須化 / 型4「実物の数値」の新設 /
   自分で書いたルール3つの訂正）
5. **M1-4 2本目以降** ── **次はここ。** 前回と違う群から選ぶ（1本目は A 群だったので B〜G から）

**入力は2モードのスイッチを持つ。**

| モード | 使う場面 | 中身 |
|---|---|---|
| **素材引き（既定）** | `type: tech` の記事 | 短文（例「Embedding を廃止した話」）を打つと、`tasked/` の該当記録から**実測値・詰まった点・判断の理由**を拾って構成と骨組みにする。**実体験の段落は空欄で残し、本人が埋める** |
| **膨らませ** | `type: idea` の記事 | 手元に作業記録が無い題材（読者の痛み系）で使う |

**⚠️ 膨らませモードは既定にしない。** タスクファイル ③ の「AI が書いた文章そのままは読まれない」は、
このモードにそのまま当たる。素材引きなら文字数は実測値から出てくるので水増しにならない。

**Skill の置き場所:** `.claude/skills/article/`。**`.gitignore` に `/.claude/skills/` を足す。**
本体は公開リポジトリなので、「AI に下書きを書かせている」手順書が Zenn の読者に見える状態は、
技術記事の説得力を自分で削る。`.gitignore` はすでに同じ理由で事業文書を除外しているので方針も揃う。

##### 文体の3つの型（`reference/style.md`・オーナー指定・2026-08-23）

| 型 | 中身 |
|---|---|
| **型1 冒頭の5行** | 最初の3行で**読者の内心を代弁**する（体言止め・短文でよい）。4行目以降で**得られるものを1文。** 全体5行以内。**`近年` / `昨今` / `〜が注目されています` で始めない** |
| **型2 視点** | 「自分でやってみた人」として書く。**敬語は維持したまま評論をやめる** ──「〜が重要です」「〜が期待できます」を体験に置き換える。**1箇所は「正直なところ」「意外だったのは」を入れる** |
| **型3 リズム** | ときどき**1行だけの短い文**（30字以下の段落が 5〜22%）。読者への問いかけは0〜2箇所。箇条書きは7連続から気にする。同じ接続詞を2段落続けない |
| **型4 実物の数値** | **太字は 1000字あたり3個未満**（ここがいちばん効く）／コードブロック4個以上／外部リンク4個以上／h2 は 1000字あたり2.5個未満／本文4,000字以上 |

##### 型4 の根拠（2026-08-23・Zenn の人気記事30本を取得し5本を精読）

| 指標 | 実物5本 | 1本目の初稿 | 書き直し後 |
|---|---|---|---|
| **太字 / 1000字** | **0.0〜2.8**（226♥と70♥は **0**） | **8.8** | **0.0** |
| コードブロック | 4〜19個 | 1個 | 7個 |
| 外部リンク（ユニーク） | 4〜8個 | 1個 | 4個 |
| h2 / 1000字 | 0.55〜1.96 | 3.16 | 2.25 |
| 字数（コード除く） | 4,076〜16,453 | 2,848 | 3,997 |
| 段落の長さ中央値 | 65〜123字 | 54字 | 63字 |

**太字の密度が最大のズレだった。** 上位2本は `<strong>` を1つも使っていない。

**⚠️ 測ったら、自分で書いたルールが3つ実物と合っていなかった**（`style.md` に訂正を残した）。

| ルール | 書いていたこと | 実測 |
|---|---|---|
| 冒頭 | 「見出しの前に5行」 | **5本中3本が `## はじめに` から始まる。** 見出しの前かは問わない |
| 短い段落 | 「3段落に1回」＝33% | **実物は 5〜22%。** 2倍以上を要求していた |
| 箇条書き | 「3つ以上続いたら補足」 | **実物の最大連続は6。** 4連続は普通 |

⚠️ **リンク数を HTML から測るときは見出しのアンカーを除く。** Zenn は見出しごとに
`<a class="header-anchor-link">` を入れるので、`<a` を数えると見出しの数が混ざる
（実測で 16〜54 と出たが、実際の本文リンクは 8〜30・外部URLは 4〜8）。
**測り直す手順は `style.md` の末尾にある**（`zenn.dev/api/articles?order=liked_count`）。

**⚠️ 型に当てるために事実を曲げない。** 入れる主観が無いなら、その題材はまだ書けていない
（`tasked/` の「詰まった点」を読み直す）。**「意外だったのは」を入れるために意外でなかったことを
意外だったように書くのは、実測値を丸めるのと同じ。**

##### 分担の決定（2026-08-23・オーナー判断）

**主観と問いかけも AI が書いてよい。記事の末尾に「AI に書かせている」と書く案は採らない。**
理由は「AI っぽい文章は大抵の人が見分けるが、人間らしく整えたものは見分けられない」から。
担当（AI）が「擬装になりうる」という懸念と、人が書く分担にする代案を出したうえでの判断。
**経緯は `.claude/skills/article/reference/style.md` の「分担についての決定」に残してある。**

**Zenn の規約では問題にならない**（`https://zenn.dev/guideline` を 2026-08-23 に確認）。
**生成AI の使用は許可されていて開示の義務も無い。** 禁じられているのは
**①内容の正確性を確認せずに投稿すること ②記事を乱造すること**の2つだけ。

| Zenn が禁じていること | Skill 側の担保 |
|---|---|
| 正確性を確認せずに投稿 | **数字は `tasked/` の原文から写す。無い数字は書けない数字** |
| 乱造 | 1記事＝1セッション・前回と違う群を選ぶ・**週1本を上限の目安に** |

**つまり規約が求めているのは「事実を曲げないこと」で、文体の整え方ではない。**

**`.gitignore` に `/.claude/skills/` を追加済み**（`git check-ignore` で確認）。

**`check.mjs` が見るもの**（機械で決まることだけ。面白いかは見ない）

| | 落とす / 警告 |
|---|---|
| slug が 12〜50字・`a-z0-9-_` のみ | 落とす |
| frontmatter の必須5項目（`title` / `emoji` 1文字 / `type` / `topics` 最大5 / `published`） | 落とす |
| **読者を指して低く言う語**（初心者・弱点・苦手・理解不足・〜レベルの人） | 落とす |
| **非公開ファイル名がそのまま出ている**（`採点システム_残課題` など） | 落とす |
| **本人が書く箇所が空欄のまま残っている** | 落とす |
| `published: true`（この push で公開される） | 警告 |
| 金額の表記 ── 原価の実測値（¥0.04）は公開済みなので可、プランの価格は不可 | 警告 |
| ゴールデンセットの件名（`G05` など） | 警告 |

| 箇条書きが4項目以上続く | 警告 |

> ##### ⚠️ NG語はアプリのルールをそのまま持ち込まない
>
> `lib/ai/scorer.ts` の `NG_WORDS` には「失敗」「誤り」「間違い」「学習」が入っているが、
> **あれは画面と AI のフィードバック文への制約で、技術記事に当てると
> 「採点が失敗したら0点にしない」すら書けなくなる。**
> **記事で避けるのは、読者を指して低く言う語だけ** ── 主語がコードや処理なら使う、
> 主語が読者なら使わない。この線を `check.mjs` と `SKILL.md` の両方に書いてある。

### Chrome 操作は「投稿」ではなく「反応の回収」に使う

Zenn は Git 経路があるので、**投稿に Chrome を使う理由が無い**（DOM が変わるたびに壊れる。
「下書き保存」と「公開」を取り違えた事故は公開側に出る）。
