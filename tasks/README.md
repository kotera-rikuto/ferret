# tasks/ — 作業単位ごとの指示書

**このフォルダの使い方。**

Ferret の残作業を、**1ファイル = 1回のセッションで着手できる単位**に分けたもの。
セッションを始めるときは、このファイルで着手するタスクを選び、**そのタスクのファイルだけを読ませれば作業に入れる**ようにしてある。

---

## 作業する人（AIエージェント）へのお願い

### 1. 勝手に決めない

各ファイルに **「⚠️ オーナーに確認すること」** という節がある場合、
**そこはコードを書き始める前に必ず質問すること。** 黙って決めて進めない。

質問するときは、**専門用語を使わずに、選択肢とそれぞれを選んだ場合どうなるかを添えて**聞くこと。
オーナーは実装の細部まで把握しているとは限らないので、
「AとBどちらにしますか」だけでは判断できない。「Aにすると○○になり、Bにすると××になります」まで書く。

### 2. 前提のファイルを先に読む

各ファイルの冒頭に **「先に読むもの」** がある。ここに挙がっているものは着手前に読むこと。
書いていないものは読まなくてよい（読ませないために書いてある）。

### 3. 終わったら記録を残す

- そのタスクのファイルの末尾に、**やったこと・決めたこと・詰まった点**を追記する
- `残タスク.md` の該当項目にチェックを入れる
- **設計判断をしたら必ずその理由を残す。** 理由のない決定は、後で誰かが善意で元に戻す

### 4. 用語について

`何をするか` と `なぜ必要か` と `オーナーに確認すること` は**専門用語を避けて書く**こと。
`手順` と `触る場所` は正確さ優先でよい。

## 同時に複数のタスクを進めるときの決まり

> **複数を並行させるなら、まず [並列実行プラン.md](並列実行プラン.md) を見ること。**
> 衝突しない組み合わせを、バッチ単位（第1バッチ7本〜）にまとめてある。

タスクは分かれているが、**触るファイルは重なっている。** そのままだと後から衝突する。

### 守ること（3つ）

1. **1タスク = 1ブランチ。** `main` で直接作業しない
2. **着手する直前に `main` を取り込む。** 前のタスクの結果を持った状態から始める
3. **自分のタスクのファイル以外を「ついでに」直さない。** 気づいた点は
   そのタスクの `作業記録` に書いて、直すのは担当タスクに任せる

### 同時に進めてはいけない組み合わせ

**下の組は必ず順番にやること。** 同時に走らせると、後の人が手作業で直すことになる。

| 組み合わせ | 理由 | 順番 |
|---|---|---|
| **B2 ↔ B3** | 同じ指示文と、その内容を固定した検査を両方が書き換える | B2 → B3 |
| **B1 ↔ B2 / B3** | **測っている最中に採点基準が変わると、数字の意味が失われる** | B2 → B1 → B3 |
| **B1 ↔ A1 / A2** | 測っている最中に問題が増えると、前後の比較ができない | A → B1 |
| **A1 ↔ A2**、**A2 の章どうし** | どちらも問題を登録するため**表示順の番号が重複する** | 順番に1つずつ |
| **E7 ↔ E8** | どちらもマップの位置計算を作り替える | E7 → E8 |
| **E2 ↔ E6** | どちらもリザルト画面の点数まわりを組み替える | E2 → E6 |
| **E5 ↔ E9** | どちらも `app/globals.css` に色の定義を足す | どちらか先に |
| **Z1 ↔ B3 / F2** | Z1 は実装を写すので、**動いている最中に書くと書いた先から古くなる** | 実装 → Z1 |
| **C5 ↔ すべて** | 公開は「いまの `main` をそのまま外に出す」作業 | **単独で行う** |

### データベースの変更について

複数のタスクが `supabase/migrations/` にファイルを足す（C3・E2・E4）。
**ファイルが別なので衝突しない。** ただし次を守ること。

- ファイル名の日付は**作った時刻**にする（他のタスクと重ならない）
- **既存の行があるテーブルに「必須の欄」を足さない。** 追加する欄は必ず「空でもよい」形にする
- 適用の順番が入れ替わっても壊れない内容にする

## 動かし方（作業を始める前に）

### アプリを起動する

```bash
npm run dev
```

`http://localhost:3000` で開く。
**ポートが使われていると別の番号（3001、3002…）になる。** 起動時の表示で確認すること。

### ログインする

**トップ画面はログインが必要。** 開発用のアカウントがある。

```
メールアドレス: dev@ferret.test
パスワード:     FerretDev2026!
```

メール確認済みの状態で作られているので、そのままログインできる。

> ⚠️ **このパスワードは公開リポジトリに載っている。**
> ローカルで動かしている間は問題ないが、**公開（C5）の前に必ず変更し、
> `TASKS.md` と このファイルの両方から消すこと。**

### テストを流す

```bash
npm test              # 全部（実DBに繋ぐものは飛ばされる）
npm run test:unit     # 計算やロジックだけ。速い
npm run test:db       # 実DBに繋いで問題データの健全性を見る（問題を追加したら必ず）
npm run test:e2e      # ブラウザを自動で動かす
npm run lint          # 書き方の検査
npm run build         # 本番と同じ形で組み立てられるか
```

**どのタスクでも、最後に `npm test` と `npm run build` を通すこと。**

### データベースの中身を見る

Supabase の管理画面 → **SQL Editor** で直接見られる。
表の定義は `ideas/db仕様.md`。

### 採点を試すとき

**1回あたり約4円の実費がかかる。**（OpenAI の利用料）

- 何度も試すときは残高を確認しておくこと
- **同じ回答をもう一度送ると、前の結果をそのまま返す**（費用はかからない）。
  毎回本当に採点させたいときは、回答の文言を少し変えること
- 連続で叩くと使いすぎを止める仕組みに当たる（1分に10回まで）

  B2 B3 / E1 E2 E3 E5 E6 E7 E8 E9 / F2 / Z1

## 共通の決まりごと（全タスク）

`ideas/セキュリティ_残課題.md` §4 より。**新しく何か作るときは必ず守ること。**

- **認証が要る画面を追加したら** `proxy.ts` の `matcher` に追加する
- **問題に紐づく画面を追加したら** `lib/progress/unlock.ts` の `loadProgress` で解放判定する
  （画面と採点APIで判定がズレると、そこが抜け道になる）
- **新しい POST の API を作ったら** 先頭に `isCrossSiteRequest` と `hasJsonContentType` を置く
  （`lib/http/origin.ts`。`app/api/feedback/route.ts` が最新の手本）
- **ユーザーの入力を外部AIに送るなら** 個人情報の検査を通す（`app/api/score/route.ts` の `containsPii`）
- **DBを変えるときは** `supabase/migrations/` にファイルを足して `supabase db push`。手で管理画面から変えない
- **作業の最後に** `npm test` と `npm run build` を通す
