# 並列実行プラン（worktree 運用・3〜4本編成）

**作成: 2026-08-17。** `tasks/` の各タスクを、**同時に走らせても衝突しない組み合わせ**にまとめたもの。
衝突の根拠は `tasks/README.md` の「同時に複数のタスクを進めるときの決まり」。

---

## なぜ7本ではなく3〜4本なのか

**28タスクのうち22本が、オーナーの判断待ちになる**（判断不要は2本、軽微が4本）。

7本を同時に走らせると、**設計の質問が7個同時にあなたへ飛んでくる。**
エージェントはそこで止まるので、実際の進みは「あなたが何問さばけるか」で決まる。
ファイルの衝突より、こちらが先に詰まる。

もう1つ、**残りのUI系タスクが4ファイルに集中している。**

| ファイル | 奪い合うタスク |
|---|---|
| `app/result/[id]/ResultView.tsx` | E1 E2 E3 E6 E8 |
| `app/problems/[id]/page.tsx` | E4 E5 E8 G2 |
| `app/stages/page.tsx` | D1 D2 E3 E7 E8 |
| `app/api/score/route.ts` | B2 D1 E2 E3 G3 |

**各波でこの4ファイルから1本ずつしか取れない。** 増やしても待ちが増えるだけ。

## 運用の前提

- **`origin/main` から worktree を切って、1タスク = 1ブランチ = 1 worktree**
- **波（なみ）単位で進める。** 1つの波が全部 `main` にマージされてから、次の波の worktree を切る

```bash
git -C <repo> fetch origin
git -C <repo> worktree add ../ferret-E4 -b task/E4 origin/main
```

> **統合先は `main` 一本にする（2026-08-17 決定）。**
> 初版はここを `develop` と書いていたが、**`origin/develop` は存在しない。**
> ローカルの `develop` は main より遅れており、E4 を含んでいなかった
> （A1 で `origin/develop` から切ろうとして判明。`tasked/A1-読解型の検証.md`）。
> 実際に E4・F1・B2 が積まれているのは `main` なので、**実態に合わせて main を正とする。**
> 2本を同期し続ける手間を持たない、という判断でもある。

タスクは性質の違う3本の流れに分かれる。**各波は、各レーンから1本ずつ取る形になる。**

**レーン1 の A2（量産・特大）が最長。** ここに一番厚く人を割くのが、完了を早める唯一の方法。

## 波を終えるときの手順

1. 各 worktree で `npm test` と `npm run build` を通す
2. そのタスクのファイル末尾の `作業記録` に、やったこと・決めたこと・詰まった点を書く
3. `残タスク.md` の該当項目にチェックを入れる
3b. **タスク票を `tasks/` から `tasked/` へ移す**
3c. **このファイルを更新する** ← 忘れやすい
   - 完了した波を「✅ 完了」ブロックに畳む
   - **新しく起票したタスクを、どの波に入れるか決めて書き込む**
3d. **このファイルはすぐコミットすること。** 未コミットのまま置くと、
   作業ツリーを共有している別セッションが古い版で上書きして**更新が消える**（2026-08-18 に実際に発生）
4. `main` にマージして push する
5. **その波の全員がマージされてから**、次の波の worktree を切る
