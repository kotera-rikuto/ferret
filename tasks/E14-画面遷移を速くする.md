# E14. 画面の切り替わりを速くする

**種別:** 実装（調査が先）
**規模:** 中
**前提として終わっていること:** なし

> ### ⚠️ 同時進行の注意
> `app/stages/page.tsx` `app/problems/[id]/page.tsx` `app/result/[id]/page.tsx` と
> `proxy.ts` を触る可能性がある。**画面系タスクと同時に進めないこと。**

**先に読むもの**
- `proxy.ts`（**`getUser()` を使っている理由がコメントに書いてある。消さないこと**）
- `lib/progress/unlock.ts`（**すでに `Promise.all` で並列化されている**）
- `node_modules/next/dist/docs/` の該当ガイド（**このバージョン固有の作法がある**）

## 何をするか

**画面を切り替えたときに1秒以上「何も起きない」状態を無くす。**

**オーナーの報告（2026-09-12）:** 画面遷移が遅すぎる。1秒以上ラグがあって体験が悪い。

---

## 実測した事実（2026-09-12）

### ① `loading.tsx` が1つも無い ← **たぶんこれが主因**

```
find app -name 'loading.tsx'  → 0件
```

Next.js の App Router は、**この用意が無いとサーバー側の処理が終わるまで画面を切り替えません。**
その間ブラウザは**前の画面を出したまま**なので、**押しても何も起きない**ように見えます。

**実際に遅いこと**と、**遅いあいだ何も出ないこと**は別の問題で、
**後者のほうが体感に効きます。**

### ② 画面ごとに DB へ3回、順番に問い合わせている

| 画面 | 順に待っているもの |
|---|---|
| `/stages` | `auth.getUser()` → `loadProgress()` → 連続日数の集計 |
| `/problems/[id]` | `auth.getUser()` → `loadProgress()` → 問題の取得 |
| `/result/[id]` | `auth.getUser()` → 回答の取得 → XP の導出 |

**`loadProgress` の中はすでに `Promise.all` で並列**になっていますが、
**画面の側では3つが直列**です。

### ③ 1回の問い合わせに約0.2秒かかる（実測）

```
Supabase REST 1件取得: 1.17s（初回） / 0.22s / 0.22s
本番 LP:                2.13s（初回） / 0.48s / 0.64s
```

**0.2秒 × 3回 = 0.6秒**が、画面を描き始める前に必ず乗っています。

### ④ `getUser()` が遷移ごとに2回走っている

`proxy.ts` と各画面の両方が `auth.getUser()` を呼んでいます。
これは**セッションの有効性をサーバーに問い合わせる**ので、そのたびに通信が発生します。

⚠️ **`getSession()` に置き換えないこと。** `proxy.ts` のコメントに理由が書いてあります
（Cookie の中身を信じるだけになる）。**守りを弱めずに回数を減らす方法**を考えること。

## なぜ必要か

**押してから1秒以上「何も起きない」のは、壊れているのと区別が付きません。**

そして Ferret は**問題 → 採点 → リザルト → マップ**と画面を何度も行き来する作りです。
1回1秒でも、**1問解くたびに3〜4秒が待ち時間**になります。

登録の障害を下げる話（C13）をしている段階で、**触った人が最初に感じるのがこの遅さ**です。

### 直した内容

**A. 読み込み中の表示（`loading.tsx`）**

- `app/stages/loading.tsx` / `app/result/[id]/loading.tsx` を新設。
  中身は `components/ui/LoadingSkeleton.tsx`（`Bone` = 灰色の板 / `WaitingMascot`）。
- **マスコットは採点待ちと同じもの**（`MascotMotion motion="thinking"`）。
  「フェレットが考えている＝待つ場面」という結び付きは採点待ちで既にできているので、
  別の絵を出すと意味を二重に覚えさせることになる。
  リザルトでも**祝う動きは使わない** ── クリアしたかどうかはまだ分かっていないので、
  先に喜ぶ絵を出すと届かなかった回に「一度祝ってから取り消す」ことになる。
- `app/globals.css` に `--animate-skeleton` を足し、**`prefers-reduced-motion` の一覧にも登録した**。
  Tailwind 既定の `animate-pulse` を使わなかったのは、あれの `@keyframes` が
  `globals.css` に無く、**U-811（動きの止め忘れ検査）が見張ってくれない**から。
- ⚠️ **`Bone` に既定の `rounded-*` を持たせないこと。** 最初 `rounded-xl` を既定にしていたら、
  呼ぶ側の `rounded-full` と競合して**ステージの丸が角丸の四角で出た**。
  どちらが勝つかはクラスを書いた順ではなく生成された CSS の並び順で決まる。

**A'. `/problems` の押した直後の反応**

`loading.tsx` を置かない代わりに、`components/stage/StageMap.tsx` の
「挑む / もう一度読む」を `useTransition` で包んだ。**押すと 35 ms で文言が
「ひらいています」に変わり、押せなくなる**（実測。大きさは 220×53.5 のまま変わらないので、
ポップオーバーが動いて押し間違いになることはない）。
問題画面へは `<Link>` ではなく `router.push` で飛ぶので、`useLinkStatus` は使えない。

**B. 直列だった問い合わせを並列に**

- `app/stages/page.tsx`: `loadProgress` / つづけた日数 / 採点残数の3つは
  どれも `user.id` しか要らず互いの結果を使わないので `Promise.all` に。**4往復 → 2往復。**
- `app/result/[id]/page.tsx`: 最新の回答と XP 用の一覧を `Promise.all` に。**3往復 → 2往復。**
- `app/problems/[id]/page.tsx` は**触っていない。** ここは
  `getUser → 解放判定 → 問題の本文` が本当に順番に要る（前の答えで次を出すかどうかが決まる）。
  本文を先に投げて後から捨てる形にすると、**「未解放なら詳細を引きにすらいかない」という
  取り決め（I-376b）が壊れる。**

### 詰まった点

**E-723 が落ちるようになった**（`tests/e2e/preview.spec.ts`。**この票の変更が原因**）。

`loading.tsx` を置くと、ブラウザの `load` は**骨組みが出ている段階で発火する。**
そのとき**本物のマップはすでに DOM にいる**（React が隠したまま持っている）ので、
数え上げや `disabled` の判定は通るのに、**表示されていない。**
E-723 は「押せないボタンを押してもポップが開かない」を見るケースで、
`click({ force: true })` を使っている ── `force` は Playwright の待ち合わせを飛ばすため、
隠れているボタンを押しにいって `Element is not visible` で落ちていた。
実測すると `skeleton 22件 / circles 103件` が同時に DOM にいる状態を再現できた。

**直し方: 押す前に `toBeVisible()` を1行入れた。** `force` は外せない（押せないボタンを
押すのがこのケースの中身）。落ちていたのはこの1件だけで、他は `force` を使っていないので
Playwright が自分で待つ。

**`npm run test:e2e` で E-452 も落ちるが、これは前からのもの。**
問題 id 2588（ステージ70）のタイトルに「失敗」が入っている
（`lib/seo/site.ts` の `shareText` のコメントに「直すのは A2 側」と明記済み）。
**この票の変更前でも同じように落ちる**ことを確認した。

**`npx tsc --noEmit` は単体では通らない**（`@/public/*.png` が解決できない）。
`next build` が生成する型定義が要るので、確認は `npm run build` で行う。**この票の変更とは関係ない。**

### ③ 本番に反映した後（2026-09-12・PR #26 マージ後）

同じ手順で測り直した（`dev@ferret.test` で本番にログイン・実クリック）。

| | 前 | 後 |
|---|---|---|
| **問題 → ステージ選択**（押してから何か出るまで） | 1,305 ms | **62 ms**（先読みが済んでいるとき） |
| **リザルト → ステージ選択**（同） | ── | **284〜428 ms** |
| ステージ選択 → 問題（同・`loading.tsx` を置かない画面） | 1,312 ms | 1,071〜1,083 ms |

**⚠️ ただし「押した直後に骨組みが出る」は先読みが間に合ったときだけ。**
2回測って中央値が 62 ms と 977 ms に割れたので切り分けた（`.measure/prefetch.mjs`）。
問題画面を開いた**直後**に × を押すか、**2秒待ってから**押すかで揃って変わる:

| 押すまでの間 | 何か出るまで |
|---|---|
| 0 秒（先読みが終わっていない） | 240 / 385 / 415 ms |
| 2 秒（先読みが終わっている） | 48 / 52 / 59 ms |

**Next.js の仕様どおりの挙動。** `loading.tsx` を置くと行き先が「部分的に先読みできる」ようになり、
**先読みが届いていれば骨組みは即座に出る**が、届く前に押すとサーバーの返事を待つ
（`node_modules/next/dist/docs/01-app/01-getting-started/04-linking-and-navigating.md` の
「slow or unstable networks」の節。**対処として `useLinkStatus` が名指しで挙がっている**）。

**前の 1,305 ms と比べれば、最悪でも 3〜5分の1。** ただし
**混んでいるときほど先読みが間に合わない**ので、遅い時ほど無反応に近づく。

### やり残し・申し送り

- **`useLinkStatus` を足すと、先読みが間に合わなかったときも押した瞬間に反応が返る**（上記）。
  対象は `/stages` へ行く2本 ── 問題画面の × と、リザルトの「つぎのステージへ / ステージにもどる」。
  **`StageMap` の「挑む」で既にやっていること**（`useTransition`・35 ms で文言が変わる）の
  リンク版で、あちらは `router.push` なので別の仕組みになっている。**別票にするのが素直。**
- **`/stages` / `/problems/1` / `/result/10` の「最初の1バイト」は本番では 7〜8 ms で揃う。**
  Vercel がヘッダを先に流すためで、**`loading.tsx` の有無を見分けられない**
  （手元の `next start` では 6 ms と 369 ms に分かれる）。**本番の速さは実クリックで測ること。**
- `/problems` の**サーバー側**はまだ 335 ms かかっている。速くするなら
  `getUser` と「問題一覧の取得」を同時に投げる形になるが、**`loadProgress` の引数の形を
  変えることになる**（アクセス制御の中心なので、単独の票にしたほうがよい）。
- `lib/changelog.ts` に1件足した（`fix`・2026-09-12）。**日付は本番に反映した日**なので、
  merge が翌日以降になるならそこで直すこと。
