# F5. 保守性を上げる（カバレッジと品質確認の仕組み）

**種別:** 仕組みづくり（開発体制）
**規模:** 大
**前提として終わっていること:** なし
**関連:** F4（セキュリティレビューのエージェント）と目的が近い。**まとめて考えると設計が揃う**

**先に読むもの**
- `tests/README.md`（テストの分け方の方針）
- `tests/unit/テストケース.md` `tests/integration/テストケース.md` `tests/e2e/テストケース.md`

---

## 何をするか

いま**テストは701件あって全部通っている**が、次の2つが分からない。

1. **どこが試されていないか**（カバレッジを測っていない。`vitest` の coverage 設定が無い）
2. **人が触って確かめる観点が決まっていない**（毎回その場の判断で見ている）

この2つを仕組みにする。

---

## なぜ必要か

**1人開発で、これから公開して人に使われる段階に入る。**

いまは「テストが全部通っている」ことは分かるが、**通っていない場所がどこか分からない。**
テスト件数が増えても、肝心な経路が素通しなら意味がない。

とくに危ないのは、**採点・課金・認証**の3つ。ここは壊れると
「静かに間違った結果を返す」形になるので、テストが無いと気づけない。

人が触る確認（QA）も、いまは思い出しながらやっている。
**節目ごとに同じ手順で確認できる形**があれば、見落としが減る。

---

## ⚠️ オーナーに確認すること

> 保守性の仕組みについて決めることがあります。
>
> **① カバレッジの目標をどうしますか**
> - **案A: 目標は決めず、まず測って可視化するだけ**（おすすめ）
>   数字が見えるようになるだけで「ここが空いている」に気づけます
> - 案B: 数値目標を決めて、下回ったらテストを失敗させる
>   厳密ですが、**目標を満たすためだけのテストが増える**ことがあります。
>   1人開発だと、その手間が品質に直結しません
>
> **おすすめは案A**です。数字を強制すると「カバレッジのためのテスト」が増えて、
> かえって保守性が下がることがあります。まず空いている場所を知るのが先です。
>
> **② 全体で測りますか、大事な場所だけにしますか**
> - **案A: 採点・認証・課金の3つに絞る**（おすすめ）
>   壊れたときの実害が大きい順です。画面の見た目は E2E で見ているので重複します
> - 案B: 全部測る
>
> **③ 人が触る確認（QA）をどこまで形にしますか**
> - **案A: チェックリストを1枚作る**（おすすめ）— 公開前・大きな変更後に上から順に見る
> - 案B: エージェントに任せる（F4 と同じ作り方）
> - 案C: いまのまま
>
> **④ F4（セキュリティ）と一緒に作りますか**
> どちらも「観点を固定して繰り返す」仕組みなので、**まとめると形が揃います。**
> 別々に作ると出力の形が揃わず、読みにくくなる可能性があります。

---

## 手順

1. 上の4点を決める
2. **カバレッジを測れるようにする**
   - `vitest` の coverage を有効にし、`npm run coverage` のようなコマンドを足す
   - **既定のテスト（`npm test`）は重くしないこと。** 別コマンドにする
3. **測って、空いている場所を洗い出す**
   - 特に見るべき場所: `lib/ai/`（採点）・`app/api/`（サーバー処理）・`lib/auth/`・`lib/progress/`
   - **結果をこのファイルに記録する**（次に見た人が同じ場所を探し直さなくて済む）
4. **空いている場所のうち、実害の大きいものだけテストを足す**
   - ⚠️ **カバレッジの数字を上げるためのテストは書かないこと。**
     「壊れたら気づけない場所」を埋めるのが目的
5. **QA のチェックリストを作る**（決めた形で）
   - 公開前・大きな変更後に上から順に見る形
   - 既存の `tests/*/テストケース.md` と役割が重複しないようにする
     （あちらは自動テストの一覧、こちらは人が触る確認）
6. 使い方を `tasks/README.md` に足す

---

## 触る場所

| ファイル | 何をするか |
|---|---|
| `vitest.config.mts` / `package.json` | coverage の設定とコマンド |
| `tests/`（追加） | 空いている場所のうち実害の大きいもの |
| `tests/QAチェックリスト.md`（新規） | 人が触る確認 |
| `tasks/README.md` | 使い方 |
| `.gitignore` | カバレッジの出力先を除外 |

---

## 終わったと言える条件

- [ ] 4点についてオーナーの判断を得ている
- [ ] `npm run coverage` のようなコマンドでカバレッジが出る
- [ ] **既定の `npm test` が重くなっていない**
- [ ] 空いている場所の一覧がこのファイルに記録されている
- [ ] 実害の大きい箇所にテストが足されている
- [ ] QA のチェックリストがある
- [ ] `npm test` と `npm run build` が通る

---

## 注意

- **カバレッジは目的ではなく道具。** 数字を追うと保守性は下がる
- **既存のテストの分け方を壊さないこと。** 単体 / 結合 / E2E / 実DB接続 / ゴールデンで分かれていて、
  実DB接続とゴールデンは**費用や実データに触るので既定では走らない**設計になっている
- カバレッジの出力ファイルは**git に入れないこと**（実行ごとに変わるのでノイズになる）
