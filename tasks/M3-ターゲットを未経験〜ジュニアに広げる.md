**規模:** 判断込みで**中**（決まった後の作業だけなら**小**）
**前提として終わっていること:** **C12（AI向けの説明）** ✅済み・**M2（LP）** ✅済み

> ### ⚠️ 同時進行の注意
> `lib/seo/site.ts` と `app/page.tsx`（LP）を触る。**M1・C11 と同時に進めないこと。**
> **M1（技術記事）は、この票が決まってから次を書くほうがよい** ── 記事の書き出しが読者の想定で決まるため。

## なぜ必要か

### 読者像を決めないまま、もう作り始めている（2026-09-12 実測）

| | 状況 | この票との関係 |
|---|---|---|
| **M1**（技術記事） | **8本公開済み** | **9本目以降の書き出しが変わる。** 出したものは直さないが、**これ以上増える前に決めたほうが揃う** |
| **A4**（問題の場面） | **全100問に投入済み**（2026-09-12） | **書き直さない。** 100問ぶんの文章を、言い回しのために作り直す価値は無い。**次に問題を足すときの書き方の基準**として使う |
| **`lib/seo/llms.ts`**（AI向けの説明） | **対象者の記述なし** | AI に「誰向けのサイトか」と聞かれても答える材料が無い |

**A4 が終わっているのは、この票にとってむしろ都合がよい。**
場面の文章が既に100問ぶんあるので、**決めた対象者に本当に合っているかを、実物を見て確かめられる**
（想像で決めなくてよい）。

### 未経験者を入れるとどう有利か（オーナーの主張の整理）

1. **「他人のコードが読める」は目標の宣言であって、いま抱えている困りごとの描写ではない。**
   実務に入る前の人ほど「現場のコードについていけるか」を不安に思っている。
2. **お金を払ってでも実務に近い経験を積みたい、という需要が実在する。**
   （※ 実態が問題視されているサービス形態のことを指しているが、**Ferret はそれを真似るのではなく、
   まっとうな代替として同じ需要に応える**、という位置づけ）
3. **`需要分析.md` が新人を否定した根拠が、そのまま未経験者を推す根拠になる。**
   「会社の研修があるから自費で払わない」── **未経験者には会社が無い。**
   比較対象がスクールの受講料になるので、金額の見え方も変わる。

### 中身はすでに未経験者に届く作りになっている

| 済んでいる作業 | 効果 |
|---|---|
| **A3**（最初の数問をチュートリアル化） | 1〜3問目が素直な問題。難度 1→2→2 |
| **C13**（登録なしで読める） | ステージ1を登録前に見られる |
| **A4**（実務の場面）── **全100問に投入済み** | 「上司から頼まれた」の場面カードが全問に付いた |
| 問題の中身 | `const` と `let` から始まる。言語は JS/TS だけ |

**プロダクトは既に入口を広げていて、言葉だけが置いていかれている状態。**

## ⚠️ オーナーに確認すること（着手前に必ず）

### 判断1. 「誰向けか」をどう書くか（**これが本体**）

`M2` で「年次は書かない」と決めているので、そのままでは書けない。3つの書き方がある。

| | 書き方の例 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 状況で書く**（年次を出さない） | 「これから実務に入る人と、入って間もない人へ。」 | **過去の判断と衝突しない。** 読んだ人が自分を当てはめやすい | ぼやけて見える可能性 |
| **B. 年次で書く** | 「未経験〜実務2年目まで」 | はっきりする。検索にも効きやすい | **`M2` の判断を覆すことになる。** 当てはまらない人を弾く |
| **C. 何も書かない**（現状維持） | ── | 誰も弾かない | **M1・A4 が止まったまま** |

**勧めるのは A。** オーナーの言う「未経験の学習段階者〜ジュニア」は**年数ではなく状況の話**なので、
そのまま状況として書けば、過去の判断を覆さずに意図が伝わる。

### 判断2. 3年目を切ってよいか

`需要分析.md` は「**3年目のほうがペインが強い**」と書いている。
未経験側に寄せると、この層に向けた言葉は出さないことになる。

- **切る** → `ideas/需要分析.md` 1.5 に「2026-09-12 に不採用。理由は〜」と追記して決着させる
- **切らない** → 判断1は C（何も書かない）にするしかない。**M1 と A4 は止まったまま**

⚠️ **どちらを選んでも、`ideas/` の該当箇所に理由を書き残すこと。**
理由が無いと、後で誰かが善意で元に戻す。

### 判断3. コアコピーは変えるか

いま: **「他人のコードが読める、AI時代のエンジニアに。」**

**変えないことを強く勧める。** 理由は2つ。

- オーナー自身が「**これは目標の宣言**」と整理している。未経験者にもそのまま届く
- `lib/seo/site.ts` の `SITE_DESCRIPTION` の1文目で、**検索結果と AI の説明の両方に出ている**。
  変えると検索エンジンと AI が持っている説明を作り直すことになる（C12 で揃えたばかり）

**変えるなら「誰に向けているか」の1行を足すだけにする。**

### 判断4. 未経験者向けの案内を足すか

「プログラミングを触ったことがない人でも大丈夫か」は、未経験者がいちばん最初に気にする点。

- **足す** → LP の FAQ に1問足す（`app/page.tsx`）。**どこまでの前提知識が要るかを正直に書く**
  （※ 実際には `const`・`let`・`console.log` を知っている前提で問題が作られている。
  **まったくの未経験者ではなく、「学習中で実務未経験」の人が対象**になる）
- **足さない** → 現状維持

⚠️ **ここは事実確認が要る。** 「未経験者歓迎」と書くなら、**実際に1問目を開いて**
（場面カード → コード → 設問）解けるかを見てから書くこと。
記録は `tasked/A3-最初の5問をチュートリアルにする.md` と `problems/stage-001-003.md`。

## 手順

**判断1〜4 が決まってから着手すること。** 決まる前にコードを触らない。

### 1. 決めたことを社内文書に書き戻す（先にやる）

| ファイル | 直す場所 |
|---|---|
| `CLAUDE.md` | 「確定済みの意思決定」の**ターゲット**の行／「未解決の論点」から**ターゲット年次**を消す |
| `ideas/仕様書.md` | 決定1 と 2.1（ペルソナ）。**古い記述を消さず、日付付きで上書きの記録を残す** |
| `ideas/需要分析.md` | 1.5 に決着を追記（判断2の結果） |

### 2. 公開する文言に出す

**`lib/seo/site.ts` に定数を1つ足して、そこから配る**（散らさない・`CLAUDE.md` の決まり）。

```
lib/seo/site.ts        ← 新しい定数を1つ足す（例: TARGET_AUDIENCE）
  ├→ app/page.tsx      LP 本文
  ├→ SITE_DESCRIPTION  検索結果の説明文（※ 変えるなら判断3の結論に従う）
  ├→ lib/seo/llms.ts   AI 向けの説明の箇条書き
  └→ lib/seo/structured-data.ts   JSON-LD（`audience` を名乗れる）
```

⚠️ **4か所を別々に書かないこと。** 散らすと **AI が矛盾した説明のどちらかを事実として答える**
（画面を見ても気づけない ── C12 の理由と同じ）。

### 3. 検査を足す

`tests/unit/seo.test.ts` に、**LP と `/llms.txt` が同じ対象者を名乗っているか**を見る検査を1つ足す。
（手本は同ファイルの U-894 ── `SITE_IS_FREE` と画面の文言が揃っているかを見ている）

### 4. 更新情報に載せるか

**載せない。** `E12` の決まりで「画面から分かる変更」が対象だが、
**説明文の言い回しはユーザーにとって新機能ではない。**

### 5. 最後に

```bash
npm test && npm run build
```
