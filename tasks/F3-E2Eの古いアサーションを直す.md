# F3. ブラウザの通しテストが全部落ちているのを直す

**種別:** テストの修復
**規模:** 中
**前提として終わっていること:** なし
**起票:** 2026-08-17（F1 の作業中に発見。**F1 が原因ではない**）

> ### ⚠️ 同時進行の注意
> `tests/e2e/` を触るタスクは他に無いので衝突しない。
> ただし `next.config.ts` に1行足す可能性があるため、そこを触る作業とは順番にやること。

**先に読むもの**
- `tests/e2e/auth.spec.ts`（落ちている本体）
- `playwright.config.ts`（`baseURL` の設定がある）
- `tests/e2e/テストケース.md` の §1

---

## 何をするか

**`npm run test:e2e` が動いていない。** 認証まわりの7件が全部落ちる。直す。

---

## なぜ必要か

**3階層のテストのうち、一番外側が丸ごと死んでいる。**

単体・結合は 537件通っているが、これらは Supabase も OpenAI も差し替えた状態で動く。
**「ブラウザで実際に操作したら本当に動くのか」を見ているのは E2E だけ。**
ここが落ちたままだと、画面の作り替え（E1・E2・E5・E8 など）で
壊れても誰も気づけない。

もう1つ質の悪い問題がある。**落ちている理由が「見出しが見つからない」なので、
一見すると画面が壊れているように読める。** 実際は壊れていない。
このまま放置すると、次に E2E を回した人が
**自分の変更が壊したと思い込んで、無関係な場所を探し回ることになる。**

---

## 原因（調査済み・2つある）

**どちらも F1（`middleware.ts` → `proxy.ts` の移行）とは無関係。**
移行前のコードに戻して同じテストを走らせ、**まったく同じ落ち方をすることを確認済み。**

### ① アサーションがデザイン移植に追いついていない

`tests/e2e/auth.spec.ts:27` などが、ログイン画面に「ログイン」という**見出し**があることを
期待している。

```ts
await expect(page.getByRole("heading", { name: "ログイン" })).toBeVisible();
```

しかし `943345a`（モックのデザインを各画面へ移植する）で、
**ログイン画面の見出しは「おかえりなさい」に変わっている。**
「ログイン」は送信ボタンのラベルにしか残っていない。

同じ理由で E-103 の「ステージ選択」という見出しも、いまの画面にあるか確認が必要。

### ② `127.0.0.1` からの開発リソースが遮断されている

`playwright.config.ts:27` の `baseURL` は `http://127.0.0.1:3100`。
一方 Next.js 16 は、**`localhost` 以外から開発用リソースを取りに行くのを既定で止める。**
実行中このログが大量に出る。

```
⚠ Blocked cross-origin request to Next.js dev resource /_next/static/chunks/... from "127.0.0.1".
```

**JS が読み込めないのでハイドレーションが起きない。**
つまりログイン画面のフォームが動かず、ボタンを押しても何も起こらない。
①を直しても、こちらを直さないとログインを伴うテスト（E-103・E-104・E-105・E-130）は通らない。

---

## 手順

1. **②を先に直す。** ①だけ直しても、ログインを伴うテストは通らない
   - `playwright.config.ts` の `BASE_URL` を `http://localhost:${PORT}` にする（**こちらが軽い**）
   - または `next.config.ts` に `allowedDevOrigins: ['127.0.0.1']` を足す
   - **前者を推奨。** 本番の設定に手を入れずに済み、遮断そのものは開発時の安全機能として残る
2. `npm run test:e2e -- tests/e2e/auth.spec.ts` を回して、残る失敗を見る
3. **落ちたアサーションを、いまの画面の実際の文言に合わせる**
   - 画面を実測してから直すこと。推測で直すと今度は別の理由で落ちる
   - 「見出し」で取るか「ボタン」で取るかも、実際の DOM に合わせる
4. `auth.spec.ts` が通ったら、**残りの E2E も全部回す**
   （`display` / `scoring` / `stages` / `security`）。同じ理由で落ちている可能性が高い
5. `tests/e2e/テストケース.md` の状態列を実態に合わせる

## ⚠️ オーナーに確認すること

**`npm run test:e2e` は実際の Supabase に書き込む。**

`tests/e2e/support/fixtures.ts` は、テスト用ユーザー（`e2e@ferret.test`）と
`order` が 9000 以上の問題を投入し、終わったら消す作りになっている。
後片付けは前後2回走り、失敗したら例外を投げて止まる。

> テストを直すために、実際のデータベースへ**テスト用のデータを入れて消す**作業が要ります。
> 本番と同じデータベースを開発でも使っているため、確認させてください。
>
> - **案A: そのまま実行する**（おすすめ）
>   後片付けの仕組みは入っていて、失敗したら止まるようになっています。
>   実際の問題データ（表示順 1〜5 と 999）には触りません
> - 案B: 先に別のデータベースを用意する
>   安全ですが、用意する作業が別途必要になります
>
> **おすすめは案A**です。この仕組みは以前ゴミが残る不具合があり、すでに直されています
> （`order` を引用符でくくる件・`fixtures.ts` のコメント参照）。

**E-111 だけは扱いが違う。** このテストは毎回**実在しないメールアドレスで新規登録する**ので、
実行するたびに使い捨てのアカウントが増える。除外して進めるか、確認したうえで回すか決めること。
