# F4. セキュリティレビューのエージェントを作る

**種別:** 仕組みづくり（開発体制）
**規模:** 中
**前提として終わっていること:** なし

> ### ⚠️ 同時進行の注意
> **アプリのコードを触らないので、どのタスクとも衝突しない。**
> 作るのは `.claude/agents/` 以下のファイルとドキュメントだけ。

**先に読むもの**
- `ideas/セキュリティ_観点.md`（**必読。** すでに観点が整理されている。これを土台にする）
- `ideas/セキュリティ_残課題.md`（過去のレビューで何を見て、何を意図的に見送ったか）
- `.claude/agents/` の既存ファイル（あれば書き方の手本）

---

## 何をするか

**「レビューして」と言うだけでセキュリティの指摘が返ってくる**仕組みを作る。

いまは私（AI）にその都度お願いする形なので、**何を見るかが毎回変わる。**
観点を1つのファイルに固定して、それを読ませれば同じ基準でレビューされる状態にする。

具体的には、Claude Code の**サブエージェント**として定義ファイルを1つ置く。
以降は `/security-review` のように呼び出すだけで走る。

---

## なぜ必要か

**このプロダクトは、他人のデータを預かって外部のAIに文章を送っている。**
しかも1人で開発しているので、**レビューする他人がいない。**

過去のレビューで実際に見つかったものを見ると、放置していたら実害が出ていた。

- セッションが CDN 経由で他人に配られる状態
- 認証エンドポイントの偽装
- URL 直打ちでのステージ解放の回避
- 採点の連打による OpenAI 請求の膨張

**これらは「気をつける」では防げない類。** 毎回同じ観点で機械的に見るほうが確実。

さらにこれから **D2（Stripe決済）** が入る。決済まわりは穴の実害が一番大きいので、
その前に仕組みを持っておきたい。

---

## ⚠️ オーナーに確認すること

> セキュリティレビューの仕組みについて決めることがあります。
>
> **① いつ走らせますか**
> - **案A: 自分で呼んだときだけ**（おすすめ）
>   `/security-review` のように打ったときに走ります。**費用と時間が自分の判断で決まります**
> - 案B: コミットのたびに自動で走る
>   漏れませんが、**毎回お金と待ち時間がかかります**（1回あたりの費用は内容次第）
>
> **おすすめは案A**です。まだ1人開発で変更の粒度が大きいので、
> 「決済を入れた」「新しいAPIを作った」といった節目で呼ぶほうが費用に見合います。
>
> **② 何を見る対象にしますか**
> - **案A: 直前の変更だけ**（おすすめ・速い・安い）
> - 案B: 毎回すべてのコードを見る（遅い・高いが漏れにくい）
> - 案C: 両方用意して呼び分ける
>
> **③ 指摘の出し方をどうしますか**
> **「実害と優先度を必ず添える」形にすることを勧めます。**
> 項目を並べるだけだと、直すべきものと放置してよいものが混ざって判断できません。
> 過去のレビューでもそこが要点でした。

---

## 手順

1. 上の3点を決める
2. **`ideas/セキュリティ_観点.md` を読み、観点を抜き出す。** ゼロから考えないこと
3. エージェントの定義ファイルを作る（`.claude/agents/security-reviewer.md` など）
   - 冒頭に「どういう時に使うか」を書く
   - **見る観点をチェックリストとして列挙する**（下記）
   - **出力の形を指定する**（実害・優先度・該当箇所・直し方）
   - **このプロダクト固有の前提**を書く（後述の「必ず含めること」）
4. 実際に走らせて、既知の穴を見つけられるか試す
   - `ideas/セキュリティ_残課題.md` §3 に**意図的に見送った項目**があるので、
     **それを「見送り済み」として扱えるか**を確認する（毎回同じ指摘を蒸し返すと使われなくなる）
5. 使い方を `tasks/README.md` の「共通の決まりごと」に1行足す

### 必ず含めること（このプロダクト固有）

エージェントがこれを知らないと、的外れな指摘か見落としになる。

| 前提 | なぜ必要か |
|---|---|
| **書き込みポリシーは意図的に0件** | 「INSERT ポリシーが無い」を欠陥として報告させない |
| **anon キーは公開前提** | 「鍵が露出している」という誤報を防ぐ |
| **`service_role` を使う箇所は自分で本人確認する義務がある** | ここが本当の穴になりうる場所 |
| **回答は外部AIに送る。PII 検査が入口** | 新しい送信経路を作ったら必ず指摘させる |
| **採点1回に実費がかかる** | 「認証だけで無限に叩ける経路」を穴として扱わせる |
| **見送り済みの判断**（`unsafe-inline` / Cookie の `httpOnly` / アカウント列挙） | 蒸し返させない |

## 注意

- **エージェントの指摘を鵜呑みにしないこと。** 「危ない」と書かれていても実害が無いものは多い。
  だから出力に**実害と優先度を必ず書かせる**設計にする
- **見送った判断を消さないこと。** `ideas/セキュリティ_残課題.md` §3 の記録がそのまま入力になる
- 秘密（`.env.local` の中身）をエージェントに読ませる必要はない。**読ませない前提で書くこと**

#### いちばん効いた発見 ── **既存テストの守備範囲が想像より厚かった**

着手前は「叩いて確かめる」をゼロから作るつもりだったが、実際には:

- `npm test` … I-390〜I-400（鍵の混入・matcher の漏れ・**AI を呼ぶ経路の上限確保**・閾値の直書き）
- `npm run test:db` … I-640〜I-687（**RLS 全部・RPC の revoke・上限の関数・並列・返金の対称性**）
- `npm run test:e2e` … E-400〜E-416（ヘッダ・注入・API の直叩き）

**RLS もプロンプト注入も、既に自動テストがある。** ここに同じものをもう1本足すと、
落ちたときにどちらを直せばいいのか分からなくなる。

そこで `probe.mjs` は**そのどれもが見ていないものだけ**に絞った。

| | なぜ既存テストが見ていないか |
|---|---|
| P-101/102 **本番の実物のヘッダ** | e2e はローカルしか見ない。Vercel が反映しているかは別問題 |
| P-201 **DB の入口の棚卸し** | マイグレーションを読んでも、Supabase 側で生えたものには気づけない |
| P-301/302 **フィルタ注入・埋め込みでの横取り** | 試していなかった（RLS が効いていれば無害だが、確かめていないのと無いのは違う） |
| P-303 **生SQLが増えていないか** | いま動的SQLはゼロ。**将来 `EXECUTE` を足したときに最初に落ちる網** |
| P-404 **型の違う値で 500 にならないか** | e2e は正しい型でしか叩いていない |
| P-501 **ビルド成果物への鍵の混入** | **`I-393` が `it.todo` のまま**（ビルドが要るので単体テストに置けない）。その穴がここ |
| P-502 `npm audit` | 手で回すしかなかった |

#### 費用 ── **¥0 になった**

当初 F6 は「上限まで叩くと数十円」と見積もっていたが、**実費はかからない**と分かった。

- e2e は **OpenAI のスタブ**（`tests/e2e/support/openai-stub.mjs`）を経由するので、上限も連打も¥0で試せる
- `probe.mjs` が叩く経路は全部 403 / 415 / 413 / 400 / 401 で**採点の手前**で止まる
  （`app/api/score/route.ts` のガードの順序に依存している。**順序を変えたらここも見直す**）

#### 詰まった点

- **`isCrossSiteRequest` は Origin が無いリクエストを通す。** curl で叩くと素通りするので、
  403 を確かめるには `Origin:` か `Sec-Fetch-Site:` を明示的に付ける必要がある（`lib/http/origin.ts` のコメントに理由あり）
- **`problem_id: [1]` や `true` は `Number()` で 1 に化けて通る。** 実害は無い（同じ整数になるだけで、
  この先に 401 がある）が、型の緩さとして P-404 の対象にしてある。**見るのは「5xx にならないこと」**
- **`probe.mjs` の全項目いっぺんの実行は Claude Code の auto モードに止められた。**
  外部ホストへ攻撃的なリクエストを送る形なので当然の判定。`--only=` で絞れば通る。
  通しで走らせるときは `!` を付けて手で回すか、Bash の許可ルールを足す
- **Supabase は `/rest/v1/`（入口の目次）を `service_role` にしか返さない。**
  最初 anon で引いて「入口が全部消えた」と誤警報になった。
  **これ自体が防御**（anon で構成が丸ごと読めない）なので、P-201 = anon で引けないこと・
  P-201b = service_role で棚卸し、の2本に割った
- **`grant execute on function` を P-303 が動的SQLと誤検知した。**
  **正しく `revoke` してあるファイルほど警告が増える**という逆向きの壊れ方だったので除外した
