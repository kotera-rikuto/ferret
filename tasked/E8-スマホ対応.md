## 何をするか

**いまの画面はパソコン向けに作られている。**
横幅が狭い端末では、左のメニューと右側の情報を消して、簡易的な見出しで代用している。

スマホでちゃんと使える形にする。

---

## なぜ必要か

このジャンルのアプリは**移動中や隙間時間に使われることが多い。**
「毎日続ける」ことを狙うなら、スマホで使えないのは大きな制約になる。

ただし**急ぎではない。** 公開自体はパソコン向けのままでもできる。

---

## ⚠️ 着手前にオーナーに確認すること

> スマホ対応について、範囲を決めてください。
>
> **① どこまでやりますか**
> - **案A: 全画面をスマホでも使えるようにする** — 作業は大きい
> - **案B: 問題を解く流れだけ**（ステージ選択 → 問題 → リザルト） — 設定などは後回し
> - 案C: いまのまま（簡易表示）で公開し、様子を見てから
>
> **考えどころ:** Ferret は**コードを読む**アプリです。
> スマホの狭い画面でコードを読むのは、そもそも体験として厳しい面があります。
> 「移動中に軽く復習する」用途を狙うのか、
> 「腰を据えて取り組むのはパソコン」と割り切るのかで、かける労力が変わります。
>
> **おすすめは案B**です。まず問題を解けるようにして、
> 実際にスマホで使ってみてから範囲を広げるほうが無駄がありません。
>
> **② 回答の入力についてはどうしますか**
> スマホでは長い文章を打つのが大変です。
> いまは最低文字数の決まりがありますが、
> **スマホだけ緩めるかどうか**を決めてください。
> （緩めると採点の基準が端末によって変わるので、**個人的には緩めないことを勧めます**）

## 手順

1. 範囲を決める
2. ステージ選択（`app/stages/page.tsx` / `components/stage/StageMap.tsx`）
   - いまは横幅1024px以上で3列。狭いときの表示を作る
   - マップの蛇行の幅を狭い画面に合わせる
   - 連続日数などの情報の置き場所を決める
3. 問題画面（`app/problems/[id]/page.tsx` / `ProblemForm.tsx`）
   - **コードの枠が横に溢れないようにする**（横スクロールできるようにする）
   - 下に固定されている回答ボタンが、キーボードを出したときに隠れないようにする
4. リザルト画面（`app/result/[id]/ResultView.tsx`）
5. 実機またはブラウザの端末表示で確認する
6. `npm run build`

## 注意

- **パソコン向けの表示を壊さないこと。** ここが一番起きやすい事故
- コードは折り返さないこと。折り返すと**行の対応が分からなくなり、読解の妨げになる**

## 作業記録

### 2026-08-19 ── 実装（幅375px で実測しながら）

**決めた範囲（オーナー判断）:** 「アプリを進めるのに支障が出るところ」＋ログイン・ログアウト。
案B（解く流れだけ）より広く、案A（全画面）より狭い。

**回答の最低文字数は緩めない。** そもそも `ANSWER_MIN_CHARS = 10` で、
スマホで打つのに負担になる量ではない。端末で採点の前提が変わるほうの害が大きい。

#### 着手前に実測したら、壊れている場所はタスク作成時の想定よりずっと少なかった

幅375×667 で全画面を回して `scrollWidth` を測ったところ、**横に溢れている画面はゼロ**。
コードの枠も既に横スクロールが効いていた（`lib/code/highlight.ts` の `PRE_CLASS` に
`overflow-x-auto` が入っている。E5 のときから入っていた）。

**手を入れずに済んだ画面:** ログイン / 新規登録 / リザルト / ふりかえり（一覧・詳細）/ せってい。
**ログアウトも既に届いていた** ── サイドバーは `lg` 未満で消えるが、
`stages` `settings` `review` `review/[id]` のいずれも `lg:hidden` の簡易ヘッダーに
`LogoutButton` を出す作りになっている。

なので**このタスクの「触る場所」の表のうち、実際に触ったのは3ファイル。**
`ResultView.tsx` と `AppSidebar.tsx` は直す理由が見つからなかった。
**表に無い `app/login/page.tsx` を1行だけ触っている**（幅320px の溢れ。下の「3つ目」）。

#### 直したのは2か所

**1. ステージ選択のマップ（`StageMap.tsx`）**

マップの列は `lg` 以上で約 664px、`lg` 未満は画面幅そのもの（375px 端末で 327px）と半分以下。
横位置は割合なので列が狭まると丸どうしが近づき、**現在地の「スタート」吹き出しが
1つ上の行のラベルに 53×36px 重なっていた**（実測。`lg` 以上では起きない）。

横に逃がす余地が無いので**縦に開けた。** `ROW_H` を `lg` 未満だけ 180 → 224 にする
（必要な下限は 216。導出は `ROW_H_NARROW` のコメント）。**CSS では切り替えられない** ──
行の高さは SVG の `y1` / `y2` にも入っていて、幾何属性はメディアクエリの対象にならない。
`useSyncExternalStore` + `matchMedia` で、**サーバー描画は常に `lg` 以上の値**を返す。

`scrollToCurrent` を呼ぶ effect の依存に `rowH` を足してある。狭い画面では
最初の描画のあとに全ノードの縦位置が動くので、入れないと着地の計算が古い座標で走る。

代償: 幅375 でのマップ全体の高さが 20654px → 24486px（＋19%）。「現在地へ」があるので許容した。

**2. 問題画面（`page.tsx` / `ProblemForm.tsx`）**

上下の固定バーで **220px（667px 画面の 1/3）**が埋まっていた。

- **下のバーの固定をやめた（`lg` 未満のみ・オーナー判断）。** `position: fixed` は
  仮想キーボードが出ても画面の下端に貼り付いたままなので、**書き始めた瞬間に
  「回答する」がキーボードの裏へ入る。** 回答欄のすぐ下に流して一緒にスクロールさせる。
  **注記の文言は縮めていない**（仕様書 §9.5 は常時表示を求めており、
  短い一文へ差し替える判断はこのタスクの範囲外）。案として「注記を1行に縮めて固定は維持」も
  出したが、オーナーは**法務の文言に触らないほう**を選んだ。
- 縦に積んでも **`order` は効くので、目に見える並び（注記 → ボタン）は変わらない。**
  DOM 順が「ボタン → 注記」なのは E-455 の対処なので、そこは触っていない。
- `main` の `pb-44` は固定フッターに隠れる分の逃げ。固定をやめた側では
  そのまま残すとボタンの下に 176px の空白が続くので `pb-10 lg:pb-44` にした。
- ヘッダーのタイトルが3行に折り返して 97px を使い、読解型のバッジが縦書きに潰れていた。
  `lg` 未満だけ1行に切る（97px → 70px）。

結果、**常に使える高さが 447px（67%）→ 597px（90%）**。

#### パソコン側が動いていないことの確かめ方

「見た目は変わっていないはず」で済ませず、origin/main に一度戻して撮り比べた。

- 問題画面（幅1440）: **スクリーンショットがバイト単位で完全一致**（通常表示・全ページとも）
- ステージ画面: 吹き出しと輪のアニメーションで**同じコードでも2回撮ると差が出る**ので
  画像比較は使えない。代わりに**ノード101個の座標・SVG の道の全端点・節の高さ・
  全体の高さ（20654px）を書き出して diff → 完全一致**

#### テスト

`npm test` 701 passed / 63 skipped、`npm run build` 通過、`npm run lint` 指摘なし。
E2E は **107 passed / 2 failed / 1 skipped**。

**落ちた2件はこの変更と無関係**（origin/main に戻して同じ1件を走らせても落ちる）。
`E-452 主要な画面に NG語が出ない` で、原因は**問題データのタイトル**：
`Promise.all / allSettled / race ─ 1つ失敗したら残りはどうなるか` に NG語「失敗」が入っている。
`/stages` は101件のタイトルを全部描くので、1件でも混ざると当たる。**A2 側で直す話。**

#### 受け入れ条件を詰めたときに見つけた3つ目（ログイン画面・幅320px）

375px では問題なかったが、**幅320px でログインのカードが 38px 画面から溢れていた**（origin/main から）。

原因は grid の暗黙の1列。列を書かないと `auto` ＝ `minmax(min-content, max-content)` になり、
**最小値がカードの min-content（実測310px）から下がらない。** 320px 端末の使える幅は 272px しかないので、
310px の列がそのまま溢れる。375px 以上では使える幅が min-content を上回るので起きない。
**新規登録が同じ `w-full max-w-sm` で溢れないのは、あちらが flex で組んであるから。**

`grid-cols-[minmax(0,1fr)]` で最小値を 0 にして解消。
**幅 375 / 431 / 432 / 500 / 1024 / 1440 でスクリーンショットがバイト単位で一致**しており、
320px 未満でしか挙動が変わらない。

#### 残していること

- **実機の iOS Safari では見ていない。** 375×300 での当たり判定は通っており、
  フッターが `static` なので fixed 特有の問題は成立しないが、実物で押したわけではない
- **幅320px では OAuth ボタンの文字が折り返す**（「Googleでログイ / ン」、「準備 / 中」）。
  **溢れも切れもしておらず押せる**が、見た目は綺麗ではない。
  受け入れ条件は 375px なので直していない。詰めるならカードの `p-8` を狭い画面だけ緩める（`p-6 sm:p-8`）。
  ただし**それをすると 375px の見た目も変わる**（いまはバイト単位で従来と一致している）
- リザルト画面の紙吹雪の粒が1つ、親の枠から 2px 出る位置に来ることがある。
  親が `overflow-hidden` なので切られており、ページは溢れない（直す必要なし）
