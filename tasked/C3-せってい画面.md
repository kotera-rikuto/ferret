# C3. せってい画面（退会・パスワード変更・メールアドレス変更）

**種別:** 実装
**規模:** 大
**前提として終わっていること:** メールアドレス変更のみ **C1**（メール送信）が先
**関連:** C2（プライバシーポリシー）で「退会時にデータを消すか」を決めておくと手戻りがない

## 何をするか

サイドバーに「せってい」が**準備中として置いてある**。中身を作る。

| 機能 | 必要度 |
|---|---|
| **退会（アカウント削除）** | **公開前に必須** |
| パスワード変更 | あるとよい（実装は軽い） |
| メールアドレス変更 | あるとよい（**C1 が先**） |

---

## なぜ必要か

**個人情報を預かる以上、「やめたい」と言われたときに消せる必要がある。**
退会の手段が無いまま公開するのは避けたい。

パスワード変更とメールアドレス変更は、無くても公開はできるが、
「設定画面を開いたのに何もない」状態は体験として良くないので、まとめて作る。

---

## ⚠️ オーナーに確認すること

**退会したときに何を消すか。これは着手前に必ず決めること。**

> 退会したとき、その人のデータをどう扱いますか。
>
> **案A: 全部消す**
> ログイン情報も、回答の履歴も、異議申し立ての内容も消します。
> - よい点: 「消してほしい」に完全に応えられる。分かりやすい
> - 悪い点: **問題の改善に使っていたデータも消えます。**
>   「この問題は3割が同じ勘違いをする」といった集計から、その人の分が抜けます
>
> **案B: ログイン情報だけ消し、回答は誰のものか分からない形にして残す**
> - よい点: 問題の改善に使えるデータが残る
> - 悪い点: 「残っている」ことを**プライバシーポリシーに明記する必要**があります（C2と関係）。
>   説明の手間が増えます
>
> **決め方の目安:** いま利用者はほぼいないので、**案A（全部消す）で始めるのが安全**です。
> 説明が要らず、後から案Bに変えることもできます（逆は難しい）。
>
> どちらにしますか。

あわせて確認:

> 退会するときの確認方法はどうしますか。
> - **案A: パスワードをもう一度入力させる**（おすすめ）
> - 案B: 「削除」と入力させる
>
> 案Aを勧めるのは、**パソコンを離席したときに他人に消されるのを防げる**ためです。

## 手順

### 1. 画面の枠

1. `app/settings/page.tsx` を作る
2. **`proxy.ts` の保護対象に `/settings` を追加する**（ログインが要る画面のため）
3. サイドバー（`components/layout/AppSidebar.tsx`）の「準備中」を外してリンクにする

### 2. パスワード変更（一番軽い）

4. 画面から `supabase.auth.updateUser({ password })` を呼ぶ
5. **C4 とセットで、古いパスワードの入力を必須にする設定を有効にする**
   （`supabase/config.toml` の `secure_password_change`）

### 3. メールアドレス変更（**C1 の後**）

6. `supabase.auth.updateUser({ email })` を呼ぶ
7. 新しいアドレスに確認メールが届く。**メール送信が動いていないと使えない**

### 4. 退会（一番重い）

8. サーバー側のAPIを作る（例: `app/api/account/delete/route.ts`）
   - **先頭に `isCrossSiteRequest` と `hasJsonContentType` を置く**（共通の決まりごと）
   - ログインしている本人か確認する
   - 上で決めた確認方法（パスワード再入力など）を検証する
   - 特権キー（`lib/supabase/admin.ts`）でアカウントを削除する
   - 案Aなら、関連するデータも消す
9. 削除後はログアウトさせてタイトル画面へ戻す

### 5. 仕上げ

10. `npm test` と `npm run build` を通す
11. **実際に捨てアカウントを作って退会まで通す**

## 注意

- **退会は取り消せない。** 押し間違いを防ぐ確認を必ず入れること
- **特権キーを使うAPIでは、必ず自分で本人確認をすること。**
  特権キーは「誰が呼んでいるか」を見ないので、確認を忘れると
  **誰でも他人のアカウントを消せるAPI**になる
- **開発用アカウント（`dev@ferret.test`）を消さないこと。** 動作確認で使っている
- 退会の処理を書くときは、`user_attempts` と `problem_feedback` が
  そのユーザーを参照している点に注意（消す順番を誤ると失敗する）

### 2026-08-19 実施（C7 を同梱）

#### 決めたこと（オーナー判断）

| 論点 | 決定 | 理由 |
|---|---|---|
| 退会で消す範囲 | **全部消す（案A）** | **C2 ですでに確定していた。** `/terms` 第12条・`/privacy` 第7条に「回答、採点結果、進行状況を含む利用者のデータを削除します」と**公開済み**なので、実装はそれに従うほかない。異議申し立ての本文も一緒に消えるため、問題改善に使える材料はその分減る |
| 退会の確認方法 | **「削除」の入力とパスワードの再入力を両方** | 文字の入力は押し間違いを防ぎ、パスワードは離席した端末を触った他人を防ぐ。片方だけでは片方の事故しか防げない |
| メールアドレスの変更 | **今回は作らず「準備中」表示** | 確認メールが実ユーザーに届くのは C6（独自ドメイン）の後。押しても何も起きない機能を置かない |
| C7 の同梱 | まとめて実施 | 同じ認証まわりで、票にも「C3 とまとめてよい」とある |

#### 入れたもの

- `app/settings/page.tsx` + `PasswordForm.tsx` + `DeleteAccountForm.tsx`
- `app/api/account/delete/route.ts` — 送信元 → Content-Type → 4KB → 認証 → 確認語 → パスワード再確認 →
  子→親の順に削除 → アカウント削除 → セッション Cookie 破棄
- `lib/account.ts` — 確認語（`DELETE_CONFIRM_WORD`）と削除順（`DELETE_TARGETS`）を1か所に。**テストも同じ配列を見る**
- `lib/auth/reauth.ts` — サーバー側のパスワード確認。**Cookie を持たない使い捨てクライアント**で行う
  （`lib/supabase/server.ts` のクライアントで `signInWithPassword` を呼ぶと、確認のためのログインで
  セッション Cookie が書き換わってしまう）
- `lib/auth/errors.ts` に `PASSWORD_MIN_LENGTH`（8 の直書きが3か所目になるところだった）と `same_password` の文面
- `proxy.ts` の matcher に `/settings/:path*`、サイドバーの「せってい」をリンクに（`current` で強調を切り替え）
- `supabase/config.toml` の `secure_password_change = true` — **反映は `config push` 待ち**（`site_url` が
  localhost のままなので押せない）。**いま実際に守っているのはアプリ側**の「いまのパスワードを先に確認する」処理
- C7: 新規登録の完了画面に一文（「すでにご登録のあるメールアドレスの場合、メールは届きません。
  そのままログイン画面へお進みください。」）

#### 設計判断

- **パスワード変更はブラウザから `auth.updateUser`、退会はサーバー API。** 分けたのは、
  特権キーで DB を消すのが後者だけだから。パスワードは認証基盤の担当でこちらの DB を触らない
- **退会は子 → 親の順に明示的に消す。** 外部キーの `on delete cascade` の有無に依存しない形にした。
  初期スキーマ（`users` / `problems` / `user_attempts`）は migrations 運用の前に手で作られていて、
  **cascade の有無がどこにも記録されていない**（`ideas/db仕様.md` にも無い）。実測で消えることは確認済み
- `subscriptions` も削除対象に入れた。**ただしこれは Stripe の解約ではない。**
  D2 で「この行を消す前に Stripe 側を解約する」処理を足すこと。忘れると**退会後も課金が続く**
- **削除が途中で失敗したらその先へ進まない**（ログインできる状態で残す）。中途半端に消してログインだけ
  消すと、本人にも運営にも何が残っているのか分からなくなる
- 退会後の遷移は `location.href` ではなく `router.push` + `router.refresh`。
  `location.href` は lint（`@next/next/no-location-assign-relative-destination`）が警告する。
  `refresh` まで呼ぶのは、ログイン中に描いた画面がクライアント側のキャッシュに残るため

#### 確認したこと（実測）

**下の数字は `origin/main`（`9e04ab8` = E5・C6・E2 を含む）を取り込んだ後の実測。**
取り込みは E2 セッションからの連絡（マイグレーションを1本足してリモートDBへ適用済み）を受けて行った。
**C3 はマイグレーションを作っていないので `supabase db push` は不要。** 衝突は無し
（`supabase/config.toml` だけ同じファイルを触っていたが別の項目。C6 が `site_url` を
本番URLに直したので、`secure_password_change` のコメントの「push を保留している理由」だけ書き直した）。
