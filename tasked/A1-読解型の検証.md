# A1. 読解型4種を1問ずつ作って採点を通す

**種別:** コンテンツ作成 + 検証
**規模:** 中（1種類あたり半日程度。4種類あるので分割してよい）
**前提として終わっていること:** 影響型を作る場合のみ **E4**
**このタスクが終わらないと着手できないもの:** A2（問題の量産）

> ### ⚠️ 同時進行の注意
> **A2（問題の量産）と同時に進めないこと。** どちらも問題を登録するので、
> **表示順の番号が重複する**（`npm run test:db` が検出する）。
> **B1（採点のブレを測る）とも同時に進めないこと。** 測っている最中に対象が増えると比較できない。
> アプリのコードは触らないので、コードの衝突は起きない。

**先に読むもの**
- `ideas/問題作成ガイド.md`（作り方の本体。**必読**）
- `ideas/問題構成案.md`（どの問題を作るかの一覧）
- `problems/stage-001-005.md` と `problems/stage-001-005.sql`（**既存5問の実物。一番の手本**）

---

## 何をするか

問題には**6つの読ませ方**がある。そのうち**2つしか実際に動かしたことがない。**

| 読ませ方 | 作った数 | 状態 |
|---|---|---|
| トレース（順に追う） | 4問 | 確認済み |
| ズレ（思い込みとの差） | 2問 | 確認済み |
| **意図（なぜこう書いたか）** | 0問 | **未確認** |
| **影響（何が壊れるか）** | 0問 | **未確認・E4 が先** |
| **命名（名前から中身を推測）** | 0問 | **未確認** |
| **仕様（要件を満たしているか）** | 0問 | **未確認** |

**未確認の4つを、1問ずつ作って実際に採点させる。**

---

## なぜ必要か

採点の仕組みは、この「読ませ方」ごとに**採点の物差しを切り替えている。**
切り替えた先が一度も動いていないので、**正しく採点できるか誰も知らない。**

ここを飛ばして問題を量産すると、後で物差しの調整が必要になったときに、
**作った問題の採点基準を全部書き直すことになる。** 先に4つ通しておけば、その事故を防げる。

---

## 手順

**1種類ずつ、最後まで通してから次に進むこと。** 4問まとめて作らない。

1. `ideas/問題構成案.md` から、その読ませ方に合う問題を1つ選ぶ
2. `ideas/問題作成ガイド.md` に従って中身を作る
   - コード / 設問 / 模範解答 / キーワード4組 / 採点基準
3. `problems/stage-001-005.sql` と同じ書き方で登録用のSQLを書く
   - **`id` は書かないこと。** 自動で振られるため、書くとエラーになる
   - `"order"` は引用符が必要（予約語のため）
4. Supabase の SQL Editor で実行して登録
5. `npm run test:db` を実行し、問題データの健全性チェックを通す
   （模範解答がキーワードで満点を取れるか、などを自動で確認してくれる）
6. **ブラウザで実際に解いて採点させる**（開発用アカウント: `dev@ferret.test` / `FerretDev2026!`）
   - 下の「確認する回答パターン」を全部試す
7. 結果をこのファイルの末尾に記録する

### 確認する回答パターン（各問で必ず全部やる）

| 回答 | 期待する結果 |
|---|---|
| 模範解答に近いもの | 高得点・クリア |
| **中核は合っているが短いもの** | **クリアすること**（ここが一番大事） |
| ぼんやりした一般論 | 不合格 |
| **結論が逆のもの** | **クリアしないこと**（ここも大事） |

2番目と4番目が設計の要。**「短くても正しければ通る」「間違っていれば通らない」**が
崩れていないかを見る。

---

## ⚠️ オーナーに確認すること

**採点の結果が期待とズレたときは、自分で採点の仕組みを直さないこと。**

問題データが悪いのか、採点の物差しが悪いのか、**その場では区別がつかない。**
ズレを見つけたら、次のように報告して判断を仰ぐこと。

> ○○型の問題で、「（回答の内容）」という回答が △点になりました。
> 期待は（クリア / 不合格）でした。
> 考えられる原因は2つあります。
> - 問題側: 採点基準の書き方が（狭い / 広い）
> - 仕組み側: この読ませ方の物差しが合っていない
> どちらとして扱いますか。仕組み側を直す場合、他の読ませ方にも影響します。

**採点の仕組み（`lib/ai/` 以下）を触る判断は、B1（採点のブレを測る）でまとめて行う。**
ここでは記録に留めるのが原則。

>

> 同じ日に並走していた **B2 が `PROMPT_VERSION` を `p2` → `p3` に上げている**
> （`matched_reject` の追加と、矛盾時に場所を示させる指示の追加）。
> A1 のマージ時点の main は `p3` なので、**上の表は現行の採点器の値ではない。**
>
> - **配点そのものは変わっていない。** `lib/ai/compose.ts` の重み・閾値・頭打ちは同一で、
>   B2 の変更は型とコメントの追加だけ。**「中核を読めていない回答は通らない」などの
>   設計上の保証はそのまま**なので、A1 の結論（読解型ごとの `depth` が独立に働く）は生きている
> - **ただし判定は動きうる。** プロンプトが変わったので、同じ回答でも観点の判定が振れる可能性がある

>   **プロンプト変更が判定をどう動かしたかの実測になる**（B1 で拾うと安い）
> - 上の表は **`p2` のベースライン**として読むこと

### 決めたこと

| | 決定 | 理由 |
|---|---|---|
| ① 投入の経路 | **PostgREST（service_role）で投入し、SQL は投入内容から生成する** | 手で SQL を書くと記録と DB がずれる。E4 の `prerequisite-001-005.sql` と同じ形にそろえた |
| ② 仕様型の題材 | **モックの `maskEmail` を使わず郵便番号にした** | メールアドレス形式が採点APIの PII 検出に当たり、**テストの入力値を引用して正答した学習者が 400 で拒否される**。ステージ5で `email` を外したのと同じ理由 |
| ③ 仕様型の `it` の名前 | **入力の場合だけを書き、出力のきまりは書かない** | `it("ハイフンを補う")` のように結論を日本語で書くと、見出しを写すだけで仕様の説明ができてしまい、層1が「読めたか」ではなく「写したか」の検査になる |
| ④ 命名型の `depth` | **「実装が担う責務」ではなく「同じファイルの他の関数との責務の切り分け」に置いた** | 中身を伏せる問題なので実装が見えない。`is` で始まる述語は判定だけ担い状態は変えない、という規約と周囲のコードの対応に置き換えた |
| ⑤ 影響型の `core` | **発生箇所ではなく原因箇所に置いた** | 発生箇所はログの2行目を写せば出るので、そこを `core` にすると転記で満点になる |

### 詰まった点・申し送り

1. **`origin/develop` は存在しなかった → 統合先は `main` 一本と決めた（オーナー判断）。**
   依頼では「E4 は origin/develop にマージ済み」だったが、実際は **`origin/main`**
   （ローカルの `develop` は main より5コミット遅れており E4 を含まない）。
   E4 を含む唯一のベースなので `origin/main` から worktree を切った。
   **`tasks/並列実行プラン.md` の `develop` 記述をこのコミットで `main` に直した**
   ── 実際に E4・F1・B2 が積まれているのは main なので実態に合わせる、
   2本を同期し続ける手間を持たない、という判断。`tasks/README.md` は元から main 基準だった。
2. **worktree では `node_modules` をシンボリックリンクにできない。**
   Turbopack が `Symlink [project]/node_modules is invalid, it points out of the filesystem root`
   で落ちる（`next dev` が起動しない）。`cp -Rc`（APFS のクローン）で実体を置いた。
   `.env.local` のリンクは問題なかった。**`problems/` は git 管理外なので本体側に置いてある。**
3. **投入前に機械検査を回すと差し戻しが出ない。** I-801〜I-817 は `npm run test:db` で
   投入後にしか回せないが、同じ判定を投入前に通したところ 4問とも一発で通った。
   `lib/ai/compose.ts` は依存ゼロなので `scoreKeywords` / `normalizeForMatch` を
   そのまま呼べる。**A2（91問）では常設化する価値がある。**
4. **`next dev` が worktree に `AGENTS.md` を置いていく → `.gitignore` に足した（オーナー判断）。**
   `.gitignore` は `/CLAUDE.md` を除外しているので worktree には CLAUDE.md が存在せず、
   `next dev` が代わりに `AGENTS.md` を生成する。開発サーバーを起動するたびに

   中身は自動生成物なので追跡する意味がなく、`/AGENTS.md` の1行で恒久的に消える

### 採点の物差しについて気づいた点（**仕組みは触っていない**）

タスクの方針どおり `lib/ai/` は1行も触っていない。**判断は B1・B3 でまとめて行うこと。**
詳細は `problems/stage-015-053-059-078.md` の「気づいた点」。要点だけ:

- **ステージ78 の「短いが正しい回答」が 92点（パーフェクト帯）に入った。** 合否は正しいが、
  `ground` を戻り値を書いただけで full にしている。パーフェクト率の目安（15〜25%）から外れる方向。
  問題側（`ground` の条件を絞る）か仕組み側（同じ引用で複数の観点を full にできる）かは
  この場では区別がつかない
- **`verdict` が `none` / `partial` でも `evidence` が入ってくる。** プロンプトは
  空文字列にすると指示している。点数への影響はないが指示が守られていない
- **同じ引用を複数の観点に使い回している。** 引用照合は「観点ごとに別の根拠を持っているか」を見ていない
- **ステージ59 の矛盾検出で `DEEP_CAP_ON_CONTRADICTION = 20` が実際に働いた**（層2が 44 → 20）。
  `残課題` §2 の変更が効いていることの初の実測。0点にしていたら
  「ログの読み方は合っているが結論だけ反転」が全部消えていた
- **`残課題` §11（数値だけの引用で veto が素通りする経路）は今回は踏まれていない。**
  遵守率の実測は B1 で行うこと
