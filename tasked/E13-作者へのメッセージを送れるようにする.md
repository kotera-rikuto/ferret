## なぜ必要か

**いま届く声は「この採点はおかしい」「この問題が間違っている」の2種だけ。**

既存の仕組み（`problem_feedback`）は**問題に紐づく報告**しか受け取れません。
「操作が分かりにくい」「もっとこういう問題が欲しい」といった**サービス全体への声**を受け取る口がない。

公開して人が使い始めた段階なので、**改善の材料はユーザーからしか出てきません。**
そして1人で作っている以上、**使っている人が最強のQA**になります。

---

## いまの仕組み（そのまま使える部分）

**画面もAPIもテーブルも既にある。** 3つ目の種別を足すのが基本方針。

| | 現状 |
|---|---|
| テーブル | `problem_feedback`（`user_id` / `problem_id` / `attempt_id` / `kind` / `comment`） |
| 種別 | `score_dispute`（採点への異議）/ `problem_error`（問題の誤り） |
| 文字数 | 10〜500字（`lib/feedback.ts`） |
| 画面 | リザルトに**開閉式のフォームが2つ**（`ResultView.tsx`） |
| API | `/api/feedback`（CSRF・Content-Type・本文サイズの守りが入っている） |
| 連打対策 | `unique(user_id, problem_id, kind)`。**再送は「書き直し」として上書き** |

### ⚠️ そのままでは足りない点（3つ）

**① `problem_id` が NOT NULL**
サービス全体への意見は特定の問題に紐づかないことがある。
いまの制約だと**必ずどれかの問題に紐づけないと保存できない。**

**② `kind` が2種に固定されている**
`check (kind in ('score_dispute', 'problem_error'))` があるので、
**3つ目を足すにはマイグレーションが要る。**

**③ `unique(user_id, problem_id, kind)` があるので、同じ問題には1回しか送れない**
異議申し立てなら妥当だが、**改善要望は何度でも送りたいはず。**

## メール送信について（新しい能力になる）

⚠️ **いまアプリからメールを送る経路がありません。**

`RESEND_API_KEY` は設定済みですが、**使っているのは Supabase（確認メールの送信）**で、
**アプリのコードは読んでいません**（`CLAUDE.md` に明記）。

このタスクで**初めてアプリからメールを送る**ことになります。

- `resend` のパッケージを入れるか、API を直接叩く
- **送信元は認証済みのドメイン**（`ferretcode.com`）でなければ届かない（C6 で確認済み）
- **`lib/legal.ts` の第三者提供先の記載を確認する。**
  すでに「Resend, Inc. — 確認メールなどの送信」とあるので、**用途が広がることを追記するか判断する**

## 手順

1. 上の5点を決める
2. **マイグレーションを追加する**
   - `kind` の `check` に3つ目を足す（例: `improvement`）
   - ③で「何度でも送れる」を選んだ場合、`unique` 制約の見直し
   - ②で案Bなら `problem_id` を NULL 可に
3. **`lib/feedback.ts` に種別を足す**（**ここが1か所にまとまっているので、ここだけ直せば画面もAPIも揃う**）
4. **画面**（`ResultView.tsx`）
   - 既存の2つと同じ形で3つ目を足す
   - **▼ を押すとテキストボックスが開く**（既存が既に開閉式なので合わせる）
   - 文言に禁止語を使わない（`CLAUDE.md`）
5. **API**（`app/api/feedback/route.ts`）
   - 種別を受け付ける
   - **保存に成功したらメールを送る**（④の判断どおり）
   - **メールの失敗でユーザーへの応答を失敗にしない**（案Aの場合）
6. **メール送信を作る**（例: `lib/mail.ts`）
   - 宛先は環境変数から読む
   - 本文に**どの問題・どのユーザー・いつ**を入れる（返信や調査に要る）
7. `.env.local.example` に項目を足す + Vercel に設定
8. **実際に送って、メールが届くことを確認する**
9. `npm test` と `npm run build`

## 注意

- **メールアドレスをコードに直書きしないこと。** 公開リポジトリなので、
  そのまま迷惑メールの標的になります
- **メールの失敗でユーザーを困らせないこと。** 保存が成功していれば意見は失われません
- **意見の本文を外部AIに送らないこと。** これは採点ではないので、`/api/score` の
  PII 検査とは別の経路です。**メールで自分に送るだけ**にすること
- 既存の2種（異議・誤り報告）の動きを壊さないこと。**`unique` 制約を変えるなら、
  既存2種の「書き直し」の挙動が保たれるか確認する**
- 文言に禁止語を使わないこと（`CLAUDE.md`）。「不満」という語を画面に出すかは判断が要る
  （**ネガティブな言い方を避ける方針**なので、「もっとこうしてほしい」のような言い方が合う）
