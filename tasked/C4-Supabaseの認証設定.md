## 何をするか

**Supabase の管理画面でしか変えられない設定を3つ入れる。**

一番大事なのは **「他所で漏れたパスワードを拒否する」** 設定。

---

## なぜ必要か

**Ferret のコードでは絶対に塞げないため。**

新規登録するとき、パスワードはブラウザから Supabase に**直接**送られる。
Ferret のサーバーを通らないので、こちらで検査を入れる余地がない。

そして実際に来る攻撃は、**他のサービスから漏れた「メールアドレスとパスワードの組」を
そのまま試す**というもの。1つのアカウントにつき1回しか試さないので、
「短時間に何度も試すのを止める」という一般的な防御が効かない。
パスワードの長さも関係ない（`hogehoge2020` は12文字だが、漏洩リストに載っている）。

**この設定だけがこれを止められる。**

やらなかった場合に効いてくるのは課金開始後。
乗っ取られたアカウントで採点を回されると、**AI採点の費用がこちら持ちで出ていく。**
本人は自分の枠を使えなくなる。段位や認定証も「乗っ取れば手に入るもの」になる。

---

## 手順

### 1. 漏洩パスワードの拒否（最優先）

Supabase の管理画面 →
**Authentication → Sign In / Providers → Password**

- **Prevent use of leaked passwords** を **ON**
- Minimum password length を **8** に（ついでに）

※ 契約プランによっては漏洩パスワードの拒否が使えないことがある。
その場合は長さの設定だけ先に入れて、**このファイルに「プラン制限で入れられなかった」と記録すること。**

### 2. 認証まわりの回数制限を確認

**Authentication → Rate Limits**

初期値のままでよいかを確認する。総当たり攻撃への耐性はここで決まる。
変更した場合は記録を残すこと。

### 3. パスワード変更時の再確認（C3 と同時でよい）

パスワード変更の画面を作るとき（C3）に、
**古いパスワードの入力を必須にする設定**（`secure_password_change`）を有効にする。
いまは画面が無いので、C3 とセットで行う。

#### 先に本番の実測をしてから着手した

票には「設定を入れる」としか書いていないが、**入れる前の状態を測ってある。**
測らずに入れると「もともと入っていたのか、自分が入れたのか」が後で分からなくなる。

**副作用のない測り方を見つけた。** メール欄をわざと不正な形式（`not-an-email`）にして
登録APIを叩くと、**パスワードの検査だけが先に走る**。アカウントは作られず確認メールも飛ばないので、
本番に対してそのまま実行できる。検査の順序は実測で確認した（短すぎるパスワード →
メール形式ではなく `weak_password` が返る）。

```bash
U=$(grep '^NEXT_PUBLIC_SUPABASE_URL=' .env.local | cut -d= -f2-)
A=$(grep '^NEXT_PUBLIC_SUPABASE_ANON_KEY=' .env.local | cut -d= -f2-)
curl -sS -X POST "$U/auth/v1/signup" -H "apikey: $A" -H "Content-Type: application/json" \
  -d '{"email":"not-an-email","password":"abcdefg"}'       # 7文字
curl -sS -X POST "$U/auth/v1/signup" -H "apikey: $A" -H "Content-Type: application/json" \
  -d '{"email":"not-an-email","password":"hogehoge2020"}'   # 流出済みの12文字
```

| | 実施前 | 実施後 |
|---|---|---|
| 7文字 | `400 validation_failed`（＝**通っていた**。最低6文字だった） | **`422 weak_password` "at least 8 characters"** |
| `hogehoge2020` | `400 validation_failed`（＝通る） | `400 validation_failed`（**変わらず。HIBP は OFF**） |

この手順は `ideas/セキュリティ_残課題.md` §1-2 に残した。今後の再確認はそちらを見ればよい。

#### 気づいた点1: 画面の案内と実際が、ここで初めて一致した

`app/register/page.tsx` の入力欄は `placeholder="8文字以上"`、
`lib/auth/errors.ts` の案内も「8文字以上」。**コード側は先に8で書かれていたのに、
本番は6のままだった** ── つまり今日まで「8文字以上と案内しながら7文字で登録できる」状態だった。
**コードの変更は不要**（もともと8で書かれているため）。

#### 気づいた点2: 一番効く設定が入らなかった ── 期限の考え方

`password_hibp_enabled`（流出パスワードの拒否）は**契約プランで選択できなかった。**

票と `残課題` §1-2 が書いているとおり、**実際に来る攻撃を止められるのはこれだけ**で、
文字数8はもともと付随の項目。**つまり入ったのは効かないほうである。**

効いてくるのは**課金開始後**（乗っ取られたアカウントでAI採点を回されると原価がこちら持ちで出る）。
したがって**期限は D-1（プラン別の採点上限）に着手する時点**で、**C5（デプロイ）のブロッカーではない。**
`残タスク.md` §C-3 はチェックを入れずに残し、プラン引き上げが要る旨を追記した。

#### 判断: 登録済みメールの案内（F3 から回ってきた件）

F3 が `E-112` として「決定と実装のずれ」を C4 に回していたので、ここで判断した。

- **実際:** 登録済みのメールで再登録すると「確認メールを送りました」と出るが**メールは届かない。**
  `enable_confirmations = true` の間、Supabase が登録済みメールの signUp にも成功を返すため
  （偽のユーザーを返す）、`lib/auth/errors.ts` の `user_already_exists` に**到達しない**

  止めるにはメール確認を切るしかなく、それは実在しないメールで無限にアカウントを作れる状態
