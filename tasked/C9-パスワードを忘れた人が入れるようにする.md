# C9. パスワードを忘れた人がログインできるようにする

**種別:** 実装
**規模:** 中
**前提として終わっていること:** **C1（メール送信）と C6（独自ドメイン）** ── どちらも✅済み
**関連:** C3（せってい画面）でパスワード**変更**は作った。こちらは**忘れた場合**の入口

> ### ⚠️ 同時進行の注意
> `app/login/page.tsx` と `lib/auth/errors.ts` を触る。
> `proxy.ts` の `matcher` にも足すので、**同じく matcher を触るタスクとは順番にやること。**

**先に読むもの**
- `app/login/page.tsx`（いまのログイン画面）
- `app/settings/PasswordForm.tsx` あたり（C3 で作ったパスワード変更。**書き方の手本**）
- `lib/auth/errors.ts`（エラー文の方針）
- `tasked/C1-メール送信をResendに切り替える.md` の作業記録（**メールの経路がどうなっているか**）

---

## 何をするか

**パスワードを忘れた人が、いま二度とログインできない。**

ログイン画面に「パスワードをお忘れですか」が無く、リセットの仕組みも入っていません。
確認したところ `resetPasswordForEmail` を呼んでいる箇所がゼロで、画面もありません。

メールでリセット用のリンクを送り、新しいパスワードを設定できるようにする。

---

## なぜ必要か

**公開済みなので、実際に困る人が出ます。**

パスワードを忘れる人は必ずいます。いまは**問い合わせ先も無い**ので、
その人のアカウントは**完全に使えなくなります。** 進捗も連続日数も取り戻せません。

「パスワードを忘れたら終わり」は、継続を売りにするサービスとして成立しません。

---

## ⚠️ オーナーに確認すること

> パスワードのリセットについて決めることがあります。
>
> **① メールが届かないアドレスの人をどうしますか**
> リセットのメールは登録済みのアドレスにしか送れません。
> **メールアドレス自体が使えなくなっている人は、この方法では戻せません。**
> - **案A: そのまま（戻せない）**（おすすめ）
>   個人開発の規模なら、これで十分です
> - 案B: 問い合わせ窓口を作って手作業で対応する
>   窓口の運用が増えます。**本人確認の手段も決める必要があります**
>
> **② 登録されていないアドレスを入れられたとき、何と表示しますか**
> - **案A:「送信しました」と出す（実際には送らない）**（おすすめ）
>   **登録済みかどうかを外部に教えない**ためです。C7 で同じ判断をしています
> - 案B:「登録されていません」と出す
>   分かりやすいですが、**メールアドレスの登録有無を誰でも調べられます**
>
> **おすすめは案A**です。C7（登録済みメールの案内文）で
> 「Supabase がアカウントの有無を伏せる仕様」に合わせた文面を作っているので、そこと揃えます。
>
> **③ リンクの有効期限をどうしますか**
> 既定（1時間程度）のままでよいか。短くすると安全ですが、**メールを見るのが遅れた人が失敗します。**

---

## 手順

1. 上の3点を決める
2. **入口を作る** — ログイン画面に「パスワードをお忘れですか」を置く
3. **メール送信の画面**（`app/forgot-password/page.tsx` など）
   - メールアドレスを入れて `supabase.auth.resetPasswordForEmail` を呼ぶ
   - `redirectTo` は**本番のドメイン**を指すこと（`ferretcode.com`）
   - **ログイン不要の画面にする**（`proxy.ts` の `matcher` に足さない）
4. **新しいパスワードを設定する画面**（`app/reset-password/page.tsx` など）
   - メールのリンクから来た状態で `updateUser({ password })` を呼ぶ
   - **リンクの受け取り方は C1 の作業記録を読むこと。**
     確認メールで `token_hash` 方式を使う経路を足してあるので、同じ形になる可能性が高い
5. **Supabase のメール文面を用意する**
   - 管理画面 → Authentication → Email Templates の「Reset Password」
   - **日本語にし、禁止語を使わないこと**（`CLAUDE.md` の文言ルール）
6. **実際に試す** — 使い捨てアカウントを作り、パスワードを忘れた状態から復帰できるか
7. `npm test` `npm run build`

## 注意

- **リセットのリンクは本人しか見られない前提。** リンクを持っている人は
  そのアカウントのパスワードを変えられるので、**有効期限と1回限りの扱いを確認すること**
- **リセット後は既存のセッションを切ること**を検討する。乗っ取られていた場合に追い出せる
- 文面に禁止語を使わないこと。「忘れた」は事実の記述なので使えるが、
  **責めるような言い方にしない**（`CLAUDE.md`）
- **本番のドメインを指すこと。** `localhost` を指すと届いたリンクが機能しない（C1 で同じ地雷があった）

**票と変えたところ（理由つき）**

1. **`/reset-password` を「ログインしていれば開ける画面」にしなかった。**
   票は「メールのリンクから来た状態で `updateUser` を呼ぶ」までしか決めていない。
   ところが `recovery` のリンクを開いた人はその時点でログイン状態になるので、
   ログインの有無で通すと**いまのパスワードを知らない人がパスワードを差し替えられる画面**が1枚できる。
   これは `app/settings/PasswordForm.tsx` が「いまのパスワードを先に確認する」ことで塞いだ穴と同じもの。
   代わりに、コールバックが `recovery` を確認できたときだけ**短命の Cookie（10分・httpOnly・path 限定）**を付け、
   その印が無ければ入力欄を出さない形にした（`lib/auth/recovery.ts` に理由を全部書いてある）。
   これで「**差し替えるには、いまのパスワードか、メールの受信のどちらかが要る**」が両方の入口で揃う。

   **印は署名してある**（HMAC。鍵は特権キーから導出 ── `tests/support/password.ts` と同じ考え方で、
   環境変数を増やさない）。最初は素の `1` で書いたが、**それでは印の意味が無い**と気づいて直した ──
   ここで想定している相手は「ログイン中の端末を触れる人」で、その人は開発者ツールから
   Cookie を1行で書ける。期限も署名の対象に入れてあるので、**持ち出しても延命できない**
   （Cookie の `maxAge` はブラウザ側の約束事にすぎず、保存して入れ直せば無効化できる）。
   検査は単体 §21（U-900〜U-906）と E2E の E-146。
2. **`lib/auth/errors.ts` は触っていない。** 既存の分岐（`weak_password` / `same_password` /
   `over_email_send_rate_limit` / `validation_failed`）でそのまま足りた。
   期限切れの1件だけ画面側に置いた ── 文面が「再設定のメールをもう一度送る」という
   **その画面でしか意味を持たない指示**になるため（`PasswordForm` が
   「いまのパスワードが違います」を自前で持っているのと同じ形）。
3. **`redirectTo` は `location.origin` ではなく本番URL優先**（`configuredAppOrigin()`）。
   ただし**いまの文面では使われない** ── 本文が `{{ .SiteURL }}/auth/callback?...` を自分で組むので、
   行き先は管理画面の Site URL で決まる。渡してあるのは文面を既定に戻した日の保険。
4. **`proxy.ts` は1行も触っていない。** ログイン不要のままにするので、
   `lib/seo/site.ts` の `CRAWL_DISALLOW` も触らない（2つは同じ範囲を指す約束）。
   代わりに **I-311 で「matcher に足していないこと」を固定**した ──
   足した瞬間に「パスワードを忘れた人だけが通れない経路」ができる。

**実測（2026-08-26・ローカル ＋ 実 Supabase）**

- **通し（E-144）:** 使い捨てアカウント → 管理APIで `token_hash` を発行 →
  `/auth/callback?token_hash=…&type=recovery` → `/reset-password` で設定 →
  **あたらしいパスワードでログインできた。** メールの受信だけを管理APIで代替している
  （`recoveryTokenFor`。送信しないので送信上限も消費しない）
- **リンクは1回限り（E-145）:** 同じリンクの2度目は `?error=auth_callback` でログイン画面へ
  （サーバーのログに `Email link is invalid or has expired`）
- **他の端末の扱い（`scope: "others"` の裏取り）:** 別クライアントでログインしておいて
  パスワードを差し替えたところ、**呼ぶ前の時点で既に切れていた** ──
  他端末のアクセストークンは `403` / 更新トークンは `400`。
  Supabase 側が他のセッションを無効にしている。**それでも明示的に呼ぶ**のは、
  これが設定と版に依存する挙動で、外れても気づけないため（コードのコメントに残した）
- **画面:** 幅320 / 900、明るい / 暗い の両方を撮って確認。
  320px で「ログ／イン」「送り直／す」と語の途中で折り返していたので、
  末尾のリンクに `whitespace-nowrap` を付けた。小さい文字の段が3つ続いていたのを1つにまとめた
- `npm test` **800 passed**（新規は結合 I-311 / I-345〜I-348 の6件 ＋ 単体 §21 の U-900〜U-906 の7件。
  `recovery` を受け取るようになったので I-340 の対象外リストからは1件外した）/
  `npm run build` 通過 / `npx playwright test` は auth（19 passed / 1 skipped）と security（15 passed）

**残っていること（どちらもオーナーの手が要る）**

1. **メール文面の反映。** リポジトリの控えは用意したが、**実際に送られるのは Supabase 管理画面の内容**。
   反映には Auth の書き込み権限を持つ個人アクセストークンが要る（`.env.local` には無い）:

   ```bash
   printf 'PAT: '; read -rs SUPABASE_ACCESS_TOKEN; echo; export SUPABASE_ACCESS_TOKEN
   node supabase/templates/apply.mjs
   unset SUPABASE_ACCESS_TOKEN
   ```

   **反映するまでは既定の英語の文面が送られる**（リンクの形も `{{ .ConfirmationURL }}` のままなので、
   受け取り口の `/auth/callback?token_hash=…&type=recovery` に来ない ── **反映が実質の前提**）
2. **実配信の確認。** 反映後に、自分の受け取れるアドレスで `/forgot-password` から送り、
   届いたリンクから設定し直せることを見る（`ferretcode.com` から届くこと）。
   ここだけは受信箱が要るので自動では確かめられない
