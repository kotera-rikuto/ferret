# E9. 暗い配色への切り替え

**種別:** 実装（見た目）
**規模:** 小
**前提として終わっていること:** なし（**設定画面があると切り替えの置き場所ができる → C3**）

> ### ⚠️ 同時進行の注意
> **色を追加するだけなら衝突しにくいが、E5（コードの色付け）が `app/globals.css` を触る。**
> E5 が動いているときは、**どちらか一方を先に終わらせること**（色の定義が同じ場所に入る）。
> `app/settings/page.tsx` は C3・D2 も触る。**着手前に `main` を取り込むこと。**

**先に読むもの**
- `design/移植残タスク.md` の「運用メモ」
- `design/stages-desktop-dark.html`（**暗い配色の完成品。色の定義がそのまま入っている**）

---

## 何をするか

画面全体を暗い配色に切り替えられるようにする。

**色の設計はすでに終わっている。** `design/stages-desktop-dark.html` に
暗い配色の色の一覧が用意されていて、**それを差し込めば切り替わる構造**にしてある。

---

## なぜ必要か

コードを読むアプリなので、**暗い配色を好む人が多い**と考えられる。
夜に使う人にとっては目の負担も変わる。

作りとしては最初から想定されているので、**作業は小さい。**

---

## ⚠️ オーナーに確認すること

> 切り替えの方式を決めてください。
>
> **① どうやって切り替えますか**
> - **案A: 端末の設定に自動で従う**（おすすめ・作業が最小）
>   スマホやパソコンの「ダークモード」設定を見て自動で切り替わります。
>   利用者は何もしなくてよい
> - 案B: アプリ内に切り替えボタンを置く
>   好みで選べます。ただし**設定画面（C3）が先に必要**で、
>   選んだ状態を覚えておく仕組みも要ります
> - **案C: 両方**（自動を初期値にして、変えたい人は設定で変えられる）
>
> **おすすめは案A**です。作業が最も小さく、後から案Cに広げられます。
>
> **② コードの部分はどうしますか**
> コードを表示する枠は**いまも暗い配色**です（明るい画面でも暗いまま）。
> 全体が暗くなったとき、コードの枠だけ浮かないように調整が要ります。

---

## 手順

1. 切り替え方式を決める
2. `design/stages-desktop-dark.html` の中にある色の定義を、
   `app/globals.css` に暗い配色として追加する
3. 切り替えの仕組みを入れる（決めた方式に応じて）
4. **全画面を確認する**
   - タイトル / ログイン / 新規登録 / ステージ選択 / 問題 / リザルト
   - **文字が読めなくなっている箇所がないか**を特に見る
5. `npm run build`

## 注意

- **色を画面ごとに直接書かないこと。** まとめて定義した色を使うこと。
  そうしないと切り替えが効かない箇所が残る
- クリア・満点・未開放などの**状態を表す色**は、暗い配色でも区別が付くか確認すること
- マスコットの画像は背景が透明なので、暗い背景でどう見えるかを確認すること

#### 設計判断と、その理由

**1. `--color-brand-deep` はモックの値（`#8f5400`）を採らず、明るい側（`#c47000`）のまま据え置いた。**

モックではこの色がアンバーのボタンの**下端**（＝影として濃い側）にしか出てこないが、
実装では**リンク・見出し・チップの文字色**にも使っている（`text-brand-deep` が18か所）。
モックの値を当てると読みやすさが 3.1:1（本文）／2.4:1（`bg-brand-tint` のチップ上）まで落ちる。
据え置けば 5.0:1 で読め、かつ `--color-brand` より濃いのでボタンの下端としても従来どおり影に見える。
ステージ画面の白いボタン（`bg-white text-brand-deep`）が唯一の明るい下地で、
ここを明るいアンバーにすると逆に読めなくなる点でも据え置きが都合よい。
**1つの色が持つ2つの役目が、暗い配色でだけ食い違う箇所。**

**2. `--color-danger` を新設し、`text-red-600` を6ファイルで置き換えた。**

入力の不備を伝える赤が、暗い背景では 3.9:1 まで沈む。ただし**退会ボタンだけは赤を背景に使っていて白文字が乗る**ため、
`--color-red-600` ごと明るくすると今度はそちらが読めなくなる（白文字が 4.9:1 → 2.8:1）。
文字に使う赤だけを別の名前にして分離した。

> ⚠️ **ここで一度取り違えた。** 明るい側の値を `#dc2626` と書いたが、**Tailwind v4 の red-600 は `#e40014`**
> （＋広色域用の `lab()`）で、別の色だった。「暗い配色を足すだけ」のつもりで**明るい画面のエラー文の赤が変わっていた。**
> `var(--color-red-600)` を参照する形に直し、`origin/main` と computed 値が一致することを実測で確認した。
> **U-805 がこれを固定している。**

**3. 暗い側の定義は `@theme` の外・レイヤーの外に置く。**

Tailwind は `@theme` の中身を `@layer theme` の `:root` として出す。同じ中に入れると同じ変数の後勝ちになり、
**切り替えていないのに明るい配色のほうが暗い色で描かれる。** ビルド後の CSS で
`@layer utilities` を閉じた後に出ていることを実測で確認した。U-802 がこれを固定している。

**4. コードパネルは中を変えず、外周だけ直した。**

パネルの下地（`#1d2021`）と暗い背景（`#191309`）は明るさがほぼ同じで、境目が消えてコードが宙に浮く。
`--color-code-edge` を他のパネルと同じ線の色にし、`[data-code-panel]` に内側の1px を足して輪郭を戻した。
`--color-code-bg` / `--color-code-ink` は既製テーマから写した値なので触っていない（U-604 の前提）。

**5. 最初の描画より前に `<head>` の script で当てる。**

React が動き出すのは HTML を読み終えた後なので、それを待つと**暗いはずの人に一瞬だけ明るい画面が見える。**
手順は Next.js の `preventing-flash-before-hydration` に従った（`suppressHydrationWarning` が要る理由も同項）。

**6. `ThemeSync` は開発中だけのための部品。**

開発中の React は部品を1回組み立て直し、そのとき `<html>` の属性を「React が知っているものだけ」に戻す。
script が当てた配色はそこで消えるので、これが無いと**開発中の見え方と本番の見え方が食い違う。**

#### 詰まった点

- **`useLayoutEffect` の中で `setState` すると lint が落ちる**（`react-hooks/set-state-in-effect`）。
  `useSyncExternalStore` に置き換えた。サーバー側では既定を返し、ブラウザ側でだけ実際の値に差し替わる
- **配色の変化を「変えた側から知らせる」形にするか、属性を見張る形にするかで迷った。**
  当初は前者にして「開発中にズレる」と判断したが、**測り直したら両方とも同じように追いついた**
  （ズレて見えたのは計測が下の50msの窓に入っていたためで、方式のせいではなかった）。
  最終的に `MutationObserver` にしたのは別の理由 ── **属性を書き換える経路が `applyTheme` だけではない**
  （最初の描画より前に走る script、開発中の組み立て直し）。知らせる形式だと
  「いまの値を読む先」と「変化を伝える経路」が別々になり、通らなかった書き換えのぶんだけ表示が古く残る
- **せってい画面を開き直した直後だけ、選ばれている側のボタンの枠が約50ms 遅れて追いつく**（実測）。
  画面全体の色は script が当てているので最初から正しい。消すにはサーバーが配色を知る必要があり、
  Cookie を読むと全画面が動的描画に変わる。釣り合わないので追いつく形のままにした
- `npm run build` の後に `next dev` を動かすとフォントの解決に失敗する（`.next` の作り分け）。`rm -rf .next` で直る
- 見た目の確認は Playwright で行った。**ブラウザの MCP は別セッションが専有していて使えない**
