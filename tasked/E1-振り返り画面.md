## 何をするか

**採点の内訳を見せる画面を作る。** サイドバーに「ふりかえり」が準備中として置いてある。

いまリザルト画面に出るのは、点数・内訳の数字・AIからの一言だけ。
**「なぜその点数になったのか」が分からない。**

---

## なぜ必要か

採点は4つの観点で見ている。

| 観点 | 見ているもの | 配点 |
|---|---|---|
| 中核 | 結論が合っているか | 48点 |
| 根拠 | どこを見てそう言えるのかに触れているか | 16点 |
| 深さ | もう一歩踏み込めているか | 12点 |
| 明確さ | 言い切れているか | 4点 |

そして**それぞれについて「回答のどの部分をそう判断したか」も記録してある。**
これを見せれば、次に何を書き足せばいいかが分かる。

**材料は全部揃っていて、表示していないだけ。**

---

## すでにあるデータ

`user_attempts` の `axes` という欄に、観点ごとに次が入っている。

- 判定（できている / 半分 / まだ）
- **回答のどこをそう判断したか（引用）**
- その引用が本当に回答に含まれていたか

---

## 手順

1. `app/review/[id]/page.tsx` を作る
   - **`proxy.ts` の保護対象に `/review` は既に入っている**（追加不要）
2. 該当する回答を取り出す
   - 手本は `app/result/[id]/page.tsx`
   - **ユーザー本人の権限で取ること**（他人の回答が見えないように）
3. 表示する
   - 4観点それぞれの判定と、引用された箇所
   - 模範解答
   - 自分が書いた回答
4. リザルト画面に「ふりかえる」ボタンを付ける
   - `ResultView.tsx` にコメントアウトされた導線が残っている
5. サイドバーの「準備中」を外す
6. `npm test` と `npm run build`

## 注意

- **模範解答と採点基準の扱いに注意。**
  問題画面ではこれらを画面に渡さないようにしてある（`select` で欄を名指ししている）。
  振り返りで模範解答を見せる場合も、**採点基準（`rubric_items`）は渡さないこと。**
  これが見えると、キーワードを並べるだけで点が取れてしまう
- 古い回答には `axes` が入っていないことがある（採点の仕組みを変える前のもの）。
  **無い場合に画面が壊れないようにすること**
- 文言に禁止されている言葉を使わない（`CLAUDE.md` の文言ルール）。
  「まだ」の判定を「できていない」と書かないこと

#### 実装前に実データを見て分かったこと（票に書いていなかった2点）

回答76件を数えた結果。**どちらも画面の作りを変えている。**

1. **保存されている `axes` の形が3通りある** ── `axes,keyword_hits,evidence_capped` /
   `+fabrication_suspected` / `+matched_reject`。画面の中で分岐を書くと
   「古い行を開いたときだけ落ちる」形の壊れ方をするので、`lib/review/axes.ts` に隔離した
2. **`ideas/db仕様.md` の `axes` の説明が実装と違う** ── 文書は
   `{ core: { verdict, evidence, demoted }, ... }` と書いているが、実際は
   **`{ axes: [ {axis, verdict, raw, demoted, evidence, points}, ... ], ... }` の配列**。
   → **この票では直していない**（`ideas/` は担当外）。**Z1 か次にDB文書を触る人へ申し送り**

#### 設計判断（理由つき）

- **引用は表示のたびに回答本文と突き合わせ、実在するものだけを出す**（`quoteVerified` を再利用）。
  採点時に照合しているのは `full` の引用だけで、`partial` / `none` の引用は裏を取っていない。
  さらに格下げされた行には**回答に1文字も存在しない文字列**が保存されている。
  そのまま出すと「本人が書いていない文章を本人の回答として見せる」ことになる。
  実データでも `none` の25件に引用が入っていた。**特別扱いを1つも書かずに全部塞げる**ので、
  観点ごとの分岐ではなくこの一律のルールにしてある（E2E の `E-713` が本物の格下げを経由して見ている）
- **内訳が読めないときは空の内訳を作らない。** 4観点すべて「まだ」の行と、記録が残っていない行は
  画面での意味がまったく違う。混ぜると、古い回答を開いた人に「全部できていない」という嘘を見せる。
  読めなければ `null` を返し、画面は「採点のしくみを入れかえる前に解いたものです」と出す
- **観点の点数の合計が点数に届かない回は、理由を画面に書く。** 上限（読み違い・引用ゼロ・捏造検出）が
  働いた回では内訳の合計と実際の点数が合わない。**黙ってずれていると採点の不具合に見える**
- **解放判定（`loadProgress`）を通していない。** リザルト画面と同じ考え方で、
  関門は「自分の回答が残っているか」1つ（回答がある＝そのステージは開いていた）。
  模範解答を出す画面だが、**回答の有無のほうが解放判定より強い条件**なので漏れない。
  結合テスト `I-872` が「回答が無いときは問題のクエリすら走らない」を固定している
- **コードもこの画面に出した**（票には無い）。実データで見たところ**お手本の読み方が
  コードの中の名前（`orders` / `res.ok` / `reason`）を指しており、コードが無いと読めなかった**。
  問題画面の `CodePanel` は持ってきていない（あれは実行結果と並べるための枠で、この画面には実行結果を出さない）。
  色付けの実体（`lib/code/highlight.ts`）は同じものを使っている
- **AI の文章（よかったところ / つぎの一歩）はこの画面に出していない。** リザルトの担当。
  両方に出すと、片方だけ直したときに同じ回答について違うことを言う2画面ができる。
  代わりに「この回の結果を見る」のリンクを置いた
- **一覧は最高点ではなく最新の回答を出す。** ふりかえり本体が最新の回を出すので、
  最高点を出すと一覧と開いた先で数字が食い違う回ができる（`I-382` と同じ事情）
