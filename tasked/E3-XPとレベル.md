## 何をするか

問題をクリアすると経験値がたまり、たまるとレベルが上がる仕組みを作る。

**いまは入れ物だけあって中身が無い。**
`users` に `xp` という欄はあるが、**増やす処理がどこにもない。** ずっと0のまま。

デザイン案にはXPバーと「クリアで +10 XP」の表示があるが、
**嘘の数字を出さないために、いまは表示自体を出していない。**

---

## なぜ必要か

このジャンルのアプリで「積み上がっている感じ」を出す定番の仕組み。
Ferret は「登っていくマップ」で進捗を見せているが、
**クリア済みの問題を復習しても何も増えない**ので、繰り返す動機が弱い。

ただし**急ぎではない。** 無くても機能する。

---

## ⚠️ オーナーに確認すること（このタスクは判断が主）

**設計を決めないと作れない。着手前に必ず確認すること。**

> 経験値の仕組みを作ります。決めることが4つあります。
>
> **① いつ、いくつ増やしますか**
> - 案A: クリアしたとき +10（デザイン案の想定）
> - 案B: 点数に応じて増やす（55点なら+5、80点以上なら+15 など）
> - 案C: 初回クリアだけ増やす
>
> **考えどころ:** 同じ問題を何度も解いて経験値を稼げてよいかどうかです。
> **稼げてよい**なら案A・B。**1問1回にしたい**なら案C。
> 復習を促したいなら「2回目以降は少なめ」という手もあります。
>
> **② レベルはいくつまで、どう上がりますか**
> 問題は全部で100問なので、**全部クリアしたときにどのレベルにいてほしいか**から
> 逆算するのが分かりやすいです。例えば「全クリアでレベル10」なら、
> 1レベルあたり10問ぶんの経験値になります。
>
> **③ レベルが上がると何が起きますか**
> - 案A: 表示が変わるだけ
> - 案B: 称号がもらえる（仕様書の「段位」につながる）
> - 案C: 何かが解放される
>
> **仕様書には「段位」「認定証」という構想があります。**
> レベルをそこに繋げるなら、いま決めておくほうが後の手戻りが減ります。
>
> **④ いま入れますか**
> 経験値は**一度公開すると変えにくい**（数字が変わると利用者が混乱する）ので、
> 急がないなら問題が揃ってからのほうが安全です。

---

## 手順

1. 上の4点を決める
2. 採点のAPI（`app/api/score/route.ts`）でクリア時に `users.xp` を増やす
   - **特権キーで更新すること**（ユーザー自身に増やさせない。増やせると自己申告になる）
   - 同じ回答の再送では増やさないこと
3. レベルの計算を1か所にまとめる（例: `lib/progress/level.ts`）
   - **外部に依存しない純粋な計算にすること**（画面からもテストからも使えるように）
   - 手本は `lib/progress/streak.ts`（連続日数の計算）
4. 表示する
   - リザルト画面のXPバーと「+10 XP」
   - ステージ選択の右側に現在のレベル
5. 単体テストを書く
6. `npm test` と `npm run build`

## 注意

- **経験値の加算は必ずサーバー側で行うこと。**
  ブラウザから増やせる作りにすると、点数と同じく自己申告になる。
  `users` は「本人が読めるだけ・書けない」設定になっているので、そこを崩さないこと
- **加算に失敗しても採点は成功させること。** 経験値のために採点結果を捨てない
- 数字の設計を変えると**過去の利用者の数字も変わる。** 公開後の変更は慎重に

### 決めたこと（オーナー判断・2026-08-18）

| 論点 | 決定 |

| ② レベル | **1レベル = クリア10問ぶん（100 XP）**・上限なし |
| ③ 上がると何が起きるか | **表示が変わるだけ。** 段位・認定証には繋げない |
| ④ 呼び方 | **「レベル」そのまま** |

②は1点だけ判断とずれる。**0 XP がレベル1なので、全100問クリア（1,000 XP）はレベル11**
（全問パーフェクトなら16）。「全クリアでちょうど10」にするにはレベル1の幅を200 XP にするしかなく、
**最初のレベルアップが20問先**になって序盤の手応えが消えるため、10問ごとに上がる側を採った。

### `users.xp` への加算はしていない（票の手順2からの意図的な逸脱）

**票は「採点APIでクリア時に `users.xp` を増やす」としていたが、加算そのものをやめた。**
XP は `user_attempts` から毎回導出する（`lib/progress/level.ts`）。

- カウンタを持つと「採点結果は保存できたのに XP の加算だけ失敗した」というズレが生まれる。
  しかも**画面は普通に描画される**（数字が少し小さいだけ）ので、まず気づけない
- 導出なら `user_attempts` が唯一の真実のまま保てる。**ストリークが既に同じ作り**で、
  `lib/progress/streak.ts` の冒頭に同じ理由が書いてある
- 票の終了条件「ユーザーが自分で経験値を増やせない」は、**書き込む経路が存在しない**ことで満たす。
  `users` は読みも書きもしていない（結合テスト I-384 で固定）
- 結果として **`app/api/score/route.ts` は1行も変えていない。** B2・D1・E2・G3 と衝突しない

**問題ごとの最高点だけを見る。** これが「解き直しでの稼ぎ」を防いでいる本体。

- 1回ごとに足す形だと、**同一回答の再送（リプレイ）でも増える。** リプレイも
  `user_attempts` に行を作る（`usage.replayed = true`）ので、送信ボタンを押すだけで増えてしまう
- 最高点の差で見れば点が同じなら差は0。**判定を1つも書かずに防げる**
- 点が下がっても減らさない（`xpGain` の下限は0）。一度手に入れたものは減らない見せ方に揃えた

### 「レベル◯になった」という文は出していない

実装して画面で見た結果、**出せないと分かった。**

XP を導出しているので、リザルトの「前の状態」は**その問題ぶんを引いた値**であって、
その回答をした時点の値ではない。累計100 XP・この問題の寄与が10なら「前は90＝レベル1」になるが、
**同じ寄与の問題が他にもあれば、そのどれを開いても同じ主張が出る**（実測で確認した）。

代わりに**バーの動きだけ**を残した。レベルをまたぐ回は
**満たす → 一瞬で空にする → 新しいレベルのぶんを満たす。**
前の位置から新しい位置へ直接動かすと（90% → 0%）増えたのに**縮んで**見える。
文にすると事実の主張になるが、動きは演出（クリア時の紙吹雪と同じ扱い）なので、
毎回再生されても嘘にはならない。
